RAG 入门 ​

RAG（Retrieval-Augmented Generation，检索增强生成）不是某个框架，也不等于“把 PDF 丢进向量数据库”。它是一种应用架构：先从外部知识源检索证据，再让大模型依据证据回答问题。

这一页只讲最基础、最容易看清数据流的 2-Step RAG（也常被称为 Naive RAG）。学完后，你应该能够独立回答四个问题：

  1. 一份文档怎样变成可以搜索的知识片段？
  2. 用户问题怎样找到相关片段？
  3. 怎样要求模型只根据证据回答并给出引用？
  4. 回答错误时，怎样判断问题出在检索还是生成？

IMPORTANT

本页先把最小闭环讲透。查询改写、混合检索、Rerank、GraphRAG、Agentic RAG 和自适应检索属于后续章节，不能在还没理解基础链路时堆进第一个系统。

1. 为什么需要 RAG ​

大模型本身有两个和知识问答直接相关的限制：

  • 知识有截止时间：模型训练完成后，不会自动知道企业刚发布的制度。
  • 上下文容量有限：不能把整个公司的所有文档无差别塞进一次请求。

假设公司在 2026 年 7 月发布了一份退款制度：

text
退款申请提交后需要人工审核，审核通常在 3 个工作日内完成。
1

用户问：“退款审核需要多久？”

直接询问模型时，它可能凭训练记忆猜测。RAG 则先搜索企业知识库，把上面的原文作为证据放进模型上下文，再要求模型作答。

因此，RAG 解决的不是“让模型记住更多”，而是让应用在运行时完成：

text
用户问题 -> 找到相关证据 -> 把证据交给模型 -> 生成有依据的回答
1

RAG 也不是万能方案：

需求更合适的方式
根据非结构化文档回答问题RAG
查询订单当前状态、库存数量调用业务 API 或数据库工具
让模型稳定使用特定语气或格式Prompt、结构化输出或微调
执行退款、发邮件、创建工单Agent 工具调用

一个常见错误是把所有数据都向量化。订单金额、库存数量、账户余额等结构化事实，通常应该直接查询权威业务系统，而不是依赖相似度搜索。

2. 先看懂完整链路 ​

基础 RAG 由两条链路组成。

2.1 索引链路：把资料变成可检索知识 ​

索引链路通常离线运行，或者在文档发生变化时运行：

text
知识源
  -> 文档加载器（Loader）
  -> 解析与清洗
  -> 文本切分器（Splitter）
  -> 嵌入模型（Embedding Model）
  -> 向量 + 原文 + 元数据
  -> 向量数据库（Vector Store）

5. 文档加载器：读取不同知识源 ​

文档加载器负责从外部来源读取数据，并转换成统一的文档对象。知识源可能是：

  • 本地 TXT、Markdown、PDF、Word、Excel；
  • 网页、Wiki、Notion、Google Drive；
  • 数据库记录、对象存储文件；

加载器的职责是读取与标准化，不是检索，也不是回答问题。

6. 文本切分器：建立可检索的最小单元 ​

为什么不能把整本手册作为一条记录？

  • 整篇文档的向量会混合多个主题，检索精度下降；
  • 检索回来后可能超过模型上下文限制；
  • 引用只能指向整份文档，无法定位证据；
  • 文档局部更新时，需要重新处理整篇内容。

文本切分器把长文档拆成多个 Chunk。最基础的递归字符切分示例：

python
from langchain_core.documents import Document
from langchain_text_splitters import RecursiveCharacterTextSplitter

documents = [
    Document(
        page_content=(
            "第一章 退款条件\n"
            "订单完成后 7 天内可以申请退款。\n\n"
            "第二章 审核时效\n"
            "退款审核通常在 3 个工作日内完成。"
        ),
        metadata={"source_id": "refund-policy", "version": "2026-07"},
    )
]

splitter = RecursiveCharacterTextSplitter(
    chunk_size=200,
    chunk_overlap=30,
    separators=["\n\n", "\n", "。", "；", "，", "",],
    add_start_index=True,
)
chunks = splitter.split_documents(documents)

for index, chunk in enumerate(chunks):
    print(index, len(chunk.page_content), chunk.metadata)
    print(repr(chunk.page_content))

三个参数需要真正理解：

  • chunk_size：单个文本块的目标上限。这里按字符计算，不一定等于 Token 数。
  • chunk_overlap：相邻文本块重复保留的内容，用于减轻语义在边界处被切断的问题。
  • add_start_index：记录文本块在原文中的起始位置，方便追溯。

6.1 常见切分器怎么选择 ​

切分器适用场景注意事项
RecursiveCharacterTextSplitter普通中英文文档，入门首选默认分隔符未必适合所有中文资料
CharacterTextSplitter文档有稳定单一分隔符容易在长度限制处留下过大块
MarkdownHeaderTextSplitterMarkdown 技术文档重点是保留标题层级元数据
Token 级切分需要精确控制模型输入长度Tokenizer 必须与目标模型兼容

header_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=[("#", "chapter"), ("##", "section")]

6.2 Chunk 不是越小越好 ​

text
太小：语义不完整，检索到“3 个工作日”却不知道它指退款审核。
太大：混入无关主题，浪费上下文并降低匹配精度。
1
2

切分策略应服从文档结构：优先按章节、标题、段落和句子边界切分，再用长度限制兜底。代码、表格、合同条款和聊天记录需要不同策略。

500、1000 或 20% overlap 都不是普遍正确的固定答案。应使用真实问题集比较不同切分方案的检索效果。

6.3 给 Chunk 分配稳定 ID ​

切分完成后应生成稳定 ID，而不是每次启动都随机编号：

for index, chunk in enumerate(chunks):
    source = chunk.metadata["source_id"]
    version = chunk.metadata["version"]
    start = chunk.metadata["start_index"]
    chunk.id = f"{source}@{version}#{start}-{index}"

7. Embedding：把文本映射为向量 ​

Embedding 模型接收文本并输出一个数值向量：

text
"退款审核需要多久" -> [0.12, -0.31, 0.08, ...]
1

向量本身不是摘要，也不能由人直接阅读。它的用途是让系统通过距离或相似度判断两段文本在模型表示空间中是否接近。

索引时：

python
document_vectors = embedding_model.embed_documents(
    [chunk.page_content for chunk in chunks]
)
1
2
3

查询时：

python
query_vector = embedding_model.embed_query("退款审核需要多久？")
1

基础阶段需要知道这些边界：

  • 文档向量和问题向量必须来自兼容的模型与配置；
  • 更换 Embedding 模型后，通常需要重新计算全部文档向量；
  • 向量维度必须符合向量数据库集合或字段的配置；
  • 语义相似不等于事实正确，也不等于用户有权查看；
  • 多语言资料应验证模型的中英文及跨语言检索能力；
  • Embedding 输入同样有长度上限，不能跳过切分直接输入无限长文本。

7.3 相似度是什么 ​

常见计算方式包括余弦相似度、点积和欧氏距离。选择哪一种，应遵循 Embedding 模型的说明，并与向量索引的距离配置保持一致。

以余弦相似度为例，它关注两个向量方向是否接近：

text
cosine(q, d) = (q · d) / (||q|| × ||d||)
1

不要把不同距离指标的数值阈值直接互相套用，也不要假设某个固定分数在所有模型和语料中都代表“相关”。

8. 向量数据库：保存并搜索知识片段 ​

向量数据库或向量存储通常保存：

text
ID + 向量 + 原始文本 + 元数据
1

用户提问后，系统用查询向量搜索最接近的文档向量，并返回 Top-K 个候选片段。

常见选择包括：

  • 本地实验：内存索引、FAISS、Chroma；
  • 已经使用 PostgreSQL：PostgreSQL + pgvector；
  • 独立向量检索服务：Qdrant 等。

选型时不应只看“能否存向量”，还要看：

  • 元数据过滤和租户隔离；
  • 更新、删除和批量写入；
  • 精确检索与近似检索；
  • 索引构建、内存占用和查询延迟；
  • 备份恢复、监控和水平扩展；
  • 稀疏向量、混合检索或多向量能力。

Qdrant 把一条记录称为 Point，由向量和 Payload 元数据组成；pgvector 则把向量作为 PostgreSQL 的字段类型，并支持精确搜索以及 HNSW、IVFFlat 近似索引。它们的数据模型和运维方式不同，不应仅凭示例代码长短决定选型。

一次基础检索包含以下步骤：

  1. 校验问题不能为空；
  2. 根据用户身份构造权限过滤条件；
  3. 使用 Embedding 模型生成问题向量；
  4. 在授权范围内执行相似度搜索；
  5. 返回 Top-K 文本块及其元数据。

K 太小可能漏掉必要证据；K 太大会引入噪声并占用模型上下文。应该用评测集选择，而不是凭感觉固定为 3 或 5。

11. 完整实现：从 Document 到 LCEL RAG ​

下面的程序可以直接运行。它使用真实的 LangChain 数据结构、VectorStore、Retriever、Prompt、Runnable 和输出解析器；只有 Embedding 与聊天模型是无需账号的教学替代物。

python
from __future__ import annotations

import math
from collections.abc import Sequence

from langchain_core.documents import Document
from langchain_core.embeddings import Embeddings
from langchain_core.language_models.fake_chat_models import (
    FakeMessagesListChatModel,
)
from langchain_core.messages import AIMessage
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda, RunnablePassthrough
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_text_splitters import RecursiveCharacterTextSplitter


# 只用于离线教学：通过少量关键词生成确定性向量，不是真实语义模型。
class TutorialEmbeddings(Embeddings):
    vocabulary = (
        "退款", "审核", "工作日", "物流",
        "配送", "发票", "订单", "开具",
    )

    def _embed(self, text: str) -> list[float]:
        values = [float(text.count(term)) for term in self.vocabulary]
        values.append(float(not any(values)))
        norm = math.sqrt(sum(value * value for value in values)) or 1.0
        return [value / norm for value in values]

    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        return [self._embed(text) for text in texts]

    def embed_query(self, text: str) -> list[float]:
        return self._embed(text)


# 第一步：Loader 的输出。这里直接构造 Document，方便示例离线运行。
documents = [
    Document(
        id="refund-policy",
        page_content=(
            "退款规则\n订单完成后 7 天内可以申请退款。\n\n"
            "审核时效\n退款申请提交后需要人工审核，"
            "审核通常在 3 个工作日内完成。"
        ),
        metadata={
            "source": "refund-policy.md",
            "category": "售后制度",
            "version": "2026-07",
            "tenant_id": "acme",
        },
    ),
    Document(
        id="shipping-guide",
        page_content=(
            "物流规则\n订单发货后可以查看承运商和物流单号。"
            "配送状态会在承运商扫描包裹后更新。"
        ),
        metadata={
            "source": "shipping-guide.md",
            "category": "物流制度",
            "version": "2026-06",
            "tenant_id": "acme",
        },
    ),
]


# 第二步：切分，并为每个 Chunk 分配稳定 ID。
splitter = RecursiveCharacterTextSplitter(
    chunk_size=55,
    chunk_overlap=10,
    separators=["\n\n", "\n", "。", "；", "，", ""],
    add_start_index=True,
)
chunks = splitter.split_documents(documents)

for index, chunk in enumerate(chunks):
    source_id = chunk.metadata["source"].removesuffix(".md")
    chunk.id = f"{source_id}#chunk-{index}"

print("=== 切分结果 ===")
for chunk in chunks:
    print(chunk.id, chunk.metadata, repr(chunk.page_content))


# 第三步：Embedding 并写入 VectorStore。
embeddings = TutorialEmbeddings()
vector_store = InMemoryVectorStore(embeddings)
vector_store.add_documents(
    documents=chunks,
    ids=[chunk.id for chunk in chunks],
)


# 第四步：先单独测试检索，不要一开始就把问题甩给模型。
print("\n=== 带分数检索 ===")
for document, score in vector_store.similarity_search_with_score(
    "退款审核需要几个工作日？",
    k=2,
):
    print(f"score={score:.3f}", document.id, document.page_content)


# 第五步：创建 Retriever，并把 list[Document] 格式化为证据文本。
retriever = vector_store.as_retriever(search_kwargs={"k": 2})


def format_documents(documents: Sequence[Document]) -> str:
    if not documents:
        return "没有检索到相关证据。"

    return "\n\n".join(
        f"[证据 {index}]\n"
        f"ID: {document.id}\n"
        f"来源: {document.metadata['source']}\n"
        f"版本: {document.metadata['version']}\n"
        f"正文: {document.page_content}"
        for index, document in enumerate(documents, start=1)
    )


# 第六步：构造 Prompt。
prompt = ChatPromptTemplate.from_messages(
    [
        (
            "system",
            "你是企业知识库助手。只能根据证据回答；"
            "每个事实必须标注证据编号；"
            "证据不足时回答‘现有资料不足，无法确认’。\n\n"
            "{context}",
        ),
        ("human", "{question}"),
    ]
)


# 第七步：离线 Fake Model。真实模型会在下一小节替换它。
model = FakeMessagesListChatModel(
    responses=[
        AIMessage(content="退款审核通常在 3 个工作日内完成。[证据 1]")
    ]
)


# 第八步：使用 LCEL 连接检索、格式化、Prompt、模型和输出解析器。
context_chain = (
    RunnableLambda(retriever.invoke)
    | RunnableLambda(format_documents)
)

rag_chain = (
    {
        "context": context_chain,
        "question": RunnablePassthrough(),
    }
    | prompt
    | model
    | StrOutputParser()
)


answer = rag_chain.invoke("退款审核需要多久？")
print("\n=== RAG 回答 ===")
print(answer)

13. 一个回答为什么会错 ​

RAG 的错误不能笼统归因于“大模型不行”。先判断错误发生在哪一层。

13.1 没有检索到正确证据 ​

可能原因：

  • 文档根本没有被加载或索引；
  • PDF 解析顺序错误；
  • Chunk 切得过大、过小或切断了关键语义；
  • Embedding 模型不适合当前语言和领域；
  • Top-K 太小；
  • 权限或元数据过滤条件写错；
  • 文档版本更新后，旧向量没有删除。

此时调整 Prompt 通常没有用，因为模型根本没看到正确资料。

13.2 检索到了正确证据，但回答仍然错误 ​

可能原因：

  • Prompt 没有限制模型依据证据回答；
  • 上下文中混入太多无关或冲突片段；
  • 证据编号与原始文本的映射错误；
  • 模型忽略了拒答规则；
  • 输出没有经过结构校验和引用校验。

15. 入门阶段的最低质量标准 ​

第一个 RAG 不要求具备所有高级能力，但不能只以“能回答一个问题”为完成标准。

  • 能导入至少两种真实文档并抽样检查解析结果；
  • 每个 Chunk 都有稳定 ID、来源、版本和位置；
  • 文档与问题使用兼容的 Embedding 配置；
  • 能通过元数据过滤隔离不同租户或权限；
  • 能查看每次查询返回的 Top-K 原文；
  • 找不到证据时会拒答，而不是继续猜；
  • 回答中的引用只能来自本次授权检索结果；
  • 文档更新或删除后，索引不会继续返回旧内容；
  • 至少准备一小组“问题—相关文档”样例进行回归测试。
