数据与任务 ​

Agent 服务上线后最危险的问题通常不是“选 PostgreSQL 还是 Redis”，而是没有定义哪套数据才是真相：任务显示失败，退款其实成功了；checkpoint 恢复后重复发邮件；Redis 清空后审批和任务一起丢失。

本页建立一条清晰主线：

text
API transaction
  -> task + idempotency + outbox 写入 PostgreSQL
  -> publisher 将 outbox 投递到队列
  -> worker 领取并获得 lease
  -> LangGraph 从 checkpoint 恢复
  -> domain service 幂等提交副作用
  -> task/event/checkpoint 更新
  -> SSE/查询读取公共投影

1. 先定数据所有权 ​

1.1 四类数据 ​

数据示例权威来源
业务事实订单、退款、客户、审批结果领域业务库
执行状态task 状态、尝试次数、租约、事件任务数据库
Agent 状态messages、node state、interruptLangGraph Checkpointer
长期记忆用户偏好、跨线程摘要LangGraph Store/专用记忆库

它们可以物理上位于同一个 PostgreSQL 集群，但逻辑所有权、schema、迁移和访问账号要分开。

1.2 Cache 不是第五套真相 ​

Redis 常用于：

  • 短期缓存；
  • 速率限制计数；
  • 分布式信号或 pub/sub；
  • Queue/Broker（取决于框架）；
  • 短期会话或锁辅助数据。

不要默认把这些放入仅有 Redis 的易失 key：

  • 资金动作结果；
  • 唯一审批记录；
  • 幂等键唯一记录；
  • 必须恢复的任务和事件；
  • 唯一一份长期记忆。

即使启用 Redis 持久化，它的事务、备份、恢复和一致性语义也要按真实用途评估，不能因为“很快”就成为所有数据的权威来源。

2. Checkpointer、Store 和业务库边界 ​

Checkpointer ​

保存一次线程/任务执行中的图状态：

text
thread_id -> checkpoint sequence -> channel/state values
1

用于中断恢复、时间旅行、容错和持久执行。它不是订单数据库，不能用 checkpoint 中的 order_status 作为最终业务真相。

Store ​

保存跨线程、跨会话的数据，例如用户偏好或经过治理的长期记忆：

text
namespace = (tenant_id, user_id, "preferences")
key       = "communication-style"
value     = {...}
1
2
3

记忆需要来源、置信度、更新时间、过期/删除和用户可见性，不能把模型每次推断都永久保存。

业务库 ​

保存领域不变量：订单是否可退款、已经退了多少、审批是否有效。所有真实副作用由领域服务和业务事务控制。

任务库 ​

保存 API 可见生命周期、幂等接收、租约、尝试次数、取消意图和公共事件。

正确读取顺序示例：

text
checkpoint 说“准备提交退款”
      |
      v
领域服务查询订单当前状态 + idempotency_key
      |
      +-- 已退款 -> 返回既有结果
      +-- 可退款 -> 原子提交
      +-- 不可退款 -> 领域冲突

3. PostgreSQL 基础 Schema ​

下面给出任务、幂等、事件和 Outbox 的最小教学 DDL：

sql
CREATE TYPE agent_task_status AS ENUM (
  'queued',
  'running',
  'waiting_approval',
  'cancel_requested',
  'canceled',
  'succeeded',
  'failed'
);

CREATE TABLE agent_tasks (
  task_id uuid PRIMARY KEY,
  tenant_id text NOT NULL,
  actor_id text NOT NULL,
  graph_version text NOT NULL,
  input_schema_version integer NOT NULL
    CHECK (input_schema_version > 0),
  status agent_task_status NOT NULL,
  input_json jsonb NOT NULL,
  public_result_json jsonb,
  error_code text,
  attempt integer NOT NULL DEFAULT 0 CHECK (attempt >= 0),
  max_attempts integer NOT NULL CHECK (max_attempts > 0),
  cancel_requested_at timestamptz,
  lease_owner text,
  lease_expires_at timestamptz,
  fence_token bigint NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  finished_at timestamptz,
  CHECK (
    (status IN ('succeeded', 'failed', 'canceled'))
    = (finished_at IS NOT NULL)
  )
);

CREATE INDEX agent_tasks_runnable_idx
  ON agent_tasks (next_attempt_at, created_at)
  WHERE status = 'queued';

CREATE INDEX agent_tasks_recoverable_idx
  ON agent_tasks (status, lease_expires_at)
  WHERE status IN ('running', 'cancel_requested');

CREATE INDEX agent_tasks_tenant_idx
  ON agent_tasks (tenant_id, created_at DESC);

CREATE TABLE agent_idempotency (
  tenant_id text NOT NULL,
  endpoint text NOT NULL,
  idempotency_key text NOT NULL,
  payload_sha256 text NOT NULL,
  task_id uuid NOT NULL REFERENCES agent_tasks(task_id),
  created_at timestamptz NOT NULL DEFAULT now(),
  expires_at timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, endpoint, idempotency_key)
);

CREATE TABLE agent_task_events (
  task_id uuid NOT NULL REFERENCES agent_tasks(task_id),
  sequence bigint NOT NULL,
  schema_version integer NOT NULL CHECK (schema_version > 0),
  event_type text NOT NULL,
  public_payload_json jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (task_id, sequence)
);

CREATE TABLE outbox_events (
  event_id uuid PRIMARY KEY,
  aggregate_type text NOT NULL,
  aggregate_id text NOT NULL,
  event_type text NOT NULL,
  schema_version integer NOT NULL CHECK (schema_version > 0),
  payload_json jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz,
  publish_attempts integer NOT NULL DEFAULT 0,
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  last_error text,
  claim_owner text,
  claim_expires_at timestamptz,
  CHECK (
    (claim_owner IS NULL) = (claim_expires_at IS NULL)
  )
);

CREATE INDEX outbox_unpublished_idx
  ON outbox_events (next_attempt_at, claim_expires_at, created_at)
  WHERE published_at IS NULL;

input_schema_version 和事件 schema_version 必须在创建记录时写入，之后不能根据“当前代码版本”猜测。graph_version 决定由哪版图执行，input_schema_version 决定如何解析输入，两者不是同一概念。Outbox 也保存它所承载事件的 schema 版本，消费者才能拒绝或迁移未知版本，而不是误读 JSON。

4. 任务接收必须是一笔事务 ​

API 接收任务的原子目标：

text
要么 task + idempotency + outbox 全部存在
要么全部不存在

python
def accept_task(command: CreateTask, db: Connection) -> TaskReceipt:
    fingerprint = sha256(canonical_json(command.payload))

    with db.transaction():
        previous = db.fetch_one(
            """
            SELECT payload_sha256, task_id
              FROM agent_idempotency
             WHERE tenant_id = %s
               AND endpoint = %s
               AND idempotency_key = %s
             FOR UPDATE
            """,
            command.tenant_id,
            "/v1/tasks",
            command.idempotency_key,
        )
        if previous:
            if previous["payload_sha256"] != fingerprint:
                raise IdempotencyConflict()
            return TaskReceipt(previous["task_id"], replayed=True)

        task_id = uuid4()
        db.execute("INSERT INTO agent_tasks (...) VALUES (...)")
        db.execute("INSERT INTO agent_idempotency (...) VALUES (...)")
        db.execute(
            "INSERT INTO outbox_events (...) VALUES (...)"
        )

    return TaskReceipt(task_id, replayed=False)

5. 为什么需要 Transactional Outbox ​

这段代码有双写漏洞：

python
db.insert_task(task)
queue.publish(task.task_id)  # 两个系统，不是一笔事务
1
2

失败窗口：

顺序结果
DB 成功，publish 前崩溃任务永远不执行
publish 成功，DB 回滚Worker 找不到任务
publish 响应丢失后重试消息重复

Outbox 将任务和“需要发布”事件写入同一个数据库事务，再由独立 publisher 重试投递：

text
transaction: task + outbox commit
                     |
                     v
publisher claims rows -> queue publish -> mark published
1
2
3
4

Publisher 仍可能在 publish 成功、标记前崩溃，因此队列是至少一次投递，Worker 必须幂等。

5.1 领取 Outbox ​

Publisher 先用短事务领取一批记录，并为这批记录设置租约。$1 是每个 Publisher 进程唯一且不会复用的实例 ID：

sql
WITH claimed AS (
  SELECT event_id
    FROM outbox_events
   WHERE published_at IS NULL
     AND next_attempt_at <= now()
     AND (
       claim_owner IS NULL
       OR claim_expires_at <= now()
     )
   ORDER BY created_at
   FOR UPDATE SKIP LOCKED
   LIMIT 100
)
UPDATE outbox_events AS e
   SET publish_attempts = publish_attempts + 1,
       claim_owner = $1,
       claim_expires_at = now() + interval '30 seconds'
  FROM claimed
 WHERE e.event_id = claimed.event_id
RETURNING e.*;

6. Queue 的语义比品牌更重要 ​

选型前明确：

  • 投递是 at-most-once、at-least-once 还是其他语义；
  • ACK 在什么时候发生；
  • Worker 崩溃后消息何时重新可见；
  • 是否支持延迟任务、优先级、取消、死信；
  • 顺序范围是全局、队列还是 key；
  • payload 大小与保留期限；
  • broker 故障和网络分区时的行为；
  • 如何观测 queue depth、oldest age、redelivery。

Agent 系统通常按 at-least-once 设计：允许重复领取，但通过幂等和 fencing 阻止重复副作用。

7. Worker 领取、租约与 Fencing Token ​

7.1 租约 ​

任务不能永久处于 running。Worker 领取时设置：

text
lease_owner = worker-17
lease_expires_at = now + 60s
fence_token = fence_token + 1
1
2
3

执行期间每 20 秒 heartbeat。Worker 崩溃后，另一个 Worker 可在租约过期后接管。

7.2 为什么只用分布式锁不够 ​

旧 Worker 可能发生长时间 GC/网络暂停：租约已过期，新 Worker 接管；旧 Worker 恢复后仍提交结果。Fencing Token 让存储拒绝旧执行者：

sql
UPDATE agent_tasks
   SET status = 'succeeded',
       public_result_json = $1,
       finished_at = now(),
       updated_at = now()
 WHERE task_id = $2
   AND lease_owner = $3
   AND fence_token = $4
   AND lease_expires_at > now()
   AND status = 'running';

7.3 必须按消息里的任务 ID 领取 ​

队列消息是唤醒某个具体任务的通知。Worker 收到任务 B 的消息时，不能运行一个“任选下一条 runnable task”的 SQL；否则它可能领取任务 A，完成 B 的消息处理后却 ACK A/B 中错误的一条，留下无法解释的状态。

$1 是 Worker ID，$2 是消息中的 task_id，$3 是消息中的租户提示。SQL 用它们精确匹配任务；返回行里的租户仍是后续授权使用的权威值：

sql
WITH requested_task AS (
  SELECT task_id, status
    FROM agent_tasks
   WHERE task_id = $2
     AND tenant_id = $3
     AND (
       status = 'queued'
       OR (
         status = 'running'
         AND lease_expires_at <= now()
       )
       OR (
         status = 'cancel_requested'
         AND (
           lease_expires_at IS NULL
           OR lease_expires_at <= now()
         )
       )
     )
     AND next_attempt_at <= now()
   FOR UPDATE
)
UPDATE agent_tasks AS t
   SET status = CASE
         WHEN requested_task.status = 'cancel_requested'
           THEN 'cancel_requested'::agent_task_status
         ELSE 'running'::agent_task_status
       END,
       attempt = attempt + 1,
       lease_owner = $1,
       lease_expires_at = now() + interval '60 seconds',
       fence_token = fence_token + 1,
       updated_at = now()
  FROM requested_task
 WHERE t.task_id = requested_task.task_id
RETURNING t.*;

8. 重试先分类失败 ​

失败示例策略
temporary连接重置、短暂 503有界指数退避 + jitter
rate_limited模型 429尊重 Retry-After、租户公平性
permanent400、资源状态不允许不重试，明确失败
unknown_commit请求超时但下游可能成功查询权威状态，禁止盲重试
poison task每次都触发确定性 bug有界尝试后死信
canceled用户请求取消安全点停止，不重试

项目中的可运行策略：

python
import math
from enum import StrEnum

from pydantic import BaseModel, Field


class FailureKind(StrEnum):
    TEMPORARY = "temporary"
    RATE_LIMITED = "rate_limited"
    PERMANENT = "permanent"
    UNKNOWN_COMMIT = "unknown_commit"


class RetryDecision(BaseModel):
    should_retry: bool
    delay_seconds: float = Field(ge=0)
    reason: str


def retry_decision(
    failure: FailureKind,
    *,
    attempt: int,
    max_attempts: int,
    operation_idempotent: bool,
    base_delay_seconds: float = 0.5,
    retry_after_seconds: float | None = None,
    max_delay_seconds: float = 300.0,
) -> RetryDecision:
    if attempt < 1 or max_attempts < 1:
        raise ValueError("attempt values must be positive")
    if not math.isfinite(base_delay_seconds) or base_delay_seconds < 0:
        raise ValueError("base delay must be finite and non-negative")
    if not math.isfinite(max_delay_seconds) or max_delay_seconds <= 0:
        raise ValueError("max delay must be finite and positive")
    if retry_after_seconds is not None and (
        not math.isfinite(retry_after_seconds)
        or retry_after_seconds < 0
    ):
        raise ValueError("Retry-After must be finite and non-negative")
    if attempt >= max_attempts:
        return RetryDecision(
            should_retry=False,
            delay_seconds=0,
            reason="attempt_limit",
        )
    if failure == FailureKind.UNKNOWN_COMMIT:
        return RetryDecision(
            should_retry=False,
            delay_seconds=0,
            reason="query_authoritative_status",
        )
    if failure == FailureKind.PERMANENT:
        return RetryDecision(
            should_retry=False,
            delay_seconds=0,
            reason="permanent_failure",
        )
    if not operation_idempotent:
        return RetryDecision(
            should_retry=False,
            delay_seconds=0,
            reason="operation_not_idempotent",
        )

    exponential_delay = min(
        max_delay_seconds,
        base_delay_seconds * (2.0 ** min(attempt - 1, 1023)),
    )
    if failure == FailureKind.RATE_LIMITED and retry_after_seconds is not None:
        return RetryDecision(
            should_retry=True,
            delay_seconds=min(retry_after_seconds, max_delay_seconds),
            reason="server_retry_after",
        )

    return RetryDecision(
        should_retry=True,
        delay_seconds=exponential_delay,
        reason="bounded_retry",
    )

进入死信的条件应明确：

  • graph version 已无可用 Worker；
  • 不变量被破坏；

11. 调度与延迟任务 ​

场景包括：

  • Retry-After 后重试；
  • 审批超时；
  • 每日知识库同步；
  • 长期任务租约扫描；
  • 记忆过期和数据删除；
  • 定期评测与对账。

调度设计要回答：

  • 时间使用 UTC 还是业务时区；
  • 错过一次执行是补跑、跳过还是合并；
  • 多调度器如何避免重复；
  • 同一计划重叠时允许并发还是跳过；
  • 修改 schedule 后旧任务如何处理；
  • 每次实例如何生成稳定幂等键。

Cron 表达式只是触发器，不提供 exactly-once。定时任务仍要幂等。

13. Redis 的正确用法 ​

缓存 ​

Key 必须包含租户、资源、权限/版本：

text
rag:v4:tenant:acme:acl:7:query:<sha256>
profile:v2:tenant:acme:user:u-1
1
2

设置 TTL、防击穿、最大值和序列化版本。权限撤销和数据删除必须能失效缓存。

限流 ​

使用 Lua/原子命令实现窗口或令牌桶；多 key 操作要理解集群 slot。Redis 不可用时，高风险配额选择 fail closed，普通请求可按明确降级策略处理。

锁 ​

锁适合减少重复工作，不应单独保护资金不变量。数据库唯一约束、条件更新和 fencing 才是最终边界。

Pub/Sub ​

适合在线通知，不保证离线消费者收到。需要可靠 SSE 重放时，公共事件仍应持久化；Redis Streams 等方案也要验证 pending、claim、trim 和故障语义。

16. LangGraph 与任务队列如何组合 ​

一种清晰分工：

text
Task System: 排队、优先级、租约、Worker 容量、重投
LangGraph:    节点、状态、路由、checkpoint、interrupt
Domain DB:    订单、退款、审批和副作用幂等
1
2
3

Worker 收到 task_id 后：

  1. 按消息中的 task_id 精确领取任务并得到 fence token；
  2. 读取 task、graph version 和 trusted tenant；
  3. 使用稳定 thread_id 调用对应版本的图；
  4. checkpoint 恢复后重新授权；
  5. 节点副作用调用幂等领域服务；
  6. 中断等待审批时释放 Worker，不持续占用线程；
  7. 将公共事件和 task 状态事务化更新；
  8. ACK 消息；失败则按分类安排重试或死信。

第 8 步 ACK 的始终是触发当前 task_id 的那条消息；数据库查询不得顺手领取另一条任务。

不要每次消息重投都创建新 thread ID，否则 checkpoint 无法关联；也不要让两个 Worker 并发运行同一 thread，除非图和 checkpointer 明确支持且你已处理冲突。

17. 优先级、公平与背压 ​

只有 high/normal/low 三个队列仍可能饿死低优先级任务。设计：

  • 每租户并发上限；
  • weighted fair scheduling；
  • 高优先级保留容量但设置配额；
  • queue depth 和 oldest message age 门禁；
  • 任务接收时估算 token、工具和时间成本；
  • 容量不足早拒绝或降级模型；
  • 人工审批恢复与新任务分别保留容量。

监控平均等待时间不够。P95 很好但最老任务卡了两小时仍可能被掩盖，因此必须监控 oldest age。

迁移策略：

  • 旧 Worker 粘性：旧任务继续由旧代码处理；
  • 读时迁移：恢复前将旧 State 转新 State；
  • 双读/双写：短期兼容新旧 schema；
  • 显式终止：不兼容且不可安全迁移的任务进入人工处理。

数据库迁移遵循 expand/contract：先新增兼容字段和代码，回填，再切换读取，最后在确认无旧 Worker/任务后删除。

这些版本必须持久化在第 3 节的任务/事件表中。任务接收时校验当前输入并记录版本；读取旧任务时根据已存版本选择解析器或迁移器。事件写入时记录该 payload 的 schema 版本，不能因为部署了新代码就原地把旧事件解释为新结构。

19. 备份、恢复与数据生命周期 ​

必须实际演练：

  • PostgreSQL 备份和时间点恢复；
  • checkpoint、task、领域库恢复点不一致时如何对账；
  • Redis 清空后哪些能力退化、如何重建；
  • 队列丢失后如何从 Outbox/任务表重新驱动；
  • 对象存储文档与向量索引如何重建；
  • PII 删除如何覆盖业务表、Store、checkpoint、Trace、缓存和备份策略。

恢复成功的标准不是“数据库启动了”，而是关键不变量仍成立、任务不重复产生副作用、租户不串数据。

21. 常见错误 ​

用 Redis 保存唯一任务真相 ​

缓存、broker 和权威任务状态混在一起，清理或故障会让任务不可解释。先确定一致性与恢复要求。

把 Checkpoint 当业务事务 ​

Checkpoint 记录图状态，不能回滚支付、邮件或数据库副作用。领域服务必须幂等。

DB 写完直接 publish ​

双写窗口会丢任务或重复消息。使用 Outbox，并接受消费者仍要去重。

宣称 Queue exactly-once ​

网络和崩溃窗口使端到端 exactly-once 很难成立。按至少一次投递 + 幂等副作用设计。

超时后立即重试写工具 ​

可能第一次已经成功。先用幂等键查询权威结果。

租约过期就认为旧 Worker 死了 ​

旧 Worker 可能恢复。使用 fencing token 保护提交。

死信自动无限重放 ​

确定性 bug 会持续消耗容量并重复风险动作。修复、审核、限批重放。

定时器触发等于只执行一次 ​

调度器故障切换也会重复触发。每次业务执行仍需稳定幂等键。

23. 练习 ​

练习一：数据地图 ​

为退款 Agent 列出业务事实、任务状态、checkpoint、Store、缓存、事件和 Trace，给每项指定 owner、权威来源、保留期限和删除方式。

在 PostgreSQL 实现 task + idempotency + outbox 原子写入。并发 50 次相同 key，只得到一个 task；不同 payload 必须冲突。

练习三：Outbox 故障 ​

在 commit 后、publish 前和 publish 后、mark 前分别杀进程。证明任务不丢，重复消息不重复副作用。

练习四：租约和 Fencing ​

暂停 Worker A 直到租约过期，让 B 接管，再恢复 A。证明只有 B 能更新任务和提交领域动作。

练习五：重试与死信 ​

注入 temporary、429、permanent、unknown commit 和 poison task，验证退避、查询、最大尝试和人工重放。

练习六：框架 Spike ​

从候选中选两个，在相同案例测试崩溃重投、延迟任务、取消、graceful shutdown、指标和运维复杂度，不只比较 Hello World。

练习七：恢复演练 ​

恢复旧数据库快照并重建队列/缓存。对账 task、checkpoint 和退款事实，证明不会重复退款。
