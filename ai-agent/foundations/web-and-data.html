Web 与数据基础 ​

AI Agent 很少只在模型内部工作。它通常要调用模型 API、查询业务系统、执行工具、保存会话，并在网络抖动或服务限流时恢复。模型回答得再好，如果 HTTP 客户端会无限等待、重复扣款，或者把缓存当成唯一数据源，系统仍然不可靠。

本章不要求你先会 Web 后端开发。我们从一次请求开始，逐步建立一条完整链路：

-> 认证并发送 HTTP 请求
-> 分类处理超时和状态码
-> 在安全条件下重试
-> 用异步并发提升吞吐
-> 将事实写入 PostgreSQL
-> 用 Redis 加速或协调

学完后，你应该能够：

  • 阅读和构造 HTTP/REST API 请求；
  • 正确处理认证、超时、限流、重试与幂等；
  • 解释同步、异步、协程、事件循环和并发限制；
  • 使用参数化 SQL、事务、索引和连接池；
  • 判断一份数据应放在 PostgreSQL 还是 Redis；
  • 为成功、超时、错误响应和部分失败编写测试。

阅读说明：稳定原理与版本事实 ​

以下原理不依赖某个框架版本：HTTP 方法和状态码语义、超时必须有上限、重试必须考虑幂等、数据库事务应尽量短、缓存不是默认事实来源。

本章代码分别采用 requests、HTTPX、psycopg 3 和 redis-py 的常见 API 风格。这不是“当前最新版”声明。安装命令、异常类和参数名可能随版本变化，实际项目应以锁文件及所用版本的官方文档为准。不要为了复制示例而取消依赖锁定。

一、HTTP 是一次有边界的消息交换 ​

HTTP 请求由客户端发出，HTTP 响应由服务端返回。一次请求至少要回答六个问题：

问题HTTP 中的载体示例
请求谁URLhttps://api.example.com/v1/tickets/42
做什么MethodGET、POST、PATCH、DELETE
附加条件HeaderAuthorization、Accept
提交什么BodyJSON、表单或二进制内容
是否成功Status Code200、404、429
返回什么Response Header + BodyJSON 和 Content-Type

1. URL 不只是一个字符串 ​

以这个 URL 为例：

text
https://api.example.com:443/v1/tickets/42?include=messages#summary
\___/   \_____________/\__/\____________/ \_____________/ \_____/
scheme         host     port      path           query      fragment
1
2
3
  • scheme 决定协议，生产 API 通常使用 https；
  • host 和 port 决定连接目标；
  • path 定位资源；
  • query 表达筛选、分页等可选参数；
  • fragment 只供客户端定位页面片段，不会发送给 HTTP 服务端。

不要手工拼接未经转义的查询参数：

response = requests.get(
    "https://api.example.com/v1/tickets",
    params={"q": keyword, "page": 1},
    timeout=(3.0, 20.0),
)

2. REST 是资源设计风格，不是强制协议 ​

REST API 通常用 URL 表示资源，用 HTTP 方法表达操作：

意图请求常见成功码
查询工单列表GET /v1/tickets200 OK
查询一张工单GET /v1/tickets/42200 OK
创建工单POST /v1/tickets201 Created
局部修改工单PATCH /v1/tickets/42200 OK 或 204 No Content
删除工单DELETE /v1/tickets/42204 No Content

这是一组常见约定，不代表所有 API 都完全相同。调用前应阅读该 API 的契约，尤其是分页、错误体、幂等和限流规则。

JSON 是常见的数据交换格式，但它只支持对象、数组、字符串、数字、布尔值和 null。日期、十进制金额、二进制内容都需要双方约定表示方式：

json
{
  "ticket_id": "T-42",
  "created_at": "2026-07-16T09:30:00Z",
  "amount": "99.90",
  "refundable": true
}

3. Header 描述请求和响应的元数据 ​

常见 Header：

Header方向作用
Accept: application/json请求客户端希望收到 JSON
Content-Type: application/json请求/响应Body 实际采用 JSON 编码
Authorization: Bearer ...请求携带访问凭证
User-Agent请求标识客户端，便于服务端排障
X-Request-ID请求/响应关联一次跨服务调用
Retry-After响应建议客户端等待多久再请求
Cache-Control响应描述缓存策略

Accept 与 Content-Type 不相同：前者描述“想要什么”，后者描述“Body 实际是什么”。Header 名不区分大小写，但值的语义由各 Header 规范决定。

4. 状态码先分类，再读取错误体 ​

范围含义客户端通常怎么做
1xx临时信息一般由 HTTP 库处理
2xx请求被成功处理校验 Body，不要只看状态码
3xx重定向明确是否允许跟随，防止凭证发往意外域名
4xx请求或权限问题多数不应盲目重试
5xx服务端失败可在满足幂等和退避条件时重试

Agent 开发中尤其常见：

  • 400 Bad Request：输入不符合 API 约定；
  • 401 Unauthorized：缺少、过期或无效凭证；
  • 403 Forbidden：身份已知，但没有权限；
  • 404 Not Found：资源不存在，也可能用于隐藏资源；
  • 409 Conflict：资源状态冲突或幂等键冲突；
  • 422 Unprocessable Content：语法可读，但字段校验失败；
  • 429 Too Many Requests：触发限流，应查看 Retry-After；
  • 500/502/503/504：服务端或网关暂时异常。

200 也不保证数据可用。Body 可能为空、不是 JSON、字段缺失，或业务状态明确失败。因此网络成功之后还要做结构校验和业务校验。

二、认证：证明“你是谁”和“你能做什么” ​

1. API Key ​

API Key 通常标识一个应用或项目：

http
X-API-Key: <secret>
1

有些服务也把 Key 放进 Authorization。具体位置由服务端契约决定。不要把 Key 放在 URL 查询参数中，因为 URL 更容易进入浏览器历史、代理日志和监控记录。

2. Bearer Token ​

Bearer Token 的含义是“持有者即可使用”，所以必须像密码一样保护：

http
Authorization: Bearer <access-token>
1

Token 可能包含过期时间和权限范围，也可能只是不可读的随机字符串。客户端不应假设它一定是 JWT，更不应只解码而不验证就信任其中内容。

3. OAuth 解决委托授权 ​

OAuth 的核心不是某种 Token 字符串，而是：资源所有者允许客户端在限定范围和期限内访问资源。典型角色包括客户端、授权服务和资源服务。

应用层至少要理解：

  • Access Token 有有效期和权限范围（scope）；
  • Refresh Token 用于申请新的 Access Token，不应发送给资源 API；
  • 授权码、客户端凭证等流程适用于不同参与者，不能混用；
  • 401 后是否刷新 Token，需要并发控制，避免大量请求同时刷新；
  • OAuth 流程的精确参数和安全要求必须遵循授权服务文档。

三、用 requests 编写可靠的同步客户端 ​

同步代码一次只沿当前调用栈向下执行，容易理解，适合命令行工具、低并发任务和初学阶段。下面是一个包含失败路径的客户端，而不只是“请求成功”的演示。

python
from __future__ import annotations

from dataclasses import dataclass
from typing import Any

import requests


class TicketApiError(RuntimeError):
    """调用方可以捕获的统一业务边界异常。"""


@dataclass(frozen=True)
class Ticket:
    ticket_id: str
    status: str
    summary: str


class TicketClient:
    def __init__(
        self,
        base_url: str,
        token: str,
        *,
        session: requests.Session | None = None,
    ) -> None:
        self.base_url = base_url.rstrip("/")
        self.session = session or requests.Session()
        self.session.headers.update(
            {
                "Accept": "application/json",
                "Authorization": f"Bearer {token}",
                "User-Agent": "agent-course/1.0",
            }
        )

    def get_ticket(self, ticket_id: str) -> Ticket:
        try:
            response = self.session.get(
                f"{self.base_url}/v1/tickets/{ticket_id}",
                timeout=(3.0, 20.0),  # 连接超时、读取超时
            )
        except requests.ConnectTimeout as exc:
            raise TicketApiError("连接工单服务超时") from exc
        except requests.ReadTimeout as exc:
            raise TicketApiError("工单服务未及时返回数据") from exc
        except requests.RequestException as exc:
            raise TicketApiError(f"工单服务网络错误: {type(exc).__name__}") from exc

        if response.status_code == 404:
            raise TicketApiError(f"工单不存在: {ticket_id}")
        if response.status_code in {401, 403}:
            raise TicketApiError("工单服务认证或授权失败")

        try:
            response.raise_for_status()
        except requests.HTTPError as exc:
            # 不直接拼接 response.text，避免泄露服务端敏感信息。
            raise TicketApiError(
                f"工单服务返回 HTTP {response.status_code}"
            ) from exc

        try:
            payload: Any = response.json()
        except requests.exceptions.JSONDecodeError as exc:
            raise TicketApiError("工单服务返回的内容不是合法 JSON") from exc

        if not isinstance(payload, dict):
            raise TicketApiError("工单响应应为 JSON 对象")

        required = ("id", "status", "summary")
        missing = [name for name in required if not isinstance(payload.get(name), str)]
        if missing:
            raise TicketApiError(f"工单响应缺少字符串字段: {', '.join(missing)}")

        return Ticket(
            ticket_id=payload["id"],
            status=payload["status"],
            summary=payload["summary"],
        )

四、超时不是一个数字 ​

一次请求可能在多个阶段等待：

超时等待什么常见原因
DNS/连接超时建立到目标的连接域名、网络、防火墙或服务不可达
TLS 握手超时建立安全通道网络异常或证书协商问题
写入超时把请求体发送出去大文件或对端读取太慢
读取超时等待响应数据服务处理慢或流中断
连接池超时等待可复用连接本地并发超过连接池容量
总截止时间整个操作允许多久上游请求预算或任务 SLA

requests 常用的二元组 timeout=(connect, read) 不是整个请求的总截止时间。读取超时通常约束“相邻数据到达之间最多等待多久”，服务持续缓慢发送数据时，总耗时仍可能很长。

HTTPX 可以分别配置多个阶段：

python
import httpx

timeout = httpx.Timeout(
    connect=3.0,
    read=20.0,
    write=10.0,
    pool=2.0,
)
limits = httpx.Limits(
    max_connections=20,
    max_keepalive_connections=10,
)

with httpx.Client(timeout=timeout, limits=limits) as client:
    response = client.get("https://api.example.com/health")
    response.raise_for_status()

具体 HTTP 库如何定义每类超时属于版本事实，应查看所用版本文档。稳定原则是：

  1. 每次外部调用都有有限等待时间；
  2. 连接、读取和总操作预算不要混为一谈；
  3. 下游超时应小于上游截止时间，给清理和返回错误预留时间；
  4. 超时之后要假设结果未知，而不是简单假设操作没有发生。

最后一条尤其重要：客户端读取超时，不代表服务端没有完成退款。

五、重试、退避、抖动与幂等 ​

1. 哪些失败可能重试 ​

通常可以考虑重试：连接暂时失败、408、429、部分 5xx。通常不应自动重试：字段校验失败、401、403、确定的 404。

但“状态码可重试”只是第一个条件。还必须同时判断：

  • 操作重复执行是否安全；
  • 是否还有调用截止时间；
  • 服务端是否给出 Retry-After；
  • 本次尝试是否已经把请求提交给服务端；
  • 重试是否会进一步放大服务故障。

2. 幂等意味着重复执行结果一致 ​

GET、PUT、DELETE 按 HTTP 语义应当幂等，但具体 API 是否正确实现仍需确认。POST 通常不天然幂等。例如，退款请求发送成功但响应丢失，直接重试可能退款两次。

常见解决方案是客户端生成幂等键，服务端在一段约定时间内记住该键的结果：

python
from uuid import uuid4

idempotency_key = str(uuid4())
headers = {"Idempotency-Key": idempotency_key}
payload = {"order_id": "O-100", "amount": "99.90"}

幂等键应代表一次业务意图。一次逻辑操作的所有重试必须复用同一个键；用户明确发起新操作时才生成新键。只有服务端明确支持时，这个 Header 才真正有效。

3. 指数退避和抖动 ​

固定间隔会让大量客户端同时重试。指数退避逐渐增加等待时间，抖动（jitter）再加入随机量，降低“同一时刻再次拥塞”的概率：

text
delay = min(cap, base * 2^attempt) + random_jitter
1

下面是 HTTPX 风格的同步重试边界。它只对幂等方法或带幂等键的请求开放重试，并限制最大尝试次数：

python
from __future__ import annotations

import random
import time
from datetime import datetime, timezone
from email.utils import parsedate_to_datetime
from typing import Any

import httpx


RETRYABLE_STATUS = {408, 425, 429, 500, 502, 503, 504}
IDEMPOTENT_METHODS = {"GET", "HEAD", "OPTIONS", "PUT", "DELETE"}


def retry_after_seconds(value: str | None) -> float | None:
    if not value:
        return None
    if value.isdigit():
        return float(value)
    try:
        retry_at = parsedate_to_datetime(value)
        if retry_at.tzinfo is None:
            retry_at = retry_at.replace(tzinfo=timezone.utc)
        return max(0.0, (retry_at - datetime.now(timezone.utc)).total_seconds())
    except (TypeError, ValueError, OverflowError):
        return None


def request_with_retry(
    client: httpx.Client,
    method: str,
    url: str,
    *,
    idempotency_key: str | None = None,
    max_attempts: int = 3,
    **kwargs: Any,
) -> httpx.Response:
    if max_attempts < 1:
        raise ValueError("max_attempts 必须至少为 1")

    method = method.upper()
    retry_is_safe = method in IDEMPOTENT_METHODS or idempotency_key is not None
    headers = dict(kwargs.pop("headers", {}))
    if idempotency_key:
        headers["Idempotency-Key"] = idempotency_key

    for attempt in range(max_attempts):
        try:
            response = client.request(method, url, headers=headers, **kwargs)
        except (
            httpx.ConnectError,
            httpx.ConnectTimeout,
            httpx.ReadTimeout,
            httpx.WriteError,
            httpx.PoolTimeout,
        ):
            if not retry_is_safe or attempt == max_attempts - 1:
                raise
        else:
            if response.status_code not in RETRYABLE_STATUS:
                response.raise_for_status()
                return response
            if not retry_is_safe or attempt == max_attempts - 1:
                response.raise_for_status()

            server_delay = retry_after_seconds(response.headers.get("Retry-After"))
            if server_delay is not None:
                # 等待时间超出本客户端预算时直接失败，不能提前重试违背服务端提示。
                if server_delay > 30.0:
                    response.raise_for_status()
                time.sleep(server_delay)
                continue

        backoff = min(8.0, 0.5 * (2**attempt))
        jitter = random.uniform(0.0, 0.25)
        time.sleep(backoff + jitter)

    raise AssertionError("循环应当已经返回或抛出异常")

生产实现还要把总截止时间纳入判断。成熟的重试库也能减少重复代码，但不能替你决定业务是否幂等。

4. 重试会放大流量 ​

如果一条用户请求经过三层服务，每层最多尝试三次，最坏情况可能把一个请求放大到数十次下游调用。通常在最了解操作语义的一层重试，并配合：

  • 最大尝试次数与总时间预算；
  • 熔断或降级；
  • 并发限制；
  • 随机抖动；
  • 可观测的尝试次数和最终原因。

六、同步、异步、协程与事件循环 ​

1. 异步适合等待密集型工作 ​

同步函数等待网络响应时，当前线程通常无法继续处理其他任务。异步函数在 await 网络 I/O 时把控制权交还事件循环，事件循环可以推进其他就绪协程。

text
同步：请求 A ----等待 A----------------完成 A -> 请求 B ----等待 B----完成 B

异步：请求 A ----等待 A----------------完成 A
      请求 B ------等待 B------完成 B
      请求 C --等待 C------------------完成 C

4

异步提升的是 I/O 等待期间的利用率，不会自动加速 CPU 密集型计算。协程也不是线程；它在遇到 await 时协作式让出执行权。

核心术语：

  • async def 定义协程函数；
  • 调用协程函数得到协程对象，不会立刻执行完；
  • await 等待另一个异步操作并让出控制权；
  • Task 把协程安排到事件循环运行；
  • 事件循环调度就绪任务并监听 I/O；
  • asyncio.run() 通常是同步程序进入异步世界的顶层入口。

2. 不受控并发会制造新的故障 ​

一次创建一万个请求可能耗尽本机文件描述符、连接池和下游限额。Semaphore 限制正在执行的操作数，HTTP 客户端的连接池再限制连接资源：

python
from __future__ import annotations

import asyncio
from typing import TypedDict

import httpx


class FetchResult(TypedDict):
    ticket_id: str
    ok: bool
    data: dict[str, object] | None
    error: str | None


async def fetch_one(
    client: httpx.AsyncClient,
    semaphore: asyncio.Semaphore,
    ticket_id: str,
) -> FetchResult:
    async with semaphore:
        try:
            response = await client.get(f"/v1/tickets/{ticket_id}")
            response.raise_for_status()
            payload = response.json()
            if not isinstance(payload, dict):
                raise ValueError("响应不是 JSON 对象")
            return {"ticket_id": ticket_id, "ok": True, "data": payload, "error": None}
        except (httpx.TimeoutException, httpx.NetworkError, httpx.HTTPStatusError, ValueError) as exc:
            return {
                "ticket_id": ticket_id,
                "ok": False,
                "data": None,
                "error": type(exc).__name__,
            }


async def fetch_many(ticket_ids: list[str]) -> list[FetchResult]:
    semaphore = asyncio.Semaphore(10)
    timeout = httpx.Timeout(connect=3.0, read=15.0, write=10.0, pool=2.0)
    limits = httpx.Limits(max_connections=10, max_keepalive_connections=10)

    async with httpx.AsyncClient(
        base_url="https://api.example.com",
        timeout=timeout,
        limits=limits,
    ) as client:
        tasks = [
            asyncio.create_task(fetch_one(client, semaphore, ticket_id))
            for ticket_id in ticket_ids
        ]
        # Python 3.11+ 的总截止时间；超时会取消仍在等待的任务。
        async with asyncio.timeout(30.0):
            return await asyncio.gather(*tasks)


results = asyncio.run(fetch_many(["T-1", "T-2", "T-3"]))

3. 取消也是正常控制流 ​

2. 事务保证一组数据库操作的边界 ​

事务的四个经典性质是 ACID：原子性、一致性、隔离性、持久性。应用开发最先要掌握的是：一组必须同时成功的写操作，要么提交，要么回滚。

下面采用 psycopg 3 风格，并把连接池作为依赖传入：

python
from __future__ import annotations

from uuid import UUID

from psycopg.types.json import Jsonb
from psycopg_pool import ConnectionPool


def complete_run(
    pool: ConnectionPool,
    run_id: UUID,
    output: dict[str, object],
    assistant_message: dict[str, object],
) -> None:
    with pool.connection() as connection:
        with connection.transaction():
            updated = connection.execute(
                """
                UPDATE agent_runs
                SET status = 'succeeded', output = %s, updated_at = now()
                WHERE id = %s AND status = 'running'
                """,
                (Jsonb(output), run_id),
            ).rowcount
            if updated != 1:
                raise ValueError("运行不存在或状态已变化")

            connection.execute(
                """
                INSERT INTO agent_messages (run_id, sequence_no, role, content)
                SELECT %s, COALESCE(MAX(sequence_no), 0) + 1, 'assistant', %s
                FROM agent_messages
                WHERE run_id = %s
                """,
                (run_id, Jsonb(assistant_message), run_id),
            )

九、PostgreSQL 与 Redis 的职责边界 ​

两者不是互相替代的“快数据库”和“慢数据库”。

需求PostgreSQLRedis
订单、权限、Agent 运行等事实首选，支持约束和事务不应默认作为唯一事实来源
多表关系与复杂查询擅长不擅长
短期缓存可以但通常不是首选擅长，原生 TTL

1. Cache-Aside 模式 ​

读取时先查 Redis，未命中再查 PostgreSQL并写回缓存：

python
from __future__ import annotations

import json
from typing import Any

from redis.exceptions import RedisError


def get_user_profile(pg_pool: Any, redis_client: Any, user_id: str) -> dict[str, object] | None:
    key = f"user-profile:{user_id}"
    try:
        cached = redis_client.get(key)
    except RedisError:
        # 缓存故障只影响性能，不能阻止读取权威数据源。
        cached = None
    if cached is not None:
        try:
            payload = json.loads(cached)
        except (json.JSONDecodeError, TypeError, UnicodeDecodeError):
            payload = None
        if isinstance(payload, dict):
            return payload

    with pg_pool.connection() as connection:
        row = connection.execute(
            "SELECT display_name, plan FROM users WHERE id = %s",
            (user_id,),
        ).fetchone()

    if row is None:
        return None

    profile = {"display_name": row[0], "plan": row[1]}
    try:
        redis_client.set(key, json.dumps(profile), ex=300)
    except RedisError:
        # 实际项目还应记录一次不含敏感数据的降级日志。
        pass
    return profile

  • 序列化格式升级后如何兼容旧缓存。

2. 过期与淘汰不是一回事 ​

TTL 表示 Key 到期后不应再被当作有效值。淘汰是 Redis 在内存压力下根据策略提前移除 Key。应用必须把缓存未命中当作正常情况，而不是数据丢失事故。

3. Redis 协调有租约语义 ​

SET key value NX EX seconds 常用于“仅当不存在时写入，并设置过期”。它可以构造简单租约，但不是万能分布式锁：任务可能在租约过期后仍继续运行，另一个 Worker 又获得租约。关键副作用仍需数据库约束、幂等键或 fencing token 防止旧持有者写入。

4. 一个实用判断 ​

问自己：“Redis 现在全部清空，系统能否从 PostgreSQL 或其他权威来源恢复？”

  • 如果能，只是暂时变慢，Redis 很可能承担缓存或协调职责；
  • 如果不能，而且丢失的是业务事实，就需要重新审视持久化设计；
  • 如果明确选择 Redis 持久化为事实源，则必须单独设计持久化、复制、故障转移和一致性，不能沿用“只是缓存”的假设。

十、把失败路径当作一等公民 ​

一个外部 API 调用至少应覆盖下列测试：

场景期望行为
200 + 合法 JSON返回已校验对象
200 + 非 JSON报“响应格式错误”，不伪装成空结果
200 + 缺字段报 Schema/数据错误
连接超时分类为连接问题，并受重试预算约束
读取超时结果视为未知，副作用操作先查幂等状态
401/403不盲目重试，触发凭证或权限处理
429 + Retry-After在总预算内等待并重试
503退避且限制尝试次数
并发任务部分失败按业务选择部分结果或整体失败
PostgreSQL 写入第二步失败整个事务回滚
Redis 不可用核心事实仍可从 PostgreSQL 读取

还应记录但不要泄密：请求 ID、目标服务、操作名、尝试次数、状态码、延迟、超时类别和最终结果。不要记录 Authorization Header、完整用户输入或未经审查的响应体。

十一、综合练习：可靠的工单 API 客户端 ​

任务 ​

实现一个小型 Python 项目，输入一组工单 ID，调用一个本地 Mock API，最后把结果写入 PostgreSQL；Redis 只缓存成功查询的工单。

要求：

  1. 从环境变量读取 API 地址、Token、PostgreSQL DSN 和 Redis 地址；
  2. 使用 URL 参数 API，不手工拼查询字符串；
  3. 显式配置连接、读取、连接池和总截止时间；
  4. 最多并发 5 个请求；
  5. 只对安全操作重试，采用指数退避和抖动；
  6. 对 429 读取 Retry-After；
  7. 将网络、HTTP、JSON 和业务校验错误分开；
  8. PostgreSQL 保存每次查询事实，Redis 缓存可重建结果并设置 TTL；
  9. 程序退出或取消时关闭 HTTP、数据库和 Redis 资源；
  10. 使用测试替身模拟失败，不依赖真实公网服务完成测试。

必做测试 ​

  • 正常返回一张工单；
  • URL 参数含空格、& 和中文；
  • API Token 缺失时在发请求前失败；
  • 连接超时后按预算重试；
  • 非幂等创建操作在没有幂等键时不重试；
  • 429 后遵守服务端等待提示；
  • 返回 HTML 或错误 JSON 时给出明确错误；
  • 20 个任务同时输入时，实际并发不超过 5；
  • 写入两张相关表时第二条 SQL 失败，第一条也回滚；
  • Redis 清空或暂时不可用时，PostgreSQL 中的事实不丢失。

验收标准 ​

你需要能现场解释并演示：

  • 为什么 timeout=20 不一定代表总耗时最多 20 秒；
  • 为什么读取超时后的退款结果是“未知”而非“失败”；
  • 幂等键为什么必须在同一次逻辑操作的重试间复用；
  • Semaphore 与 HTTP 连接池分别限制什么；
  • 为什么网络调用不应放在长事务中；
  • 一个索引对应哪条真实查询，并能用执行计划验证；
  • Redis 全部清空后，系统如何恢复。

只让正常路径跑通不算完成。超时、错误 JSON、部分失败、事务回滚和缓存失效都可预测，才达到进入模型 API 与 Agent 工具开发的门槛。

本章小结 ​

可靠 Agent 的底层不是“多调几个 API”，而是明确每一层边界：HTTP 负责消息交换，认证限制身份与权限，超时限制等待，重试只在幂等与预算内发生，异步并发必须受控，PostgreSQL 保存有约束的事实，Redis 承担可失效的缓存或谨慎设计的协调职责。
