大数据量列表、表格与计算优化 ​

“数据量大”可能意味着请求体积大、数组计算慢、DOM 太多、更新频率高，或者内存无法回收。它们发生在不同阶段，不能用同一个“虚拟列表”统一解决。

前端大数据优化可以沿着一条数据链路理解：

text
获取与传输
  -> 数据解析与处理
  -> 状态保存与更新
  -> VNode / DOM / Canvas 渲染
  -> 缓存与资源释放

优化的基本原则是：少获取、少传输、少代理、少计算、少更新、少渲染，并用相同数据和设备验证结果。

问题场景与性能定位 ​

先判断慢在哪一段 ​

现象优先检查常见原因
页面打开前等待很久Network请求过多、响应体积大
数据赋值时停顿Performance / Vue DevToolsJSON 解析、深层响应式转换
输入后页面卡住Performance全量过滤、排序、聚合
首次渲染或滚动卡顿Elements / PerformanceVNode、DOM、布局和绘制过多
使用越久内存越高Memory缓存无上限、监听器或引用未释放
实时消息逐渐延迟自定义队列指标更新速度超过处理和渲染速度

先记录优化前基线：请求体积、长任务、DOM 数量、一次交互耗时和堆内存。后续每次只改变一个主要因素，再使用相同数据重新测量。

一、数据获取与传输优化 ​

1. 分页、游标与增量加载 ​

适用场景： 数据来自远端，用户一次只查看其中一部分。

核心原理： 浏览器没有获取的数据不需要解析、保存和渲染。接口只向前端返回当前窗口：

ts
type PageResult<T> = {
  items: T[]
  nextCursor: string | null
}

前端将 Cursor 视为不透明字符串，切换筛选和排序后丢弃旧 Cursor：

async function loadPage(
  keyword: string,
  cursor: string | null,
  signal: AbortSignal
) {
  const params = new URLSearchParams({ keyword, limit: '100' })
  if (cursor) params.set('cursor', cursor)

  const response = await fetch(`/api/rows?${params}`, { signal })
  if (!response.ok) throw new Error(`request failed: ${response.status}`)

  return response.json() as Promise<PageResult<Row>>
}

代价： 需要处理加载状态、下一页失败、滚动恢复和数据变化时的分页一致性。

2. 请求取消、去重与竞态控制 ​

适用场景： 搜索、筛选和滚动会快速产生多个请求。

核心原理： 取消不再需要的工作，同一个请求只执行一次，并阻止旧结果覆盖新结果。

不同查询使用 AbortController 和版本号：

ts
let controller: AbortController | undefined
let requestVersion = 0

async function search(keyword: string) {
  const version = ++requestVersion

  controller?.abort()
  controller = new AbortController()

  try {
    const page = await loadPage(keyword, null, controller.signal)

    if (version !== requestVersion) return
    commitPage(page)
  } catch (error) {
    if (error instanceof DOMException && error.name === 'AbortError') return
    throw error
  }
}

完全相同且生命周期一致的请求，可以共享同一个 Promise：

const inFlight = new Map<string, Promise<PageResult<Row>>>()

function requestOnce(key: string, task: () => Promise<PageResult<Row>>) {
  const existing = inFlight.get(key)
  if (existing) return existing

  const promise = task().finally(() => inFlight.delete(key))
  inFlight.set(key, promise)
  return promise
}

共享请求不能由其中一个调用方随意取消；需要独立取消时，应使用独立请求或实现引用计数。

防抖只减少触发次数，不能代替取消和竞态保护。并发加载多个独立分片时还需要设置上限，避免带宽和解析任务互相争抢。

验证方式： 快速输入多个关键词，只有最后一个结果进入页面；相同查询不会产生重复 Network 请求；旧请求显示为 cancelled。

代价： 请求键必须包含所有影响结果的条件，错误的请求键会复用不相同的数据。

3. 字段、格式与传输体积 ​

适用场景： Network 显示响应体积、下载或 JSON 解析是主要瓶颈。

优化方式：

  • 列表接口只返回当前视图需要的字段，详情按需获取。
  • 避免同一响应重复包含可以通过 ID 关联的大对象。
  • 大量数值或二进制数据评估 TypedArray、ArrayBuffer 或流式格式。
  • 使用 HTTP 缓存和条件请求避免重复下载未变化数据。
  • 在 DevTools 中区分资源原始大小和实际传输大小。
ts
type RowListItem = Pick<Row, 'id' | 'name' | 'status' | 'amount' | 'version'>
1

压缩通常由服务器或 CDN 完成，前端关注是否正确协商、传输体积是否下降，以及解压和解析是否仍满足预算，不在本文展开压缩配置。

验证方式： 对比字段裁剪前后的 transferred size、JSON 解析耗时和堆内存。

代价： 过度裁剪可能造成列表逐行补请求。应根据视图用例设计稳定的列表模型，而不是每次临时删字段。

4. 有条件地预取 ​

适用场景： 用户大概率继续滚动或打开下一屏，并且网络与内存预算允许。

可以在接近列表底部时预取下一页：

ts
function shouldPrefetch(
  scrollTop: number,
  viewportHeight: number,
  contentHeight: number,
  threshold = 600

  return scrollTop + viewportHeight >= contentHeight - threshold

二、数据处理优化 ​

1. 去重、规范化与身份索引 ​

适用场景： 分页结果可能重复、实时事件按 ID 更新，或代码频繁查找单条数据。

核心原理： 用稳定 ID 表达数据身份，使用 Map 将重复线性查找变成直接索引。

ts
function mergeRows(current: Row[], incoming: Row[]) {
  const byId = new Map(current.map((row) => [row.id, row]))

  for (const row of incoming) {
    const previous = byId.get(row.id)

    if (!previous || row.version >= previous.version) {
      byId.set(row.id, row)
    }
  }

  return [...byId.values()]
}

代价： Map 本身占用内存；数据量很小、只遍历一次时不必额外建立索引。

2. 减少重复筛选、排序和聚合 ​

适用场景： 相同输入反复执行同一计算，或者每个按键都触发全量扫描。

computed 可以缓存依赖未变化的结果，但关键词变化后仍会重新扫描。可以将输入值和实际应用的查询分开：

const draftKeyword = ref('')
const appliedKeyword = ref('')

const filteredRows = computed(() => {
  const keyword = appliedKeyword.value.trim()
  if (!keyword) return rows.value

  return rows.value.filter((row) => row.name.includes(keyword))
})

function applyFilter() {
  appliedKeyword.value = draftKeyword.value
}

// filter.worker.ts
import type { FilterResult, WorkerRow } from './filter.types'

let rows: WorkerRow[] = []

self.onmessage = (event) => {
  const message = event.data

  if (message.type === 'init') {
    rows = message.rows
    return
  }

  if (message.type === 'filter') {
    const result: WorkerRow[] = []
    let total = 0

    for (const row of rows) {
      if (!row.name.includes(message.keyword)) continue

      total += 1
      if (result.length < message.limit) result.push(row)
    }

    self.postMessage({
      type: 'result',
      requestId: message.requestId,
      result: { total, rows: result } satisfies FilterResult
    })
  }
}

主线程创建 Worker，并把每次结果转换为 Promise：

ts
import type { FilterResult, WorkerRow } from './filter.types'

const worker = new Worker(
  new URL('./filter.worker.ts', import.meta.url),
  { type: 'module' }
)

let currentRequestId = 0
const pending = new Map<number, (result: FilterResult) => void>()

worker.postMessage({ type: 'init', rows: rows as WorkerRow[] })

function filterInWorker(keyword: string, limit = 100) {
  return new Promise<FilterResult>((resolve) => {
    const requestId = ++currentRequestId
    pending.set(requestId, resolve)

    worker.postMessage({
      type: 'filter',
      requestId,
      keyword,
      limit
    })
  })
}

worker.onmessage = (event) => {
  const resolve = pending.get(event.data.requestId)
  if (!resolve) return

  pending.delete(event.data.requestId)
  resolve(event.data.result)
}

const result = await filterInWorker('订单 10')
console.log(result.total, result.rows)

4. Time Slicing：时间切片 ​

适用场景： 任务可以分批执行，但放入 Worker 的通信成本过高，或每批需要访问主线程状态。

核心原理： 每执行一小段工作就让出主线程，使输入和渲染获得执行机会。

ts
function yieldToMain() {
  return new Promise<void>((resolve) => setTimeout(resolve, 0))
}

async function filterInSlices<T>(
  source: T[],
  predicate: (item: T) => boolean,
  signal: AbortSignal,
  budget = 8
) {
  const result: T[] = []
  let sliceStart = performance.now()

  for (const item of source) {
    if (signal.aborted) throw new DOMException('Aborted', 'AbortError')
    if (predicate(item)) result.push(item)

    if (performance.now() - sliceStart >= budget) {
      await yieldToMain()
      sliceStart = performance.now()
    }
  }

  return result
}

三、数据渲染优化 ​

1. 虚拟列表 ​

适用场景： 数据已经在内存中，但同时创建大量 VNode 和 DOM 导致渲染、布局或内存问题。

固定行高时，可见区间可以直接计算：

ts
function calculateWindow(
  scrollTop: number,
  viewportHeight: number,
  total: number,
  rowHeight: number,
  overscan = 5
) {
  const firstVisible = Math.floor(scrollTop / rowHeight)
  const visibleCount = Math.ceil(viewportHeight / rowHeight)
  const start = Math.max(0, firstVisible - overscan)
  const end = Math.min(total, start + visibleCount + overscan * 2)

  return {
    start,
    end,
    offsetY: start * rowHeight,
    totalHeight: total * rowHeight
  }
}

2. 分片渲染 ​

适用场景： 最终确实需要生成完整 DOM，但可以逐批出现，例如只读卡片、树节点或打印准备。

ts
async function renderInChunks(
  rows: Row[],
  container: HTMLElement,
  signal: AbortSignal,
  chunkSize = 200
) {
  for (let start = 0; start < rows.length; start += chunkSize) {
    if (signal.aborted) return

    const fragment = document.createDocumentFragment()

    for (const row of rows.slice(start, start + chunkSize)) {
      const element = document.createElement('div')
      element.textContent = row.name
      fragment.append(element)
    }

    container.append(fragment)
    await new Promise<void>((resolve) => requestAnimationFrame(() => resolve()))
  }
}

3. Vue 组件与单元格更新 ​

适用场景： DOM 数量已经受控，但复杂单元格和组件更新仍然耗时。

  • 大列表快照使用 shallowRef()，避免无意义的深层代理。
  • 使用稳定业务 ID 作为 key，不能使用数组索引。
  • 格式化器在组件外复用，不在每个单元格中重复创建。
  • 将高频编辑状态与只读列表快照分离。
  • 对输入稳定、渲染昂贵的行谨慎使用 v-memo。

4. 高频数据批量提交 ​

适用场景： 实时事件产生速度高于界面需要的刷新频率。

ts
const pending = new Map<number, Row>()
let scheduled = false

function receiveRow(row: Row) {
  pending.set(row.id, row)

  if (scheduled) return
  scheduled = true

  requestAnimationFrame(() => {
    scheduled = false
    const updates = new Map(pending)
    pending.clear()

    rows.value = rows.value.map((current) =>
      updates.get(current.id) ?? current
    )
  })
}

四、缓存、存储与资源生命周期 ​

1. 前端查询缓存 ​

缓存键必须包含查询条件和数据版本，并设置容量与失效策略：

ts
const pageCache = new Map<string, PageResult<Row>>()
const MAX_PAGES = 10

function cachePage(key: string, page: PageResult<Row>) {
  pageCache.delete(key)
  pageCache.set(key, page)

  if (pageCache.size > MAX_PAGES) {
    const oldestKey = pageCache.keys().next().value
    if (oldestKey) pageCache.delete(oldestKey)
  }
}

2. IndexedDB 与本地大数据 ​

本地文件、离线数据或需要跨刷新保存的大集合可以使用 IndexedDB。它适合异步存储结构化数据，不适合直接把十万条记录放进 localStorage。

使用时必须定义：

  • Schema 版本和迁移方式。
  • 用户与租户隔离。
  • 存储容量和淘汰规则。
  • 数据过期与重新验证。
  • 写入失败和配额不足的处理。

普通远端列表不应为了“优化”默认持久化全部数据。

3. 预加载与预缓存边界 ​

预加载只有在命中概率高、资源可复用且不会挤占当前任务时才有价值。记录预取命中率、取消率和额外流量；命中率低时应减少或关闭。

4. 资源释放 ​

组件卸载或查询切换时清理长期资源：

ts
onBeforeUnmount(() => {
  controller?.abort()
  worker.terminate()
  window.removeEventListener('resize', handleResize)

  if (objectUrl) URL.revokeObjectURL(objectUrl)
})

五、可视化大数据专项 ​

Canvas、WebGL 和 WebGPU 不是普通业务表格的默认优化方式，只在数据主要表现为图形时考虑。

渲染方式适合场景主要代价
DOM表格、表单、文本和语义交互元素数量大时布局成本高
Canvas 2D大量二维点位、轨迹、简单图形需要自定义拾取和无障碍替代
WebGL/WebGPU点云、三维和 GPU 批量绘制学习、调试、兼容与资源管理成本高

选择前确认是否需要 DOM 语义、逐项焦点、文本选择和原生表单。具体实现进入可视化与图形专题，不在本文重复。

七、不同数据规模的方案选择 ​

数据条数只是参考，单元格复杂度、更新频率和设备条件同样重要。

场景优先方案
几千条简单数据保持普通列表，先测量再优化
一万条左右远端数据分页、请求控制，必要时虚拟化
十万条本地数据浅层状态、索引、Worker 或时间切片、虚拟列表
复杂可编辑表格稳定 ID、局部编辑状态、行列虚拟化
高频实时数据按 ID 合并、批量提交、积压监控
无法虚拟化的复杂内容分片渲染和时间切片
大量图形点位进入 Canvas/WebGL 可视化专项
