前端缓存、离线与数据同步 ​

“加一层缓存”和“支持离线编辑”是两种复杂度完全不同的需求。前者主要减少重复请求，后者必须回答：页面断网后从哪里读取，用户修改保存在哪里，恢复网络后按什么顺序提交，以及服务器和本地都修改过同一字段时谁来决定结果。

本文使用一个 Vue 3 现场巡检应用贯穿方案。巡检人员可以离线查看最近同步的工单、填写结果、温度和备注；恢复网络后，客户端把修改同步到服务器。服务器仍是真实来源，审批、权限变更和大附件上传不进入离线队列。

方案包含三条相互配合但职责不同的链路：

text
应用壳：Service Worker -> HTML / JS / CSS 可离线加载
读取链路：服务器快照 -> IndexedDB -> UI 立即读取 -> 增量刷新
写入链路：本地变更 -> Outbox -> 幂等同步 -> 版本冲突处理

存储 API 的基础用法见Web Storage、IndexedDB、Cache API 与 Cookie，Service Worker 生命周期见Worker、Service Worker 与消息通信，服务端状态概念见服务端状态、缓存与一致性。

问题场景与常见错误 ​

一个看似简单的实现可能把接口响应写入 localStorage，断网时直接重放请求：

ts
async function loadOrders() {
  if (navigator.onLine) {
    const response = await fetch('/api/work-orders')
    const orders = await response.json()
    localStorage.setItem('orders', JSON.stringify(orders))
    return orders
  }

  return JSON.parse(localStorage.getItem('orders') ?? '[]')
}

window.addEventListener('online', () => {
  const pending = JSON.parse(localStorage.getItem('pending') ?? '[]')
  pending.forEach((body: unknown) => {
    void fetch('/api/work-orders', {
      method: 'POST',
      body: JSON.stringify(body)
    })
  })
})

这段代码没有建立可恢复的数据协议：

问题后果
navigator.onLine 被当作网络真相连上局域网但接口不可达时仍会发起同步
大量结构化数据放在 localStorage同步读写阻塞主线程，也没有事务和索引

成功前就删除本地修改响应丢失时既无法确认结果，也无法安全重试
所有错误都继续重试401、403、校验错误和冲突形成无限循环
Service Worker 缓存所有 GET敏感接口、旧权限和用户数据可能被错误复用

案例约束 ​

离线能力先写成产品契约：

项目案例决定
离线范围最近 7 天、最多 500 个已分配工单
最长预期离线时间8 小时，超过后可读取陈旧快照，但停止新增离线修改
可离线修改巡检结果、温度和备注
必须在线审批、关闭工单、修改权限、大附件上传
冲突要求不允许客户端时间戳静默覆盖；相同字段并发修改需确认
数据恢复App 重新打开后仍能看到未同步修改
浏览器范围当前两个主要版本的 Chrome、Edge 和 Safari
安全边界每次同步重新认证授权，登出清理账号数据

离线不等于永远可用。首次访问仍需要在线下载应用壳和账号数据，浏览器也可能在存储压力下清理站点数据。界面必须展示最后同步时间、待同步数量和冲突，而不是只放一个绿色“离线可用”图标。

一、先确定数据所有权和离线边界 ​

案例是 Server-first 应用，不是完整的 Local-first 系统：

text
服务器快照：工单身份、权限、版本和最终状态
本地快照：最近一次成功同步的服务器数据
Outbox：尚未被服务器确认的用户意图
派生视图：本地快照按顺序叠加 Outbox 后的界面结果
1
2
3
4

把服务器快照和本地修改分开保存很重要。如果每次离线编辑都直接覆盖缓存快照，稍后收到服务器新版本时就无法还原“编辑前是什么、用户改了什么、远端又改了什么”。

操作离线行为恢复在线后的行为
查看已分配工单读取本地快照，显示最后同步时间拉取增量变化
修改巡检字段写入 Outbox，立即形成乐观视图按实体顺序提交
最终审批和关闭禁用并说明需要在线重新取权限和最新版本后执行
上传大附件保存本地填写内容，不进入普通 Outbox交给大文件上传方案
工单已被远端删除保留本地修改并标记冲突由用户放弃或复制为新记录

本地可见不代表服务端已接受。页面应使用“待同步”“同步中”“冲突”描述状态，不能在离线点击后直接显示“已提交成功”。

二、区分四层缓存 ​

层次保存什么失效依据不应保存什么
HTTP Cache带哈希静态资源、允许验证的响应Cache-Control、ETag、URL 版本需要应用查询和事务的数据
Cache StorageApp Shell 和明确选择的静态资源Service Worker 版本和容量策略默认不放带身份的业务 API
IndexedDB工单快照、Outbox、同步游标业务版本、保留期和账号边界Token、无限历史数据
内存查询缓存当前页面查询和派生结果页面会话、查询键和容量跨刷新恢复的唯一副本

带内容哈希的 JS/CSS 可以长期缓存；HTML 通常需要重新验证，以便发现新版本。工单 API 即使使用 HTTP ETag，也仍需要 IndexedDB 承担离线查询和事务。不要同时让 Cache Storage 与 IndexedDB 各自保存同一份鉴权 API 响应，否则更新和登出时会出现两个真实来源。

Cache-Control: no-store 约束普通 HTTP Cache，但不能阻止自定义 Service Worker 主动把响应写入 Cache API。Service Worker 路由必须显式排除 /api/ 和其他敏感路径。

三、让应用壳可离线加载 ​

Service Worker 只保证应用代码可以启动，不处理工单版本和业务冲突。案例使用构建时生成的 Precache Manifest，避免手工维护每次都会变化的资源哈希：

ts
/// <reference lib="webworker" />
// src/sw.ts
import { clientsClaim } from 'workbox-core'
import { ExpirationPlugin } from 'workbox-expiration'
import {
  cleanupOutdatedCaches,
  createHandlerBoundToURL,
  precacheAndRoute
} from 'workbox-precaching'
import { NavigationRoute, registerRoute } from 'workbox-routing'
import { CacheFirst } from 'workbox-strategies'

declare let self: ServiceWorkerGlobalScope & {
  __WB_MANIFEST: Array<{ url: string; revision?: string }>
}

precacheAndRoute(self.__WB_MANIFEST)
cleanupOutdatedCaches()
clientsClaim()

const appShell = createHandlerBoundToURL('/inspection/index.html')
registerRoute(new NavigationRoute(appShell, {
  allowlist: [/^\/inspection(?:\/|$)/]
}))

registerRoute(
  ({ request, url }) =>
    url.origin === self.location.origin
    && url.pathname.startsWith('/inspection/assets/')
    && ['font', 'image', 'script', 'style'].includes(request.destination),
  new CacheFirst({
    cacheName: 'inspection-assets-v1',
    plugins: [new ExpirationPlugin({
      maxEntries: 80,
      maxAgeSeconds: 30 * 24 * 60 * 60
    })]
  })
)

self.addEventListener('message', (event) => {
  if (event.data?.type === 'ACTIVATE_UPDATE') {
    void self.skipWaiting()
  }
})

四、用 IndexedDB 保存快照与 Outbox ​

示例使用 idb 作为 IndexedDB 的 Promise 和类型封装，不改变底层事务语义。数据库按服务端下发的非敏感账号作用域隔离，避免两个账号复用同一批工单。

1. 数据模型 ​

ts
// offline-db.ts
import { openDB, type DBSchema, type IDBPDatabase } from 'idb'

export type EditableFields = {
  result: 'pending' | 'pass' | 'fail'
  temperature: number | null
  note: string
}

export type RemoteWorkOrder = EditableFields & {
  id: string
  title: string
  version: number
  updatedAt: string
}

export type WorkOrderSnapshot = RemoteWorkOrder & {
  lastSyncedAt: number
}

export type WorkOrderPatch = Partial<EditableFields>

export type PendingMutation = {
  id?: number
  entityId: string
  patch: WorkOrderPatch
  baseValues: WorkOrderPatch
  baseVersion: number
  idempotencyKey: string
  createdAt: number
  state: 'pending' | 'conflict' | 'rejected'
  conflictFields?: Array<keyof EditableFields | 'entity'>
  message?: string
}

interface InspectionDB extends DBSchema {
  workOrders: {
    key: string
    value: WorkOrderSnapshot
  }
  mutations: {
    key: number
    value: PendingMutation
    indexes: {
      'by-entity-order': [string, number]
    }
  }
  meta: {
    key: string
    value: { key: string; value: string | null }
  }
}

export type InspectionDatabase = IDBPDatabase<InspectionDB>

export function openInspectionDb(
  accountScope: string
): Promise<InspectionDatabase> {
  if (!/^[a-zA-Z0-9_-]{8,80}$/.test(accountScope)) {
    throw new Error('invalid account scope')
  }

  return openDB<InspectionDB>(`inspection:${accountScope}`, 1, {
    upgrade(db) {
      db.createObjectStore('workOrders', { keyPath: 'id' })
      const mutations = db.createObjectStore('mutations', {
        keyPath: 'id',
        autoIncrement: true
      })
      mutations.createIndex(
        'by-entity-order',
        ['entityId', 'id']
      )
      db.createObjectStore('meta', { keyPath: 'key' })
    }
  })
}

workOrders 只保存服务器确认的快照，mutations 保存尚未确认的用户意图。界面数据由两者派生，因此远端刷新不会直接抹掉本地修改。

2. 本地编辑和 Outbox 必须同一事务 ​

ts
function applyPatch(
  order: WorkOrderSnapshot,
  patch: WorkOrderPatch
): WorkOrderSnapshot {
  return { ...order, ...patch }
}

function pickBaseValues(
  order: EditableFields,
  patch: WorkOrderPatch
): WorkOrderPatch {
  return {
    ...('result' in patch ? { result: order.result } : {}),
    ...('temperature' in patch ? { temperature: order.temperature } : {}),
    ...('note' in patch ? { note: order.note } : {})
  }
}

function removeUnchangedValues(
  order: EditableFields,
  patch: WorkOrderPatch
): WorkOrderPatch {
  return {
    ...('result' in patch
      && patch.result !== undefined
      && patch.result !== order.result
      ? { result: patch.result }
      : {}),
    ...('temperature' in patch
      && patch.temperature !== undefined
      && !Object.is(patch.temperature, order.temperature)
      ? { temperature: patch.temperature }
      : {}),
    ...('note' in patch
      && patch.note !== undefined
      && patch.note !== order.note
      ? { note: patch.note }
      : {})
  }
}

function entityMutationRange(entityId: string): IDBKeyRange {
  const range = IDBKeyRange.bound(
    [entityId, 0],
    [entityId, Number.MAX_SAFE_INTEGER]
  )
  return range
}

export async function loadOptimisticOrder(
  db: InspectionDatabase,
  entityId: string
): Promise<WorkOrderSnapshot | null> {
  const tx = db.transaction(['workOrders', 'mutations'], 'readonly')
  const snapshot = await tx.objectStore('workOrders').get(entityId)
  if (!snapshot) {
    await tx.done
    return null
  }

  const queued = await tx.objectStore('mutations')
    .index('by-entity-order')
    .getAll(entityMutationRange(entityId))
  await tx.done
  return queued.reduce(
    (current, mutation) => applyPatch(current, mutation.patch),
    snapshot
  )
}

export async function enqueueOfflineEdit(
  db: InspectionDatabase,
  entityId: string,
  patch: WorkOrderPatch
): Promise<WorkOrderSnapshot> {
  const tx = db.transaction(['workOrders', 'mutations'], 'readwrite')
  const snapshots = tx.objectStore('workOrders')
  const mutations = tx.objectStore('mutations')
  const currentSnapshot = await snapshots.get(entityId)
  if (!currentSnapshot) {
    await tx.done
    throw new Error('work order is not cached')
  }

  const queued = await mutations
    .index('by-entity-order')
    .getAll(entityMutationRange(entityId))
  const current = queued.reduce(
    (order, mutation) => applyPatch(order, mutation.patch),
    currentSnapshot
  )
  const effectivePatch = removeUnchangedValues(current, patch)
  if (Object.keys(effectivePatch).length === 0) {
    await tx.done
    return current
  }

  await mutations.add({
    entityId,
    patch: effectivePatch,
    baseValues: pickBaseValues(current, effectivePatch),
    baseVersion: currentSnapshot.version,
    idempotencyKey: crypto.randomUUID(),
    createdAt: Date.now(),
    state: 'pending'
  })
  await tx.done

  return applyPatch(current, effectivePatch)
}

五、读取本地快照并增量刷新 ​

页面启动时先读 IndexedDB，不等待网络决定是否渲染。随后始终尝试接口请求，成功就刷新，失败才进入离线或故障状态：

text
读取本地快照
  -> 有数据：立即展示并标记最后同步时间
  -> 无数据：展示首次加载状态
  -> 请求增量变化
      -> 成功：事务写入快照、删除墓碑、推进 Cursor
      -> 网络失败：保留本地数据并进入离线可用
      -> 401：进入重新登录，不把它伪装成离线

六、按顺序同步 Outbox ​

1. Mutation 请求必须幂等并带基础版本 ​

ts
class SyncHttpError extends Error {
  constructor(
    public readonly status: number,
    message: string,
    public readonly remote?: RemoteWorkOrder
  ) {
    super(message)
  }
}

async function pushMutation(
  base: WorkOrderSnapshot,
  mutation: PendingMutation,
  signal: AbortSignal
): Promise<RemoteWorkOrder> {
  const response = await fetch(
    `/api/work-orders/${encodeURIComponent(base.id)}`,
    {
      method: 'PATCH',
      credentials: 'include',
      signal,
      headers: {
        'content-type': 'application/json',
        'Idempotency-Key': mutation.idempotencyKey,
        'If-Match': `"${mutation.baseVersion}"`
      },
      body: JSON.stringify({ patch: mutation.patch })
    }
  )

  if (response.status === 409) {
    const body = await response.json() as {
      message: string
      remote: RemoteWorkOrder
    }
    throw new SyncHttpError(409, body.message, body.remote)
  }
  if (!response.ok) {
    throw new SyncHttpError(
      response.status,
      `sync failed: ${response.status}`
    )
  }

  return response.json() as Promise<RemoteWorkOrder>
}

2. 单一同步循环 ​

ts
const activeSync = new WeakMap<InspectionDatabase, Promise<void>>()

export function syncOutbox(
  db: InspectionDatabase,
  signal: AbortSignal
): Promise<void> {
  const current = activeSync.get(db)
  if (current) return current

  const running = runSync(db, signal).finally(() => {
    activeSync.delete(db)
  })
  activeSync.set(db, running)
  return running
}

async function runSync(
  db: InspectionDatabase,
  signal: AbortSignal
): Promise<void> {
  while (!signal.aborted) {
    const queue = await db.getAll('mutations', undefined, 1)
    const mutation = queue[0]
    if (!mutation) return
    if (mutation.id === undefined) {
      throw new Error('mutation has no queue id')
    }

    // 案例保持全局顺序；先解决队首冲突，再发送后续操作。
    if (mutation.state !== 'pending') return

    const base = await db.get('workOrders', mutation.entityId)
    if (!base) {
      await db.put('mutations', {
        ...mutation,
        state: 'conflict',
        conflictFields: ['entity'],
        message: '工单已删除或本地快照缺失'
      })
      return
    }

    if (mutation.baseVersion !== base.version) {
      const rebased = mergeMutation(mutation, base)
      if (rebased.conflicts.length > 0) {
        await db.put('mutations', {
          ...mutation,
          state: 'conflict',
          conflictFields: rebased.conflicts,
          message: '同步前服务器快照已经变化'
        })
        return
      }

      if (Object.keys(rebased.patch).length === 0) {
        await db.delete('mutations', mutation.id)
      } else {
        await db.put('mutations', {
          ...mutation,
          patch: rebased.patch,
          baseValues: pickBaseValues(base, rebased.patch),
          baseVersion: base.version,
          idempotencyKey: crypto.randomUUID()
        })
      }
      continue
    }

    try {
      const updated = await pushMutation(base, mutation, signal)
      const tx = db.transaction(['workOrders', 'mutations'], 'readwrite')
      await tx.objectStore('workOrders').put({
        ...updated,
        lastSyncedAt: Date.now()
      })
      await tx.objectStore('mutations').delete(mutation.id)
      await tx.done
    } catch (error) {
      if (error instanceof SyncHttpError
        && error.status === 409
        && error.remote) {
        const merged = mergeMutation(mutation, error.remote)
        const tx = db.transaction(['workOrders', 'mutations'], 'readwrite')
        await tx.objectStore('workOrders').put({
          ...error.remote,
          lastSyncedAt: Date.now()
        })

        if (merged.conflicts.length > 0) {
          await tx.objectStore('mutations').put({
            ...mutation,
            state: 'conflict',
            conflictFields: merged.conflicts,
            message: '本地和服务器修改了相同字段'
          })
          await tx.done
          return
        }

        if (Object.keys(merged.patch).length === 0) {
          await tx.objectStore('mutations').delete(mutation.id)
        } else {
          await tx.objectStore('mutations').put({
            ...mutation,
            patch: merged.patch,
            baseValues: pickBaseValues(error.remote, merged.patch),
            baseVersion: error.remote.version,
            idempotencyKey: crypto.randomUUID()
          })
        }
        await tx.done
        continue
      }

      if (error instanceof SyncHttpError
        && [404, 410].includes(error.status)) {
        await db.put('mutations', {
          ...mutation,
          state: 'conflict',
          conflictFields: ['entity'],
          message: '工单已被服务器删除'
        })
        return
      }

      if (error instanceof SyncHttpError
        && [403, 422].includes(error.status)) {
        await db.put('mutations', {
          ...mutation,
          state: 'rejected',
          message: error.message
        })
        return
      }

      throw error
    }
  }
}

七、使用三方比较处理冲突 ​

冲突需要比较三份值：用户编辑时看到的 Base、用户想要的 Local、服务器当前的 Remote。

ts
type EditableKey = keyof EditableFields

type MergeResult = {
  patch: WorkOrderPatch
  conflicts: EditableKey[]
}

const editableKeys: EditableKey[] = [
  'result',
  'temperature',
  'note'
]

function setPatchValue<K extends EditableKey>(
  patch: WorkOrderPatch,
  key: K,
  value: EditableFields[K]
) {
  patch[key] = value
}

export function mergeMutation(
  mutation: PendingMutation,
  remote: RemoteWorkOrder
): MergeResult {
  const patch: WorkOrderPatch = {}
  const conflicts: EditableKey[] = []

  for (const key of editableKeys) {
    const local = mutation.patch[key]
    if (local === undefined) continue

    const base = mutation.baseValues[key]
    const server = remote[key]

    if (Object.is(server, base)) {
      setPatchValue(patch, key, local)
    } else if (!Object.is(server, local)) {
      conflicts.push(key)
    }
  }

  return { patch, conflicts }
}

三方结果处理
Remote 与 Base 相同远端没改该字段，安全保留 Local
Remote 与 Local 相同目标结果已存在，不再提交该字段
Local 与 Base 相同用户实际没改，不生成 Mutation
三者不同展示 Base、Local、Remote，让用户选择
远端已删除实体不自动重建，允许复制本地内容后放弃原修改

用户解决冲突后，以 Remote 作为新 Base，把 baseVersion 更新为远端版本，生成新幂等键并将 Mutation 恢复为 pending。不能复用已经携带旧 Body 请求过的幂等键。

巡检结果是少量独立字段，三方比较足够。多人实时编辑富文本、列表顺序或离线多设备长期合并时，才评估 OT、CRDT 或完整本地优先架构；不能为了避免一个冲突弹窗就引入整套协同协议。

八、用 Pinia 表达可见状态 ​

一个 isOffline 布尔值无法区分缓存加载、陈旧可用、同步中、冲突和登录失效。Pinia Store 可以只管理 UI 状态，不复制 IndexedDB 数据库：

ts
import { computed, ref } from 'vue'
import { defineStore } from 'pinia'

type SyncPhase =
  | 'loading-cache'
  | 'ready'
  | 'stale'
  | 'syncing'
  | 'conflict'
  | 'auth-required'
  | 'error'

export const useSyncStatusStore = defineStore('sync-status', () => {
  const phase = ref<SyncPhase>('loading-cache')
  const pendingCount = ref(0)
  const lastSyncedAt = ref<number | null>(null)
  const message = ref('')

  const hasPendingChanges = computed(() => pendingCount.value > 0)

  function update(input: {
    phase: SyncPhase
    pendingCount?: number
    lastSyncedAt?: number | null
    message?: string
  }) {
    phase.value = input.phase
    if (input.pendingCount !== undefined) {
      pendingCount.value = input.pendingCount
    }
    if (input.lastSyncedAt !== undefined) {
      lastSyncedAt.value = input.lastSyncedAt
    }
    message.value = input.message ?? ''
  }

  return {
    phase,
    pendingCount,
    lastSyncedAt,
    message,
    hasPendingChanges,
    update
  }
})

九、更新、配额与安全边界 ​

1. 存储不是永久磁盘 ​

使用 Storage API 观察容量，而不是等写入失败后才处理：

ts
const { usage = 0, quota = 0 } = await navigator.storage.estimate()

if (usageRatio !== null && usageRatio > 0.8) {
  console.warn('offline storage is close to its quota')
}

案例只保留最近 7 天和最多 500 个工单，优先淘汰已完成且没有 Mutation 的旧快照。未同步 Mutation 不是普通缓存，不能按 LRU 静默删除。navigator.storage.persist() 只能请求更稳定的存储，浏览器可以拒绝，应用仍需处理配额和数据丢失。

Schema 升级先做短小的结构迁移，再由应用分批转换大量记录。升级失败时保留 Outbox 并阻止继续编辑，不能为了“修复缓存”直接删除包含未同步输入的数据库。

2. 离线数据仍是敏感数据 ​

风险处理方式
共用设备切换账号使用账号作用域隔离数据库，登出关闭并删除对应数据
XSS 读取 IndexedDB执行 CSP、输出编码和依赖治理；浏览器内加密不能阻止同源恶意脚本
缓存旧权限只允许低风险离线编辑，服务端同步时重新授权
Service Worker 泄露接口响应不注册业务 API 的通用缓存路由
Outbox 含敏感内容只保存必要字段，不记录 Token、Cookie 和完整请求头
Cookie 同步请求被伪造使用项目统一的 SameSite 与 CSRF 防护
登出时仍在同步Abort 请求、清空内存状态，再删除账号数据库

客户端隐藏审批按钮只是交互限制。权限在离线期间可能变化，所有 Mutation 到达接口时都要重新验证用户、租户、实体和动作。

十、测试、故障实验与监控 ​

1. 浏览器级测试 ​

Service Worker、IndexedDB 和网络切换要在真实浏览器环境验证：

场景预期结果
在线访问一次后切到离线并刷新App Shell 启动，显示本地工单和最后同步时间
离线连续修改同一工单Outbox 顺序稳定，刷新后乐观结果不丢失
恢复网络并重复触发同步每个幂等键只产生一次服务端效果
第一条 Mutation 返回 409队列暂停，显示冲突，不发送后续操作
远端只修改不同字段自动重放安全 Patch，不弹冲突
返回 401保留 Outbox，进入登录恢复，不标记为网络离线
返回 403 或 422保留用户输入并显示拒绝原因，不无限重试
新 Service Worker 等待激活用户确认更新前当前页面和编辑状态不被刷新
IndexedDB 升级或配额失败不删除 Outbox，阻止会造成丢失的后续写入
登出后换账号新账号无法读取旧账号快照和 Mutation

Playwright 可以使用浏览器上下文的离线模式验证启动和同步，但仍要在真实 Safari、移动设备和存储压力环境中检查 Service Worker 生命周期与淘汰行为。测试不能只 Mock Repository，否则无法发现事务、升级和 Worker 接管问题。

2. 线上指标 ​

指标用途
App Shell 离线启动成功率验证 Service Worker 与资源版本
本地快照命中率和陈旧时长判断缓存范围是否合理
Outbox 数量和最老等待时间发现长期无法同步的数据
Mutation 成功、重试、拒绝比例区分网络、权限和校验问题
冲突率及字段分布判断数据模型是否需要调整
自动合并与人工解决比例验证三方合并规则
IndexedDB 写入和升级失败率发现配额、兼容和 Schema 问题
Service Worker 版本分布发现旧版本长期未激活

日志记录实体类型、Mutation ID、版本和错误分类，不记录备注全文、Cookie、Token 和 IndexedDB 内容。冲突诊断需要值时，应在受控环境使用脱敏样本，而不是上传真实业务文本。

十一、方案选择 ​

业务要求优先方案
只减少重复请求HTTP Cache 或内存查询缓存，不引入 Service Worker
打开过的页面可在弱网阅读IndexedDB 快照 + 在线重新验证
应用断网后仍能启动增加 Service Worker App Shell
允许离线草稿IndexedDB + Outbox，但不自动提交高风险动作
允许离线业务修改幂等接口、实体版本、顺序队列和冲突处理
多设备长期离线并频繁协作重新评估本地优先同步模型，而不是继续堆补丁

出现以下信号时重新评审方案：

  • Outbox 经常积压到超过产品承诺的离线时间。
  • 大量冲突集中在同一字段，简单三方比较无法表达业务意图。
  • 全局队首冲突频繁阻塞无关工单，需要按实体拆分队列。
  • IndexedDB 数据量、迁移时间或存储失败超过预算。
  • Service Worker 更新长期碎片化，前后端协议无法兼容旧客户端。
  • 产品开始要求多设备离线创建、共享和合并同一数据集。

总结 ​

前端缓存、离线和同步不是三个独立开关，而是一条有所有权的数据链：

text
静态资源由 HTTP Cache 和 Service Worker 管理
  -> 服务器快照进入 IndexedDB
  -> UI 读取快照并叠加 Outbox
  -> 本地编辑先事务化保存再展示
  -> 网络恢复后按顺序发送幂等 Mutation
  -> 版本冲突执行三方比较
  -> 成功后更新快照并删除已确认 Mutation
  -> 配额、登出和升级都保护未同步输入

常见误区正确处理
navigator.onLine 决定能否请求它只触发尝试，接口结果才是事实
Service Worker 缓存所有 GET只缓存明确资源，业务数据进入受控存储

离线提交后直接显示成功展示待同步、同步中、冲突和拒绝状态
恢复网络后并发重放同一实体按顺序提交，并使用幂等键

所有冲突都采用最后写入获胜只自动合并有证据安全的字段
更新或配额不足就清空数据库未同步输入不是缓存，必须优先保护

可靠的离线方案最终要回答四个问题：当前界面由哪份数据派生，哪些修改尚未被服务器确认，恢复网络后以什么顺序提交，以及本地和远端都变化时如何让用户得到可解释的结果。
