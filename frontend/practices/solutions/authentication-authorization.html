登录、会话、鉴权与权限系统 ​

前端登录权限方案不只是“保存 Token + 路由守卫”。它需要正确表达会话初始化、登录失效、页面跳转、请求错误、权限控制和多标签页同步，同时明确一个安全边界：前端只能改善交互，最终认证和授权必须由服务端执行。

本文默认使用同源 Web 应用和 Cookie 会话作为主要示例。核心状态与安全原则保持框架无关，Store、Router 和组件部分使用 Vue 3、Pinia 与 Vue Router。

问题场景与常见错误 ​

一个企业应用包含：

  • 登录页和公开页面。
  • 必须登录才能访问的业务页面。
  • 不同用户可见的菜单和操作按钮。
  • 会话过期后的重新登录与任务恢复。
  • 多个标签页中的登录、登出和权限变化。

最直接的实现经常是：

ts
const isLoggedIn = Boolean(localStorage.getItem('token'))

router.beforeEach((to) => {
  if (to.meta.requiresAuth && !isLoggedIn) {
    return '/login'
  }
})

function canDelete(user: User) {
  return user.role === 'admin'
}

正确方案需要分别设计身份认证、会话、前端访问控制和服务端授权。

一、概念与职责边界 ​

1. 认证、会话和授权 ​

概念回答的问题前端负责什么
身份认证当前用户是谁收集凭据、展示流程和结果
会话多次请求如何关联同一身份初始化、失效处理和交互状态
授权用户能否执行某个动作根据能力改善 UI，不做最终决定
审计谁在何时执行了什么传递关联信息，不保存安全结论

路由守卫、菜单隐藏和按钮禁用都不是安全措施。用户可以绕过页面直接发送请求，因此接口必须重新验证身份、资源和动作。

二、会话保存方式 ​

1. HttpOnly Cookie ​

同源 Web 应用通常优先使用 Secure、HttpOnly、适当 SameSite 的 Cookie 保存不可解释的会话标识。

核心原理： JavaScript 无法读取 HttpOnly Cookie，但浏览器会按规则随请求发送。前端通过 /api/session 判断会话，而不是读取 Cookie 内容。

ts
async function fetchSession(signal?: AbortSignal) {
  const response = await fetch('/api/session', {
    credentials: 'include',
    signal
  })

  if (response.status === 401) return null
  if (!response.ok) throw new Error(`session failed: ${response.status}`)

  return response.json() as Promise<SessionSnapshot>
}

2. JavaScript 可读 Token ​

前后端跨域、原生容器或必须直连多个资源服务时，可能使用短期访问 Token。

存放位置刷新后保留主要风险
内存否页面刷新后需要恢复
sessionStorage当前标签页XSS 可读取
localStorage是XSS 可长期读取，跨标签页共享

不要因为接入简单就默认把长期 Token 放进 localStorage。凭证价值、有效期、撤销能力和 XSS 风险需要共同评估。

本文后续代码使用 Cookie 会话，因此 Store 中不会保存 Token。

2. Pinia 会话 Store ​

ts
// stores/auth.ts
import { computed, ref, shallowRef } from 'vue'
import { defineStore } from 'pinia'

export const useAuthStore = defineStore('auth', () => {
  const status = ref<AuthStatus>('unknown')
  const user = shallowRef<SessionUser | null>(null)
  const permissions = shallowRef<string[]>([])

  const permissionSet = computed(() => new Set(permissions.value))
  let initializePromise: Promise<void> | null = null

  function clear(nextStatus: AuthStatus) {
    user.value = null
    permissions.value = []
    status.value = nextStatus
  }

  async function loadSession() {
    try {
      const session = await fetchSession()

      if (!session) {
        clear('anonymous')
        return
      }

      user.value = session.user
      permissions.value = session.permissions
      status.value = 'authenticated'
    } catch {
      status.value = 'error'
    }
  }

  function initialize(force = false) {
    if (!force && status.value !== 'unknown') return Promise.resolve()
    if (initializePromise) return initializePromise

    initializePromise = loadSession().finally(() => {
      initializePromise = null
    })

    return initializePromise
  }

  function can(permission: string) {
    return status.value === 'authenticated' &&
      permissionSet.value.has(permission)
  }

  function markExpired() {
    clear('expired')
  }

  return {
    status,
    user,
    permissions,
    initialize,
    can,
    markExpired,
    clear
  }
})

四、登录、登出与任务恢复 ​

1. 登录流程 ​

ts
type LoginForm = {
  account: string

async function login(form: LoginForm) {
  const response = await fetch('/api/login', {
    method: 'POST',
    credentials: 'include',

五、统一处理请求中的会话失效 ​

1. 401 与 403 不相同 ​

状态含义前端处理
401当前请求缺少有效认证标记会话失效，要求重新登录
403身份有效，但没有当前操作权限保持登录，展示无权限结果

不要遇到任何 403 都清空登录态，也不要把网络错误当成 401。

2. 统一请求封装 ​

ts
class AuthenticationExpiredError extends Error {}
class PermissionDeniedError extends Error {}

async function apiFetch(input: RequestInfo | URL, init?: RequestInit) {
  const response = await fetch(input, {
    ...init,
    credentials: 'include'
  })

  if (response.status === 401) {
    useAuthStore().markExpired()
    throw new AuthenticationExpiredError('session expired')
  }

  if (response.status === 403) {
    throw new PermissionDeniedError('permission denied')
  }

  return response
}

3. 防止重复提示和重定向循环 ​

当多个并发请求同时返回 401，只允许一个全局恢复流程：

function createReauthenticationGate(
  openLoginDialog: () => Promise<void>
) {
  let recoveryPromise: Promise<void> | null = null

  return function requireReauthentication() {
    if (recoveryPromise) return recoveryPromise

    recoveryPromise = openLoginDialog().finally(() => {
      recoveryPromise = null
    })

    return recoveryPromise
  }
}

2. 全局守卫 ​

ts
router.beforeEach(async (to) => {
  const auth = useAuthStore()

  if (to.meta.public) return true

  await auth.initialize()

  if (auth.status === 'error') {
    return { name: 'session-unavailable' }
  }

  if (auth.status !== 'authenticated') {
    return {
      name: 'login',
      query: { redirect: to.fullPath }
    }
  }

  const required = to.meta.permissions ?? []
  const allowed = to.meta.permissionMode === 'any'
    ? required.some(auth.can)
    : required.every(auth.can)

  if (!allowed) return { name: 'forbidden' }
  return true
})

2. 隐藏还是禁用 ​

方式适用场景

九、前端安全注意事项 ​

1. XSS 与凭证 ​

  • 不把密码、验证码和完整凭证写入日志、URL 和持久状态。
  • 不直接渲染未经净化的富文本和第三方 HTML。
  • 减少第三方脚本，并使用 CSP 等浏览器安全能力。
  • 即使 Cookie 是 HttpOnly，XSS 仍可代表用户发起请求。

2. CSRF ​

Cookie 会自动随请求发送，状态变更接口需要使用项目约定的 CSRF 防护。前端可能需要从页面元数据或安全接口读取 CSRF Token，并放入请求头：

ts
function getCsrfToken() {
  const element = document.querySelector<HTMLMetaElement>(
    'meta[name="csrf-token"]'
  )

  if (!element?.content) throw new Error('missing CSRF token')
  return element.content
}

async function postWithCsrf(url: string, body: unknown) {
  return fetch(url, {
    method: 'POST',
    credentials: 'include',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': getCsrfToken()
    },
    body: JSON.stringify(body)
  })
}

3. URL 与缓存泄露 ​

  • Token、密码和敏感参数不进入查询字符串。
  • 用户私有响应不能进入公共缓存。
  • 登出和账号切换时清理对应查询缓存。
  • 错误上报和分析埋点对 URL、Header 和用户输入脱敏。

4. 权限变化 ​

高风险撤权必须由接口立即生效。前端可以在窗口重新激活、收到 403 或权限版本变化时刷新会话快照，但不能依赖固定轮询保证安全。

十、测试与监控 ​

1. Store 单元测试 ​

至少验证：

  • 会话存在时进入 authenticated。
  • 401 进入 anonymous，网络失败进入 error。
  • 多次 initialize() 只产生一个请求。
  • can() 只在已登录且具有权限时返回 true。
  • markExpired() 清理用户和权限。

2. 路由与组件测试 ​

  • 未初始化时等待会话，不出现登录页闪烁。
  • 未登录访问受限页面时保留安全回跳地址。
  • 网络错误进入故障页，不进入登录循环。
  • 缺少权限进入无权限页。
  • 菜单、按钮和路由使用同一权限命名。

3. 端到端场景 ​

  • 登录成功、失败、限流和取消。
  • 会话在页面停留期间过期。
  • 多个并发请求同时返回 401。
  • 登录恢复后保留草稿，但不重复危险写操作。
  • 两个标签页中登出和权限变化。
  • 直接请求无权限接口仍然被拒绝。
  • 开放重定向、Token 泄露和 CSRF 防护。

4. 前端监控 ​

记录流程结果，而不是敏感凭证：

指标用途
会话初始化成功率和耗时发现身份服务或网络问题
登录各阶段失败率区分输入错误、限流和系统错误
401/403 数量和页面分布发现会话失效和权限配置问题
登录重定向循环发现 Router 和状态机错误
多标签页重新验证失败发现同步和恢复问题

日志和指标不记录密码、Token、Cookie、验证码和完整权限列表。

十一、方案选择 ​

会话方式 ​

场景前端优先考虑
同源 Web 与 SSRHttpOnly Cookie + 会话接口
企业统一登录OIDC 登录后转换为站内会话
原生容器或多资源 API短期访问 Token + 受控恢复
纯公开页面不建立用户会话

权限表达 ​

场景前端表达方式
全局功能权限permission 字符串集合
当前资源允许动作接口返回 allowedActions
复杂条件前端展示提示，接口执行最终策略
菜单与路由使用同一权限命名和 can() 判断

总结 ​

登录权限前端方案可以归纳为一条状态链：

text
启动时获取会话快照
  -> 使用状态机区分未知、匿名、登录、过期和错误
  -> Router 控制正常导航
  -> 组件根据动作权限调整界面
  -> 请求层统一区分 401、403 和网络错误
  -> 多标签页只广播变化通知
  -> 服务端始终执行最终认证与授权

常见问题正确处理
本地有 Token 就算登录通过会话接口确认
初始化时闪登录页保留 unknown 状态并等待初始化
401、403 都清空登录分别处理认证失效和权限不足
页面判断角色名使用动作权限和资源允许动作
路由守卫保护数据它只改善导航，接口负责安全
多标签页直接同步权限对象只广播变化，再重新确认会话
登录后自动重放写请求只安全重取查询，危险操作需确认

前端登录权限的目标不是在浏览器中复制一套安全系统，而是准确表达会话状态、提供一致交互，并且不削弱服务端安全边界。
