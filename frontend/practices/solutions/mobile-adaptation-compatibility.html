移动端适配与浏览器兼容方案 ​

移动端适配不是把一张 375px 设计稿等比缩放到所有屏幕，浏览器兼容也不是在构建配置里写一个目标列表就结束。同一个页面会同时受到布局视口、可视视口、安全区、输入设备、浏览器引擎和内置 WebView 的影响，任何一层处理错误，都可能让核心流程无法完成。

本文使用一个 Vue 3 订单编辑页贯穿方案。它需要同时运行在 iOS Safari、Android Chrome 和应用内 WebView 中，页面包含长表单、订单摘要和底部操作栏。目标不是让所有环境像素级一致，而是让支持范围内的用户都能查看、编辑和提交订单，并且能够定位真实设备上的差异。

ts
type EnvironmentSnapshot = {
  layoutViewport: string
  visualViewport: string | null
  visualScale: number | null
  dynamicViewportUnit: boolean
  containerQueries: boolean
  coarsePointer: boolean
  hover: boolean
}

export function captureEnvironment(): EnvironmentSnapshot {
  const visual = window.visualViewport

  return {
    layoutViewport: `${window.innerWidth}x${window.innerHeight}`,
    visualViewport: visual
      ? `${Math.round(visual.width)}x${Math.round(visual.height)}`
      : null,
    visualScale: visual?.scale ?? null,
    dynamicViewportUnit: CSS.supports('height: 100dvh'),
    containerQueries: CSS.supports('container-type: inline-size'),
    coarsePointer: matchMedia('(pointer: coarse)').matches,
    hover: matchMedia('(hover: hover)').matches
  }
}

一、先定义支持契约 ​

兼容性必须是产品契约，不能由开发者根据手边设备临时决定。契约至少包含环境、功能等级、视觉要求、验证方式和退出条件。

下面是案例团队根据最近 90 天真实流量填写的示例，不是所有项目都应照抄的浏览器范围：

等级环境承诺验证方式
A：完整支持iOS Safari 16+、Chrome Android 120+、Chromium WebView 120+核心流程、响应式布局、安全区和增强交互全部可用自动化矩阵 + 每次发布真机冒烟
B：功能支持iOS Safari 15、Chromium 109～119查看、编辑、校验和提交可用，允许布局与动效降级发布前关键流程真机回归
C：范围外更旧或无法识别的 WebView保证服务端数据安全；展示可理解的升级或外部浏览器提示HTML 启动页与监控验证

这个案例对应的验收标准是：

  • 320～430 CSS px 宽度下不出现页面级横向滚动。
  • 200% 文本放大后，字段标签、错误信息和按钮仍不重叠。
  • 浏览器工具栏展开、收起和横竖屏切换后，页面仍只有一个主要滚动区域。
  • 软键盘出现时，当前输入框保持可见；关闭键盘后能够访问保存操作。
  • 不支持容器查询或动态视口单位时，核心订单流程仍然可完成。
  • A、B 级环境提交结果一致，允许阴影、间距和动效存在非关键差异。

支持范围应使用浏览器引擎和宿主版本表达，而不是只写“安卓手机”。同一个 Android 系统可能运行不同版本的 Chrome、系统 WebView和厂商内核。应用内页面还需要记录宿主应用版本，因为它可能改变 WebView 配置、键盘行为和安全策略。

如果项目确实要求支持不能解析 ES Module 的旧浏览器，需要单独评估旧产物、依赖安全和测试成本。它不是给现代构建增加几个前缀就能完成的普通兼容任务。

二、建立可收缩的页面骨架 ​

页面先使用正常文档流和内容驱动的布局，再处理少数确实需要覆盖的浏览器差异。案例使用以下视口声明：

html
<meta
  name="viewport"
  content="width=device-width, initial-scale=1, viewport-fit=cover"
>

width=device-width 让 CSS 像素宽度匹配设备视口，viewport-fit=cover 允许页面延伸到异形屏区域，后续必须使用安全区内边距保护内容。这里不限制最大缩放比例，也不禁止用户缩放。

1. 完整订单页面 ​

页面使用“头部、单一滚动区、操作栏”三行 Grid。操作栏本身不覆盖正文，因此不需要依赖全局 fixed 定位：

vue
<!-- OrderEditPage.vue -->
<script setup lang="ts">
import { reactive, ref } from 'vue'
import { useVisualViewport } from './useVisualViewport'

type OrderDraft = {
  recipient: string
  phone: string
  address: string
  quantity: number
  note: string
}

type SaveResult = {
  orderId: string
  updatedAt: string
}

const pageRoot = ref<HTMLElement | null>(null)
const formElement = ref<HTMLFormElement | null>(null)
const saving = ref(false)
const statusMessage = ref('尚未保存')

const draft = reactive<OrderDraft>({
  recipient: '',
  phone: '',
  address: '',
  quantity: 1,
  note: ''
})

useVisualViewport(pageRoot)

async function saveOrder(input: OrderDraft): Promise<SaveResult> {
  const response = await fetch('/api/orders/draft', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify(input)
  })

  if (!response.ok) {
    throw new Error(`save order failed: ${response.status}`)
  }

  return response.json() as Promise<SaveResult>
}

async function submitOrder() {
  const form = formElement.value
  if (!form?.reportValidity()) {
    form?.querySelector<HTMLElement>(':invalid')?.focus()
    return
  }

  saving.value = true
  statusMessage.value = '正在保存'

  try {
    const result = await saveOrder({ ...draft })
    statusMessage.value = `已保存，更新时间 ${result.updatedAt}`
  } catch {
    statusMessage.value = '保存失败，请检查网络后重试'
  } finally {
    saving.value = false
  }
}

function cancelEdit() {
  if (window.confirm('放弃尚未保存的修改？')) {
    window.history.back()
  }
}
</script>

<template>
  <main ref="pageRoot" class="order-page">
    <header class="order-header">
      <div>
        <h1>编辑订单</h1>
        <p role="status" aria-live="polite">
          {{ statusMessage }}
        </p>
      </div>
    </header>

    <div class="order-scroll">
      <form
        id="order-form"
        ref="formElement"
        class="order-layout"
        novalidate
        @submit.prevent="submitOrder"
      >
        <section class="order-fields" aria-labelledby="delivery-title">
          <h2 id="delivery-title">配送信息</h2>

          <label>
            <span>收货人</span>
            <input
              v-model.trim="draft.recipient"
              name="recipient"
              autocomplete="name"
              required
            >
          </label>

          <label>
            <span>手机号</span>
            <input
              v-model.trim="draft.phone"
              name="phone"
              type="tel"
              inputmode="tel"
              autocomplete="tel"
              pattern="[0-9 +()-]{7,20}"
              required
            >
          </label>

          <label>
            <span>配送地址</span>
            <textarea
              v-model.trim="draft.address"
              name="address"
              autocomplete="street-address"
              rows="3"
              required
            />
          </label>

          <label>
            <span>商品数量</span>
            <input
              v-model.number="draft.quantity"
              name="quantity"
              type="number"
              inputmode="numeric"
              min="1"
              max="99"
              required
            >
          </label>

          <label>
            <span>订单备注</span>
            <textarea
              v-model="draft.note"
              name="note"
              rows="5"
              enterkeyhint="done"
            />
          </label>
        </section>

        <aside class="order-summary" aria-labelledby="summary-title">
          <h2 id="summary-title">订单摘要</h2>
          <dl>
            <div><dt>商品</dt><dd>前端工程手册</dd></div>
            <div><dt>数量</dt><dd>{{ draft.quantity }}</dd></div>
            <div><dt>配送</dt><dd>标准配送</dd></div>
          </dl>
        </aside>
      </form>
    </div>

    <footer class="order-actions">
      <button type="button" class="secondary" @click="cancelEdit">
        取消
      </button>
      <button
        type="submit"
        form="order-form"
        :disabled="saving"
      >
        {{ saving ? '保存中' : '保存订单' }}
      </button>
    </footer>
  </main>
</template>

这段实现有几个刻意的选择：

  • 移动端单列是默认布局，增强条件失败时仍可使用。
  • minmax(0, 1fr) 和子项的 min-inline-size: 0 允许内容真正收缩，避免 Grid 子项把页面撑宽。
  • 页面只让 .order-scroll 滚动，头部和操作栏占据正常的 Grid 行，不覆盖表单。
  • 容器查询根据组件实际可用宽度切换双列；不支持时退回视口媒体查询。
  • 输入框使用稳定的 16px 字号，不通过视口宽度连续缩放文字。
  • 普通表单和按钮依赖原生语义，不为了触屏重新实现点击、焦点和键盘行为。

2. 断点来自内容，不来自设备名称 ​

当“表单 + 16rem 摘要 + 间距”能够同时容纳时才切换双列，这就是示例中 52rem 的来源。断点不是某款手机的物理宽度，也不需要为每个 DPR 建立一套尺寸。

CSS 像素已经是布局抽象。devicePixelRatio 主要影响位图和 Canvas 清晰度，不应被用来整体放大 DOM。全局把 px 转成 vw 会让大屏手机上的控件和文字持续变大，也会让弹窗、第三方组件和桌面分屏难以控制。

只有信息结构或操作路径确实不同，才在组件层做差异化渲染。例如桌面端是可编辑明细表、移动端是逐项编辑器时，可以拆成两个表现组件，但应复用同一份订单状态和提交逻辑。分支依据应是容器空间、输入能力或明确的宿主能力，而不是一个永久缓存的 isMobile 布尔值。

三、处理动态视口与软键盘 ​

移动浏览器至少需要区分两个视口：

  • Layout Viewport 决定大部分 CSS 布局尺寸。
  • Visual Viewport 表示用户当前真正看见的区域，会受浏览器工具栏、软键盘和页面缩放影响。

传统 vh 在移动浏览器中的历史行为并不一致。现代方案先声明 100vh 作为语法回退，再用 100dvh 跟随地址栏等动态浏览器界面。前面的页面骨架已经使用了这个顺序；不认识 dvh 的浏览器会忽略第二条声明。

软键盘是否改变布局视口和视口单位仍取决于浏览器策略，不能认为用了 dvh，键盘就一定会推动页面。键盘场景还要观察 Visual Viewport 和焦点控件的位置。

1. 用 VisualViewport 保持焦点可见 ​

下面的 Vue 辅助函数在可视区域变化后保证焦点控件没有落在操作栏后面。只有 B 级 WebView 缺少 dvh 但提供 VisualViewport 时，它才额外接管页面高度：

ts
// useVisualViewport.ts
import { onBeforeUnmount, onMounted, type Ref } from 'vue'

const editableSelector = [
  'input:not([type="hidden"])',
  'textarea',
  'select',
  '[contenteditable="true"]'
].join(',')

export function useVisualViewport(root: Ref<HTMLElement | null>) {
  let viewport: VisualViewport | null = null
  let frame = 0
  let usesHeightFallback = false

  function keepFocusedControlVisible() {
    const active = document.activeElement
    const page = root.value

    if (!(active instanceof HTMLElement)) return
    if (!page?.contains(active) || !active.matches(editableSelector)) return
    if (!viewport) return

    const rect = active.getBoundingClientRect()
    const visibleTop = viewport.offsetTop + 12
    const visibleBottom = viewport.offsetTop + viewport.height - 80

    if (rect.top < visibleTop || rect.bottom > visibleBottom) {
      active.scrollIntoView({ block: 'center', behavior: 'auto' })
    }
  }

  function update() {
    const page = root.value
    if (!page || !viewport) return

    // 页面缩放也会改变 VisualViewport，不能把缩放误判为键盘。
    if (Math.abs(viewport.scale - 1) > 0.01) return

    if (usesHeightFallback) {
      page.style.setProperty(
        '--visual-viewport-height',
        `${Math.round(viewport.height)}px`
      )
    }
    keepFocusedControlVisible()
  }

  function scheduleUpdate() {
    cancelAnimationFrame(frame)
    frame = requestAnimationFrame(update)
  }

  onMounted(() => {
    viewport = window.visualViewport
    if (!viewport || !root.value) return

    usesHeightFallback = !CSS.supports('height: 100dvh')
    root.value.classList.toggle(
      'uses-visual-viewport',
      usesHeightFallback
    )
    viewport.addEventListener('resize', scheduleUpdate)
    viewport.addEventListener('scroll', scheduleUpdate)
    window.addEventListener('resize', scheduleUpdate)
    update()
  })

  onBeforeUnmount(() => {
    cancelAnimationFrame(frame)
    viewport?.removeEventListener('resize', scheduleUpdate)
    viewport?.removeEventListener('scroll', scheduleUpdate)
    window.removeEventListener('resize', scheduleUpdate)
    root.value?.classList.remove('uses-visual-viewport')
    root.value?.style.removeProperty('--visual-viewport-height')
  })
}

2. 表单和键盘的细节 ​

示例中的表单还处理了以下问题：

实现解决的问题限制

横竖屏变化后优先让容器查询和正常重排接管布局。只有视频、游戏或硬件采集等确实要求方向锁定的场景，才考虑 Screen Orientation API，并为不支持和拒绝授权准备正常页面布局。

五、统一鼠标、触摸和手写笔交互 ​

屏幕宽度不能代表输入方式。大屏设备可能只有触摸，窄窗口也可能连接鼠标和键盘。普通按钮、链接和表单控件应继续使用原生 click、焦点和键盘语义；只有拖拽、绘制等连续手势才需要直接处理指针事件。

触控目标需要保留稳定面积和间距。案例选择 44px 作为团队交互基线，不通过 transform: scale() 伪造视觉尺寸。touch-action: manipulation 告诉浏览器按钮区域不需要自定义平移或缩放手势，但页面其他区域仍保留浏览器缩放能力。

六、把兼容性拆成三个层次 ​

“构建成功”不等于“浏览器可运行”。需要分别处理语法、CSS 能力和运行时 API：

2. 先检测能力，再决定增强 ​

应用启动时可以安装一组低基数能力标记，供样式、降级和监控共用：

ts
// capabilities.ts
export type Capabilities = {
  dynamicViewport: boolean
  containerQueries: boolean
  visualViewport: boolean
  pointerEvents: boolean
}

export function detectCapabilities(): Capabilities {
  return {
    dynamicViewport: CSS.supports('height: 100dvh'),
    containerQueries: CSS.supports('container-type: inline-size'),
    visualViewport: 'visualViewport' in window,
    pointerEvents: 'PointerEvent' in window
  }
}

export function installCapabilityClasses(
  capabilities = detectCapabilities()
): Capabilities {
  const root = document.documentElement

  root.classList.toggle('has-dynamic-viewport', capabilities.dynamicViewport)
  root.classList.toggle('has-container-queries', capabilities.containerQueries)
  root.classList.toggle('has-visual-viewport', capabilities.visualViewport)
  root.classList.toggle('has-pointer-events', capabilities.pointerEvents)

  return capabilities
}

七、为每种缺失能力准备结果 ​

渐进增强不是“旧浏览器随便显示”，而是预先定义缺失能力时用户还能完成什么：

缺失能力案例回退用户结果
Container Queries使用视口媒体查询宽度临界点可能不够精确，编辑和提交不受影响
dvh有 VisualViewport 时更新 CSS 变量，否则保留 100vh 和滚动表单旧环境可能需要收起键盘访问底栏
Pointer Events不启用横向拖动使用明确的删除按钮
Hover不显示 Hover 样式焦点、按下和禁用状态仍然存在
某个装饰性格式使用基础颜色或静态图核心内容和操作不变化
目标语法无法解析返回不依赖应用 Bundle 的支持提示页用户获得升级或外部浏览器路径

最后一项无法靠应用内的 try...catch 处理，因为代码可能在执行前就解析失败。如果必须为范围外浏览器提供提示，应由服务端或最小 HTML 启动页完成，而不是依赖同一个现代 Bundle 自我诊断。

降级不能静默改变业务含义。例如日期控件表现不一致时，可以退回明确格式的文本输入并做同等校验，不能把无效日期当成空值提交。支付、签名、文件选择等关键能力缺失时，应阻止当前动作并给出替代路径，而不是伪造成功状态。

浏览器引擎和主版本聚合实现差异，避免完整 UA 的高基数
浏览器或应用内 WebView区分宿主配置
视口宽度分桶发现特定布局区间，而不是记录精确设备型号
dvh、容器查询、Pointer Events 能力位判断实际能力和 UA 声明是否一致
页面启动成功率发现语法、资源加载和初始化失败
订单提交成功率判断兼容差异是否影响核心业务
横向溢出与视口回退命中率发现响应式回归和旧环境占比

页面没有成功启动时，应用自身无法上报错误。首屏 HTML、静态资源监控或服务端访问日志需要覆盖这段盲区。

生产数据用于调整支持范围和真机矩阵，但不能把完整 UA、输入内容、精确屏幕组合和用户身份一起长期保存。先做归一化与分桶，并遵守项目的隐私采集边界。

十、方案选择与重新决策 ​

1. 选择页面适配方式 ​

场景优先方案主要代价
信息和操作顺序基本相同同一 DOM + 流式布局和容器查询需要严格控制可收缩内容
桌面与移动信息结构明显不同共享状态与业务逻辑，拆分表现组件两套组件测试和一致性成本
移动端拥有独立流程和发布节奏独立移动入口或应用路由、SEO、状态和发布治理成本高
依赖大量设备能力、离线或原生交互进入跨端或原生方案评估容器、桥接、权限和版本治理成本

不要仅因为移动端有三处 CSS 差异就复制整套应用，也不要为了“只维护一份代码”把完全不同的桌面表格强塞进窄屏。判断依据是信息结构、交互链路和独立发布需求，而不是设备名称。

2. 选择兼容手段 ​

条件选择
新能力只是体验增强能力检测后启用，默认路径保持可用
CSS 能力有简单等价布局默认回退 + @supports 增强
缺失 API 是核心流程依赖且 Polyfill 成本可控按需加载并纳入同等测试
浏览器连目标语法都无法解析调低构建目标或提供独立旧产物
环境占比低且支持成本或安全风险过高明确退出范围并提供升级路径
只有特定版本存在实现错误有编号、有期限、有监控的隔离补丁

出现以下信号时重新评审方案：

  • A、B 级环境的核心流程成功率出现持续差距。
  • VisualViewport 回退或某个版本补丁的命中率已经接近零。
  • 新宿主 WebView 进入主要流量，但不在真机矩阵中。
  • 两套表现组件开始复制校验、请求和状态逻辑。
  • 为旧环境增加的产物、Polyfill 和测试时间超过其业务价值。

总结 ​

移动端适配与浏览器兼容可以归纳为一条有证据的交付路径：

text
用真实流量定义支持范围
  -> 用正常文档流建立可收缩布局
  -> 用 dvh、安全区和单滚动区处理移动视口
  -> 用原生语义和 Pointer 能力适配输入
  -> 分别处理语法、CSS 和运行时 API
  -> 为每个缺失能力定义可验证的降级结果
  -> 用自动化覆盖布局和流程
  -> 用真机覆盖键盘、工具栏与 WebView
  -> 用线上结果更新支持契约并删除旧补丁

方案的目标不是消灭所有视觉差异，而是在明确的支持范围内保持内容可读、操作可达、结果一致，并让每一次例外都有复现证据、降级结果和退出条件。
