遗留系统渐进式迁移 ​

作者：codex-gpt-sol-5.6

遗留系统迁移的目标不是把旧语法全部改成新语法，而是在业务持续交付的前提下，逐步降低不可控风险，并最终删除旧运行路径。没有基线、契约、灰度、回滚和删除计划的“边开发边重写”，很容易同时维护两个不完整系统。

本文以一个运行 8 年的 Vue 2.7 + Webpack 4 运营后台为案例。系统有 63 个路由、约 21 万行代码、Vuex 全局 Store、事件总线和一套停止维护的 UI 库。目标是迁移到 Vue 3、Vite、Vue Router 4 和 Pinia；采用按路由的绞杀策略，新旧应用独立构建并由服务端发布路由稳定分流，迁移期间允许整页跳转，但不共享内存 Store。

1. 迁移目标、约束与完成标准 ​

1.1 为什么不能直接重写 ​

系统每天被 1800 名运营人员使用，每两周交付业务需求；订单审核、退款和导出不能停摆。完整重写预计 9～12 个月，在此期间旧系统仍会变化，最终切换风险无法通过一次回归消除。

当前问题有明确证据：

问题基线
冷构建14 分 20 秒
本地启动96 秒
Node/依赖Node 14、312 个生产依赖、27 个高风险漏洞待处置
自动化核心旅程 E2E 只有 6 条，覆盖 18% 关键路径
线上错误3.8 次错误事件/千页面视图
修改风险近季度 11 次全局 Store/事件总线连带回归
浏览器支持目标 Chrome/Edge 已现代化，但构建仍输出大量旧 Polyfill

1.2 迁移目标 ​

  • 业务需求持续交付，单批迁移可以独立回滚。
  • 先建立行为和接口证据，再迁移组件实现。
  • 新旧应用共享同源 Session 与服务端契约，不共享 Vue 实例、Store 和事件总线。
  • 每迁完一个路由就删除旧 owner 代码和适配层，迁移进度以删除与流量为准。
  • 服务端接口和数据变更遵循 expand → migrate → contract，兼容仍有旧标签页的窗口。
  • 最终关闭旧构建、旧部署和旧依赖，不永久保留双系统。

1.3 可验收完成标准 ​

阶段完成标准
单路由新实现达到功能、权限、错误、性能和可访问性验收，100% 流量稳定两周
单领域所有子路由 owner 切换，旧领域代码/Store/API 适配删除
全应用旧入口无流量、旧制品回滚窗口结束、旧 CI/依赖/监控下线
业务关键任务完成率不下降，审计和数据口径一致
工程构建、发布、测试和漏洞目标达到，并有新 owner

“Vue 3 页面已经上线”不等于迁移完成；旧代码仍在接流量或仍被新代码依赖，就只是增加了一套实现。

2. 策略选择与迁移边界 ​

2.1 候选方案 ​

方案优点主要风险结论
一次性重写最终结构干净长分支、需求漂移、切换和回滚风险最大不采用
全应用 @vue/compat可先跑 Vue 3 兼容模式插件不兼容、问题集中、仍是一次全局切换仅用于小范围组件迁移探针
同页 Vue 2 + Vue 3 微前端可按路由拆壳、全局资源、性能和生命周期复杂暂不采用
独立应用 + 服务端路由分流隔离清楚、可逐路由灰度回滚跨新旧路由会整页跳转采用

内部运营系统不需要无刷新跨应用切换。暂时接受整页跳转，换取独立运行时和简单回滚；若用户数据证明切换成本明显影响任务，再评估稳定壳或微前端。

2.2 迁移单位是完整用户结果 ​

第一批选择“退款原因字典管理”，因为它有独立路由、低写入频率、清楚权限和 3 个 API。迁移单位包含列表、编辑、权限、错误、审计、测试、发布和运行监控，不能只迁一个 Button 或把新组件嵌回旧全局状态。

高风险订单审核最后迁移，但安全基线、API 契约和特征测试最先覆盖它。迁移顺序由依赖和风险决定，不按文件夹字母或页面数量。

2.3 新旧系统的共享与隔离 ​

可以共享不直接共享
HttpOnly Session CookieVue/Vuex/Pinia Store
服务端 API 契约事件总线
稳定 URL 和路由 ID内存对象和组件实例
设计 Token 与独立发布包旧 UI 库内部 CSS class
request ID、release 观测字段Local Storage 任意 key
业务枚举与 Schema 包Webpack/Vite 私有构建配置

跨应用状态通过 URL 或服务端恢复。整页跳转会丢失未保存内存草稿，所以路由切换前执行脏状态确认；确需保存的草稿使用带用户、组织、资源、Schema 版本和过期时间的受控接口。

3.3 新旧路由跳转适配 ​

ts
export function navigateAcrossMigration(
  target: string,
  currentRouterOwns: (pathname: string) => boolean,
  pushInsideCurrentApp: (path: string) => void
) {
  const url = new URL(target, window.location.origin)
  if (url.origin !== window.location.origin || !url.pathname.startsWith('/')) {
    throw new Error('只允许站内迁移导航')
  }

  const path = `${url.pathname}${url.search}${url.hash}`
  if (currentRouterOwns(url.pathname)) pushInsideCurrentApp(path)
  else window.location.assign(path)
}

4.2 特征测试和观测基线 ​

旧系统先增加：

  • 关键 E2E，覆盖入口、成功、权限、冲突和会话失效。

4.3 建立 API 防腐层 ​

ts
// packages/refund-contract/src/reasons.ts
import { z } from 'zod'

export const refundReasonSchema = z.object({
  id: z.string().min(1),
  name: z.string().min(1).max(80),
  channels: z.array(z.enum(['web', 'store', 'marketplace'])),
  version: z.number().int().nonnegative(),
  createdAt: z.iso.datetime()
})

export const refundReasonPageSchema = z.object({
  items: z.array(refundReasonSchema),
  total: z.number().int().nonnegative()
})

export type RefundReason = z.infer<typeof refundReasonSchema>

const createResultSchema = z.object({
  reason: refundReasonSchema,
  auditId: z.string().min(1)
})

export async function listRefundReasons() {
  const response = await fetch('/api/refund-reasons', {
    credentials: 'same-origin',
    headers: { Accept: 'application/json' }
  })
  if (!response.ok) throw new Error(`查询退款原因失败：HTTP ${response.status}`)
  return refundReasonPageSchema.parse(await response.json() as unknown)
}

export async function createRefundReason(input: {
  clientCommandId: string
  name: string
  channels: Array<'web' | 'store' | 'marketplace'>
}) {
  const response = await fetch('/api/refund-reasons', {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
      'Content-Type': 'application/json',
      'Idempotency-Key': input.clientCommandId
    },
    body: JSON.stringify(input)
  })
  if (!response.ok) throw new Error(`创建退款原因失败：HTTP ${response.status}`)
  return createResultSchema.parse(await response.json() as unknown)
}

5. 拆解旧系统依赖 ​

5.1 先绘制实际依赖 ​

静态导入图只能看到一部分。还要检索并运行记录：

  • Vue 原型属性、全局 filter/directive/mixin。
  • Vuex 跨 module dispatch 和直接 state 读取。
  • Event Bus 事件生产者、消费者和载荷。
  • Router guard、动态菜单和权限指令。
  • Local/Session Storage key 与格式。
  • UI 库全局样式、Portal 和 Message 单例。
  • Axios interceptor、取消、401 和错误提示。
  • Webpack alias、loader 和环境变量。

每个隐藏依赖指定“保留适配、替换、下沉服务端或删除”的去向，不能在迁移页面时临时发现。

5.2 常见 Vue 2 能力的迁移方向 ​

旧能力迁移方向
Global mixin明确 composable、插件或直接逻辑
Event BusProps/emits、领域服务或有类型瞬时事件
Vuex 大 Store按领域拆 Pinia；服务端状态不永久复制
Filter纯格式化函数或 computed
$http 原型显式 API client 注入/导入
.sync / 旧 v-modelVue 3 modelValue / update:modelValue
UI 库私有 class 覆盖设计 Token、公开组件 API
动态 require.context显式注册或 import.meta.glob

不要机械地把 mixin 每个字段搬进 composable。先确定职责、生命周期和消费者，删除只因历史叠加的能力。

5.3 @vue/compat 的使用边界 ​

Compat build 适合在隔离 fixture 中验证某批共享组件能否按 Vue 3 runtime 运行，并用兼容警告定位旧 API。它不解决 Vue 2-only 插件、全局副作用、Webpack loader 和领域耦合。

项目只允许在标记的迁移包中短期使用，记录警告数、owner 和删除日期；新 Vue 3 应用不以 MODE 2 长期运行。兼容层没有退出条件时，会成为第二套遗留系统。

7. 纵向切片迁移 ​

7.1 从只读查询开始 ​

第一步让内部用户在新页面完成真实查询：URL 条件、运行时响应校验、权限、空态、错误、监控和返回旧系统导航全部可用。新页面和旧页面同时读取相同 API，比较结果集合和字段口径。

影子比较只用于幂等读请求。不要把创建、审核、退款等写命令同时发给两套实现验证“结果一致”，那会制造重复副作用。

7.2 再迁写操作 ​

创建退款原因的命令包含：

ts
type CreateRefundReasonCommand = {
  clientCommandId: string

7.4 删除旧 owner ​

新路由 100% 稳定两周后：

  1. 关闭回退到旧实现的新流量，但保留旧制品固定窗口。
  2. 删除旧 Router 记录、Vuex module、API adapter、事件和页面组件。
  3. 运行依赖和未使用检查，删除只为该路由存在的包。
  4. 更新 owner、运行手册和监控面板。
  5. 回滚窗口结束后从发布路由清单移除 legacy target。

“先留着以防万一”如果没有截止日期，会让任何全局改动继续兼容旧代码。

// gateway.mjs
import { createServer } from 'node:http'
import { readFileSync } from 'node:fs'
import httpProxy from 'http-proxy'

const proxy = httpProxy.createProxyServer({ ws: true })
const targets = {
  legacy: 'http://127.0.0.1:5174',
  next: 'http://127.0.0.1:5175'
}
const reasons = [{
  id: 'reason-1',
  name: '商品破损',
  channels: ['web'],
  version: 1,
  createdAt: '2026-08-01T08:00:00.000Z'
}]
const commandResults = new Map()

function sendJson(response, status, body) {
  response.writeHead(status, { 'Content-Type': 'application/json' })
  response.end(JSON.stringify(body))
}

function readBody(request) {
  return new Promise((resolve, reject) => {
    let body = ''
    request.setEncoding('utf8')
    request.on('data', (chunk) => { body += chunk })
    request.on('end', () => {
      try { resolve(JSON.parse(body)) } catch (error) { reject(error) }
    })
    request.on('error', reject)
  })
}

async function handleApi(request, response) {
  if (request.method === 'GET') {
    sendJson(response, 200, { items: reasons, total: reasons.length })
    return
  }
  if (request.method !== 'POST') {
    sendJson(response, 405, { code: 'method_not_allowed' })
    return
  }

  try {
    const input = await readBody(request)
    const commandId = String(request.headers['idempotency-key'] ?? '')
    if (commandResults.has(commandId)) {
      sendJson(response, 200, commandResults.get(commandId))
      return
    }
    const name = String(input.name ?? '').trim()
    if (!commandId || !name || name.length > 80) {
      sendJson(response, 422, { code: 'invalid_input' })
      return
    }
    if (reasons.some((reason) => reason.name === name)) {
      sendJson(response, 409, { code: 'duplicate_name' })
      return
    }
    const reason = {
      id: `reason-${reasons.length + 1}`,
      name,
      channels: ['web'],
      version: 1,
      createdAt: new Date().toISOString()
    }
    const result = { reason, auditId: `audit-${reasons.length + 1}` }
    reasons.push(reason)
    commandResults.set(commandId, result)
    sendJson(response, 201, result)
  } catch {
    sendJson(response, 400, { code: 'invalid_json' })
  }
}

const server = createServer((request, response) => {
  const url = new URL(request.url ?? '/', 'http://localhost:5173')
  if (url.pathname === '/api/refund-reasons') {
    void handleApi(request, response)
    return
  }
  if (url.pathname.startsWith('/legacy/')) {
    proxy.web(request, response, { target: targets.legacy })
    return
  }
  if (url.pathname.startsWith('/next/')) {
    proxy.web(request, response, { target: targets.next })
    return
  }
  if (url.pathname === '/refund-reasons') {
    const configured = JSON.parse(
      readFileSync(new URL('./route-owners.json', import.meta.url), 'utf8')
    )['refund-reasons']
    const override = url.searchParams.get('implementation')
    const owner = override === 'legacy' || override === 'next'
      ? override
      : configured === 'next' ? 'next' : 'legacy'
    request.url = `/${owner}/refund-reasons${url.search}`
    proxy.web(request, response, { target: targets[owner] })
    return
  }
  response.writeHead(302, { Location: '/refund-reasons' })
  response.end()
})

server.on('upgrade', (request, socket, head) => {
  const target = request.url?.startsWith('/next/')
    ? targets.next
    : targets.legacy
  proxy.ws(request, socket, head, { target })
})

proxy.on('error', (_error, _request, response) => {
  if ('writeHead' in response) {
    response.writeHead(502)
    response.end('migration target unavailable')
  }
})

server.listen(5173, '127.0.0.1', () => {
  console.log('Migration gateway: http://127.0.0.1:5173/refund-reasons')
})

8. 服务端契约与数据演进 ​

8.1 Expand → Migrate → Contract ​

假设新页面需要把 reasonType 从自由字符串变成枚举：

  1. Expand：服务端同时返回旧字符串和新 code，接受两种客户端。
  2. Migrate：回填历史数据，新旧客户端分别验证。
  3. Switch：新页面只发送 code，旧页面仍在兼容窗口。
  4. Contract：旧流量和旧标签页降到阈值后，停止旧写入并删除字段。

前端制品可能在打开的标签页里运行数天，兼容窗口不能只按部署完成时间计算。高风险写接口可以用最低客户端版本拒绝过旧命令，并给出刷新提示。

8.2 错误语义保持稳定 ​

新旧客户端共同依赖稳定状态：400 输入、401 会话、403 权限、404 资源、409 冲突、429 限流和 5xx 服务故障。迁移 adapter 不把所有错误转成 200 {success:false}，否则取消、重试和监控无法共享。

8.3 先兼容再清理 ​

API adapter、字段别名和双版本 Schema 都必须有使用量监控与删除 owner。清理条件填写为“过去 14 天旧字段请求为 0，旧前端 release 活跃会话为 0，回滚窗口结束”，而不是“大家应该升级了”。

10.2 回滚不是清除数据 ​

前端回滚只切实现 owner，不撤销已成功命令。写操作共享同一服务端状态和幂等 ID，回退后旧页面能读取新页面刚写的数据。若新功能写入旧页面无法理解的数据，必须在放量前设计降级展示或延迟开放写入。

10.3 值班和 Runbook ​

Runbook 包含：路由当前 rollout/release、切换权限、监控链接、差异查询、已知兼容窗口、回滚步骤、数据核对和 owner。迁移团队在灰度期承担值班，不能把异常直接丢给原维护者。

11. 安全、性能与开发体验 ​

11.1 遗留应用仍要修高风险漏洞 ​

“反正要下线”不是停止安全更新的理由。旧应用在有生产流量期间继续接受高危依赖修复、Session/CSRF、CSP 和供应链治理。冻结的是新业务扩张，不是安全责任。

无法升级的高风险依赖通过功能隔离、输入限制、CSP、网络边界和缩短下线期限补偿，并记录到期。

11.2 双应用性能成本 ​

按路由整页分流意味着一次页面只下载一套运行时，不会同时加载 Vue 2 和 Vue 3。跨实现跳转会重新加载 HTML 和资源；通过带哈希缓存、稳定导航和 URL 恢复控制成本。不要为了消除一次 reload 立刻引入复杂同页壳。

11.3 开发者路径 ​

新旧系统各有固定 Node/pnpm、启动命令、Mock、测试和 release。共同契约包由兼容构建产出两种目标，或发布不含现代语法的标准 ESM；不能让旧 Webpack 直接编译新应用源码内部。

  • 旧 CI、部署凭证、CDN 路径和监控告警下线。
  • 旧依赖和 registry 权限撤销，漏洞看板不再包含活动资产。
  • 运行手册、owner、培训和支持入口切到新系统。

13. 复盘与选择边界 ​

13.1 哪些做法有效 ​

做法证据
路由级完整切片每批可独立验收和回滚
先建契约与特征测试提前发现 63 个隐藏差异
新旧不共享内存避免双 Store 同步和同页运行时冲突
稳定 cohort + 同源服务端新旧对比可信，写数据互通
每批删除旧 owner依赖和构建成本实际下降

13.2 何时调整策略 ​

证据调整
跨新旧页面跳转严重影响任务引入稳定壳或合并相邻迁移批次
大量共享 UI 难以独立迁移先建设设计 Token/组件适配，不复制旧 class
服务端 API 无法同时兼容优先接口演进，暂停前端放量
单领域高度耦合无法切路由以领域服务/API 边界先解耦，或整体迁移该域
Compat 警告长期不下降停止扩大兼容层，改为独立重写组件

遗留系统渐进迁移的核心是让每一步都可证明、可回退、可删除。新框架只是目标状态的一部分；用户结果、服务端契约、发布路由、兼容窗口和旧代码退出共同决定迁移是否真正完成。
