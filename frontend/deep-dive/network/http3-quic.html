QUIC 与 HTTP/3 ​

作者：codex-gpt-sol-5.6

HTTP/2 已能在一条 Connection 上复用多个 Stream，但 TCP 只向上层提供一条有序 Byte Stream：任何一个 Segment 丢失，后续所有 HTTP/2 Stream 的 Byte 都要等待缺口恢复。QUIC 把可靠、有序交付移到独立 Stream，把 TLS 1.3 Handshake、Loss Recovery 和 Connection Migration 集成在 UDP 之上；HTTP/3 再把 HTTP 语义映射到这些 Stream。

本文先建立 QUIC Connection、Packet、Stream 和 Path 模型，再解释 TLS 1.3、Loss Detection、Migration 与 HTTP/3 Control Stream、QPACK。HTTP Method、Cache 和 Status 等语义与 HTTP/2 相同，不在本文重复；重点是传输层变化带来的收益、剩余共享瓶颈和部署回退。

1. QUIC 解决的传输问题 ​

1.1 TCP + TLS + HTTP/2 的层间限制 ​

传统 HTTPS Stack 可以简化为：

text
HTTP/2 Streams
  -> 一条 TLS Record Sequence
  -> 一条 TCP Ordered Byte Stream
  -> IP Packets
1
2
3
4

HTTP/2 知道 Stream 边界，TCP 不知道。TCP 必须按 Byte Offset 有序交付，丢包恢复发生在所有 H2 Stream 之下。Transport 与 TLS 分开握手也增加首次 Connection 建立的 Round Trip。

1.2 QUIC 的组合模型 ​

text
HTTP/3 Request / Control / QPACK Streams
  -> QUIC Reliable Streams + QUIC Flow Control
  -> QUIC Packets + TLS 1.3 Protection + Loss Recovery
  -> UDP Datagrams
1
2
3
4

QUIC 使用 UDP 获得 User-space Packet 发送入口，但它不是“不可靠版 HTTP”。QUIC 自己实现可靠 Stream、ACK、重传数据、Congestion Control 和 Path Validation。UDP 只提供 Datagram 封装与端口路由。

1.3 标准与实现边界 ​

QUIC Version 1 由 RFC 9000 定义，HTTP/3 由 RFC 9114 定义。浏览器如何与 H2 竞速、何时缓存失败、使用哪种 Congestion Controller，以及 NetLog 如何命名事件都属于实现策略，不是协议保证。

2. Connection、Packet 与 Connection ID ​

2.1 Connection 不再绑定固定四元组 ​

TCP Connection 通常由 Source/Destination IP 与 Port 标识。QUIC 使用 Connection ID（CID）让 Endpoint 在地址或端口改变后继续识别 Connection。Peer 可以签发多个 CID，用于迁移、负载均衡和降低不同 Path 间关联。

CID 不是用户 Session ID，也不应进入应用日志作为身份。它属于 Transport，由 QUIC Stack 管理和轮换。

2.2 Long Header 与 Short Header Packet ​

Connection 建立阶段常见 Long Header Packet：

  • Initial：携带初始 CRYPTO 数据；
  • Handshake：携带后续 Handshake 数据；
  • 0-RTT：恢复 Connection 时的 Early Application Data；
  • Retry：服务器要求 Client 证明 Source Address。

Handshake 后主要使用 Short Header 1-RTT Packet。QUIC 对 Packet Number、部分 Header 和 Payload 提供保护；Initial Key 可由公开信息推导，因此 Initial Encryption 用于协议一致性和防止中间设备依赖明文，不提供 Server Authentication。身份认证来自完成的 TLS Handshake。

2.3 Packet Number Space 与 ACK Range ​

Initial、Handshake 和 Application Data 使用独立 Packet Number Space，避免不同加密阶段互相干扰。Packet Number 单调增加且不复用；接收方用 ACK Frame 表达已收到的 Range 和最大 Packet Number。

ACK 表示 Transport Packet 到达，不表示 HTTP Request 已被业务处理。应用确认仍需要 Response、事务状态或 Idempotency Record。

3. TLS 1.3 与 Connection 建立 ​

3.1 TLS Handshake 集成在 QUIC ​

QUIC 通过 CRYPTO Frame 承载 TLS 1.3 Handshake 数据，而不是先建立 TCP 再在 Byte Stream 上运行 TLS。一个新的 Client 通常能在 1-RTT Handshake 中获得 1-RTT Key 并发送受认证的 Application Data。

QUIC 强制使用 TLS 1.3，但 QUIC Packet Protection 与 TLS Record Layer 并不相同。证书验证、SNI、ALPN h3 和 Cipher Suite 仍属于 TLS 协商。

3.2 0-RTT 的延迟与 Replay 风险 ​

Client 拥有先前 Connection 的 Session Ticket 时，可以在收到新 Server Handshake 前发送 0-RTT Data。Early Data 尚未获得本次连接的新鲜性保证，攻击者可能 Replay，因此：

  • Server 可以拒绝 0-RTT，Client 必须准备重发；
  • 只对可安全 Replay 的 Request 开启；
  • 支付、创建、删除等副作用需要 Idempotency 与 Anti-replay 策略；
  • “GET”也不自动安全，错误设计的 GET 仍可能产生副作用。

0-RTT 是恢复优化，不是每次 H3 请求都少一个 RTT。

3.3 Address Validation 与 Amplification Limit ​

在验证 Client Address 前，服务器能发送的数据量受到 Anti-amplification Limit 约束，避免伪造 Source Address 利用 QUIC 放大攻击。服务器可以使用 Retry Token 验证地址，但 Retry 会增加 Round Trip。

证书链过大或 Initial Packet 丢失也可能放大 Handshake 延迟。部署时应观察 Retry Rate、Handshake Failure 和 Certificate Size，而不是只比较理论 RTT。

4. QUIC Stream 与 Flow Control ​

4.1 Bidirectional 与 Unidirectional Stream ​

QUIC Stream ID 编码 Initiator（Client/Server）和 Direction（Bidirectional/Unidirectional）。每个 Stream 有独立 Byte Offset 和有序交付：

text
STREAM id=0 offset=0  "header..."
STREAM id=4 offset=0  "other request..."
STREAM id=0 offset=20 "body..." FIN
1
2
3

不同 Stream 的 Frame 可以出现在任意 Packet 中。一个 Stream 缺少 Offset 范围时，只阻止该 Stream 向应用连续交付，其他完整 Stream 可继续。

4.2 Connection 与 Stream Flow Control ​

QUIC 使用：

  • MAX_DATA 限制 Connection 可发送总量；
  • MAX_STREAM_DATA 限制单个 Stream；
  • MAX_STREAMS 限制可打开 Stream 数；
  • DATA_BLOCKED / STREAM_DATA_BLOCKED 提供诊断信号。

这是 QUIC Transport Flow Control，不再使用 HTTP/2 WINDOW_UPDATE。Receiver 根据应用消费进度提高 Limit，避免 Peer 无限制占用内存。

4.3 Cancel 与 Partial Reliability 边界 ​

RESET_STREAM 让发送方终止 Stream，STOP_SENDING 请求 Peer 停止发送。已经交给业务系统的副作用仍不保证撤销，语义与 HTTP/2 Cancel 相同。

标准 QUIC Stream 提供可靠传输。QUIC DATAGRAM Extension 可发送不可靠 Message，但普通 HTTP/3 Request/Response Body 不会因为运行在 UDP 上自动变成可丢数据。

5. Loss Detection 与 Congestion Control ​

5.1 丢失的是 Packet，重发的是数据 ​

QUIC 不用相同 Packet Number 重传整个 Packet。Endpoint 根据 ACK 判断 Packet 丢失后，把其中仍需可靠传递的 CRYPTO、STREAM 或其他 Frame Data 放入新 Packet，新 Packet 获得新 Number。

这种设计让 ACK 明确对应一次发送，避免 TCP Retransmission Ambiguity，也允许重组不同优先级的数据。

5.2 Packet Threshold、Time Threshold 与 PTO ​

QUIC Loss Detection 综合：

  • ACK 中更大的 Packet Number，判断旧 Packet 是否超过 Packet Threshold；
  • RTT Estimate 与 Time Threshold；
  • Probe Timeout（PTO），在 ACK 长时间缺失时发送探测。

具体阈值与状态机由 RFC 9002 定义。应用看到的 Request Duration 不能直接反推出 Retransmission 次数，需要 QUIC Metric、qlog 或 Packet Trace。

5.3 Stream 独立不等于资源独立 ​

丢失 Stream A 的 Data 通常不会阻塞 Stream B 已完整到达的数据，这是相对 H2/TCP 的关键改善。但以下资源仍共享：

  • Connection-level Congestion Window；
  • Path Bandwidth 与 RTT；
  • Connection Flow-control Limit；
  • HTTP/3 Control Stream 与 QPACK Dynamic State；
  • Server CPU 和应用后端。

丢包会让 Congestion Controller 降低整条 Path 的发送速率，所有 Stream 吞吐仍可能下降。正确表述是“减少 Transport-level Cross-stream HOL”，不是“彻底消除 HOL”。

6. Connection Migration 与 Path Validation ​

6.1 NAT Rebinding 与网络切换 ​

手机从 Wi-Fi 切到蜂窝网络，或 NAT 映射改变时，UDP 四元组可能变化。只要 Peer 仍能用 CID 识别 Connection，QUIC 可以在新 Path 上继续，而不必必然重建 TLS 与 HTTP 状态。

迁移是否发生取决于 Client、Server、平台和 Network Policy。Server 可以禁用 Active Migration；使用零长度 CID 的连接也无法依靠 CID 跨 Path 识别。

6.2 PATH_CHALLENGE 与 PATH_RESPONSE ​

Endpoint 在新 Path 上发送 PATH_CHALLENGE，Peer 回显 PATH_RESPONSE，以验证地址可达并防止流量被任意重定向。验证前仍受 Amplification Limit。

新 Path 可能有不同 RTT、MTU 和 Congestion State，切换后不保证零抖动。实现需要重新探测 Path，并可能保留或废弃旧 Path。

6.3 CID 轮换与隐私 ​

长期复用同一个 CID 会让观察者关联网络切换前后的 Connection。Peer 通过 NEW_CONNECTION_ID 提供可轮换 CID，并用 RETIRE_CONNECTION_ID 退役旧值。Load Balancer 可能在 CID 中编码路由信息，应按 QUIC-LB 等方案保护可关联信息。

7. HTTP/3 Stream Mapping ​

7.1 Request Stream 与 H3 Frame ​

每个 HTTP Request 通常使用一个 Client-initiated Bidirectional QUIC Stream。该 Stream 内承载 HTTP/3 HEADERS 和 DATA Frame；Frame 使用 QUIC Variable-length Integer 表示 Type 与 Length，不复用 HTTP/2 的 9 Byte Frame Header。

HTTP/2 中的 RST_STREAM、Flow Control 和 Connection Ping 等职责由 QUIC Transport 提供。HTTP/3 只保留 HTTP Mapping 所需 Frame 与规则。

7.2 Control Stream 与 SETTINGS ​

每个 Endpoint 创建一个关键 Unidirectional Control Stream，发送 SETTINGS、GOAWAY、MAX_PUSH_ID 等。Control Stream 必须保持开启；被关闭通常是 Connection Error，因为所有 Request 都依赖其全局状态。

HTTP/3 SETTINGS 与 HTTP/2 字段编号和可用参数不同，Proxy 不能逐 Byte 透传。协议转换要按语义映射。

7.3 Critical Stream 的共享边界 ​

除 Control Stream 外，QPACK Encoder/Decoder Stream 也是 Critical Stream。它们丢失的数据可能影响多个 Header Block，因此 H3 虽让 Request Body Stream 独立，仍存在少量 Connection-level Control Dependency。

Critical Stream 被 Reset 或异常关闭会终止 Connection，不能只重置某个 Request。

8. QPACK Header Compression ​

8.1 为什么不能直接复用 HPACK ​

HPACK Dynamic Table 更新依赖一条 TCP Byte Stream 的全局到达顺序。在 QUIC 中，Request Stream 独立到达；如果 Header Block 引用尚未到达的 Dynamic Entry，Decoder 需要等待。直接套用 HPACK 会重新引入大量 Cross-stream Blocking。

QPACK 将 Table 更新放到专用 Encoder Stream，把 Header Block 放在各 Request Stream，并显式描述依赖。

8.2 Required Insert Count 与 Blocked Stream ​

Header Block 带有 Required Insert Count，表示解码所需的 Dynamic Table 状态。若 Encoder Stream 尚未提供足够 Insert，Request Stream 暂时 Block；Entry 到达后再继续。

Peer 用 SETTINGS_QPACK_BLOCKED_STREAMS 限制允许同时阻塞的 Stream 数，并设置 Dynamic Table Capacity。Encoder 可以改用 Static Table 或 Literal，牺牲压缩率换取不阻塞。

8.3 Encoder 与 Decoder Stream ​

QPACK Encoder Stream 发送 Insert、Duplicate 和 Capacity Update；Decoder Stream 返回 Header Acknowledgement、Stream Cancellation 和 Insert Count Increment。两条 Stream 让 Encoder 知道哪些 Entry 可安全复用或驱逐。

QPACK 控制而非消灭 Header Compression Blocking。动态引用越激进，压缩率可能越高，等待风险与状态成本也越大。

9. Priority、发现与回退 ​

9.1 Extensible Priority 仍是提示 ​

HTTP/3 使用 RFC 9218 的 Urgency 与 Incremental 语义，并可发送 PRIORITY_UPDATE。QUIC Stack、H3 Server 和应用后端仍可因 Congestion、Flow Control 与资源状态调整实际顺序。

Priority 不应承载正确性。低优先级 Request 仍必须最终得到公平处理，不能永久 Starvation。

9.2 Alt-Svc、HTTPS Record 与 ALPN h3 ​

Client 需要先发现 Origin 支持 H3。常见方式包括：

http
Alt-Svc: h3=":443"; ma=86400
1

以及 DNS HTTPS Resource Record。Client 随后用 ALPN h3 建立 QUIC。首次访问可能先走 H2，再根据 Alt-Svc 在后续请求使用 H3；浏览器也可能并行尝试，具体 Race 与缓存策略属于实现。

9.3 UDP 不可达时回退 H2 ​

企业防火墙、NAT 或运营商可能阻止 UDP/443。成熟 Client 会在 H3 失败后回退 H2，并缓存失败一段时间；超时策略必须避免让每次导航都先等待很久。

Edge 支持 H3 不代表 Edge 到 Origin 也用 H3。浏览器 Resource Timing 只能说明 Client 到第一跳的 Negotiated Protocol，后端链路需通过 Proxy 与 Origin Trace 验证。

10.3 DevTools、NetLog 与 qlog ​

Chromium Network 面板开启 Protocol Column，清除 Site Data 后连续 Reload，可观察首次 H2 与后续 H3 的可能切换。chrome://net-export 能记录 QUIC Session、Alt-Svc 与失败原因，但格式为 Chromium 非标准实现。

受控 Server 或 QUIC Library 可输出 qlog，用 qvis 等工具查看 Packet、ACK、Loss、PTO 和 Stream。qlog 可能包含 URL、Header、CID 和 Timing，采集前应脱敏并限制访问。

11. 性能、安全与验证边界 ​

11.1 普通 DevTools Throttling 不等于 Packet Loss ​

DevTools Latency/Throughput Throttling 通常模拟带宽与延迟，不完整模拟 QUIC Packet Loss、Reordering、Path MTU 和 Migration。研究恢复算法需在隔离网络使用 NetEm、硬件网络仿真或 QUIC Test Harness，并记录参数与清理步骤。

11.2 H3 不是所有网络都更快 ​

收益取决于 RTT、Loss、Connection Reuse、0-RTT、安全策略、UDP Path 和实现质量。稳定低延迟网络上的 Warm H2 Connection 可能与 H3 接近；UDP 被限速时 H3 甚至更慢。发布应比较分位数和失败回退，而不是单次本机瀑布图。

11.3 加密不替代应用安全 ​

QUIC 强制 TLS 1.3，保护 Transport Payload 和大部分 Header，但服务器仍要做认证、授权、CSRF、输入校验和速率限制。0-RTT 还要求额外 Replay 审查，Connection Migration 也不能被当成用户 Session 延续证明。

12. 总结 ​

QUIC 把 TLS 1.3、Reliable Stream、ACK、Loss Recovery 与 Migration 集成到 UDP 上，以 CID 维持 Connection 身份，并让不同 Stream 独立有序交付。HTTP/3 把 Request、Control 和 QPACK 映射到这些 Stream：它减少 TCP 造成的 Cross-stream Head-of-line Blocking，却仍共享 Congestion、Flow Control 和 Critical Stream 状态。真正验证 H3 需要同时观察协议发现、ALPN、UDP Path、回退和 Server Trace，而不是只看到“UDP”或一个更短的瀑布图。
