环境、配置与密钥边界 ​

作者：codex-gpt-sol-5.6

前端配置最常见的事故不是“变量没读到”，而是把不同性质的数据混在一起：构建常量被误当成可动态修改的配置，测试 API 地址进入生产包，服务端密钥使用客户端前缀后被打进 JavaScript，或者同一份配置在多个模块中各自解析，最终得到不同默认值。

本文用“何时绑定、由谁读取、是否公开”建立配置边界，并给出构建时配置、运行时公开配置和服务端秘密的完整实现。Vite 的 mode、.env 加载顺序和 import.meta.env API 见Vite 开发与构建体系；Node.js process.env 与 CLI 细节见Process、环境变量与 CLI。

1. 配置分类 ​

1.1 按绑定时机分类 ​

类别何时确定谁能读取示例
源码常量编写/编译时bundle 使用者固定分页上限、协议版本
构建时公开配置执行 build 时下载 bundle 的任何人API 公网地址、公开 DSN、构建版本
部署时公开配置部署或应用启动时下载配置的任何人环境标识、功能开关、租户品牌
服务端运行配置服务进程启动/请求时受信服务端数据库地址、上游服务地址
密钥运行或短期任务执行时最小授权主体私钥、上传 token、数据库密码
用户偏好用户交互后当前用户/设备主题、语言、表格密度

用户偏好不是部署配置，不能用 .env 管理；服务端地址不一定是密钥，但若浏览器无需知道就不应发送；构建时变量一旦进入 bundle，就无法在不重新构建的情况下安全改变。

1.2 环境名不是行为契约 ​

下面的分支把业务行为绑定到模糊环境名：

ts
if (import.meta.env.MODE === 'production') {
  enableNewCheckout()
}
1
2
3

它无法表达 staging 是否启用、灰度用户如何处理，也让本地复现生产行为变得困难。更清楚的是使用具体能力：

ts
if (config.features.newCheckout) {
  enableNewCheckout()
}
1
2
3

development、staging、production 仍可用于日志标签、告警路由和安全策略，但业务开关应是独立、可审计的配置。动态灰度和用户分群属于Feature Flag 与渐进式发布，不应由静态 .env 模拟完整系统。

1.3 公开值与密钥 ​

判断标准不是变量名里有没有 KEY，而是持有它能否获得不应公开的权限：

值是否可放客户端原因与控制
公网 API base URL可以浏览器请求本来就会暴露
OAuth public client ID可以public client 不以 client secret 证明身份
错误采集 DSN通常可以是路由标识，仍需服务端限流和来源控制
地图服务 browser key视供应商设计必须限制域名、API 和额度
OAuth client secret不可以可代表受信客户端换取权限
数据库密码、私钥不可以能直接访问受保护资源
Source Map 上传 token不可以只供 CI 上传制品
第三方服务管理 API token不可以通常具有写入或管理权限

浏览器中的值可以被查看、修改和重放。混淆、Base64、Wasm 或把字符串拆开都不会把它变成秘密。

1.4 配置也是输入数据 ​

环境变量、JSON 文件和远程配置都来自边界外，必须像 API 响应一样验证。TypeScript 的类型声明只约束源码：

ts
interface Config {
  apiBaseUrl: string
}

const config = JSON.parse(raw) as Config
1
2
3
4
5

as Config 不检查缺失字段、类型或 URL。配置应在单一入口完成解析、校验、默认值和冻结，业务模块只接收已验证对象。

2. 配置契约 ​

2.1 字段应表达用途 ​

避免一个模糊字符串承载多个含义：

dotenv
# 模糊：调用地址、代理目标还是 WebSocket 地址？
HOST=https://api.example.com
1
2

改为职责清楚的字段：

dotenv
PUBLIC_API_BASE_URL=https://api.example.com
INTERNAL_ORDER_SERVICE_URL=http://order-service.internal:8080
ORDER_REQUEST_TIMEOUT_MS=5000
1
2
3

公开与内部前缀只是可读性提示，真正暴露规则仍由构建器和部署系统决定。字段文档至少说明类型、是否必填、默认值、公开级别、示例和负责人。

2.2 缺失时失败还是降级 ​

配置缺失策略原因
API base URL启动失败默认到错误后端可能写错数据
订单超时使用经过评审的默认值默认值不改变权限或数据目标
可选统计 DSN关闭统计并记录状态核心业务仍可运行
鉴权公钥/服务端密钥服务启动失败无安全默认值
实验功能开关默认关闭遵循 fail closed

“缺失就用空字符串”会把配置错误推迟到某次用户操作。关键配置应在启动阶段 fail fast，并显示不包含秘密的诊断编号。

2.3 解析字符串值 ​

环境变量天然是字符串。布尔值不能用 Boolean(value)：

ts
Boolean('false') // true
1

应显式解析：

ts
export function parseBoolean(value: string | undefined, fallback: boolean): boolean {
  if (value === undefined) return fallback
  if (value === 'true') return true
  if (value === 'false') return false
  throw new Error(`布尔配置只能是 true 或 false，收到：${value}`)
}

export function parsePositiveInteger(value: string | undefined, name: string): number {
  const result = Number(value)
  if (!Number.isInteger(result) || result <= 0) {
    throw new Error(`${name} 必须是正整数`)
  }
  return result
}

持续时间还应在字段名中写单位，如 _MS、_SECONDS，避免 30 在不同模块被解释为毫秒或秒。

2.4 默认值属于契约 ​

默认值应集中在 schema 或解析函数中：

ts
const DEFAULT_ORDER_TIMEOUT_MS = 5000
1

不要让每个调用点写 config.timeout ?? 3000。不同默认值会使同一环境产生不同行为，也让配置清单无法说明最终值。

安全相关默认值遵循最小权限和 fail closed：功能未声明时关闭、允许来源未声明时拒绝、密钥缺失时停止启动。

2.5 来源与优先级 ​

一条可解释的优先级：

text
代码中的安全默认值
  < 版本控制内的非敏感环境配置
  < 部署平台注入值
  < 受控的单次 CLI override
1
2
3
4

越靠后优先级越高。每一层只覆盖明确字段，并记录最终来源；不要把多个 .env、shell 变量和远程配置无提示合并。

CLI override 适合一次性诊断，不应成为生产长期配置。最终日志可以输出配置版本和非敏感字段，但不能打印 process.env 或整个配置对象。

3. 构建时公开配置 ​

3.1 静态替换 ​

Vite 将 import.meta.env.VITE_* 静态替换到客户端代码：

ts
const apiBaseUrl = import.meta.env.VITE_API_BASE_URL
1

构建后用户可以在 JavaScript 中看到值。它适合：

  • 不同环境可以接受不同 bundle。
  • 值在应用启动前已确定。
  • 值本来就是公开信息。
  • 静态分支有利于删除开发代码。
ts
if (import.meta.env.DEV) {
  installDebugPanel()
}
1
2
3

构建器可以移除生产中不可达的开发分支，但前提是使用它能静态识别的表达式。动态访问 import.meta.env[key] 通常无法可靠替换。

3.2 Mode 不等于部署环境 ​

vite build --mode staging 只决定加载哪组 mode 配置，仍然执行生产构建。MODE === 'staging' 不意味着 DEV === true，也不保证制品一定部署到了 staging。

部署环境应由发布系统记录并注入不可变标识；不要根据域名字符串猜环境，也不要让同一个 production mode 隐式代表多个地区、租户和灰度批次。

3.3 Build per environment ​

为每个环境单独构建：

text
commit 8f3c41a
  ├─ build(staging config)    → artifact A
  └─ build(production config) → artifact B
1
2
3

优点：实现简单、配置可被 Tree Shaking、无需启动请求。代价：staging 验证的不是最终 production 字节，构建次数多，环境之间可能出现依赖或工具漂移。

若采用此模式，生产构建必须复用相同锁文件、Node.js 和构建镜像，并保存配置摘要。不能把“同一 commit”当成“同一制品”。

3.4 客户端密钥泄漏 ​

以下配置是明确错误：

dotenv
VITE_PAYMENT_ADMIN_TOKEN=secret-value
1

任何带 Vite 客户端前缀的值都可能进入 bundle。即使源码只在一个条件分支中引用，构建产物、Source Map 或缓存也可能保留它。

发现泄漏后应：立即撤销/轮换凭据，检查日志和使用记录，移除构建输入，重新发布并清理缓存。仅删除 Git 历史或重新压缩 bundle 不能使已经泄漏的 token 失效。

4. 部署时公开配置 ​

4.1 Build once, deploy many ​

运行时配置把公开值从 JavaScript bundle 中分离：

text
app-[hash].js        所有环境相同
config.json          每个部署目标不同
1
2

优势：staging 验证过的 bundle 可以原样晋级生产，回滚只需选择旧 bundle 和对应配置。代价：启动增加一次读取，必须处理超时、格式错误、缓存和不可用状态；运行时配置也无法让已完成的 Tree Shaking 改变。

4.2 JSON 启动配置 ​

一个公开配置响应：

json
{
  "configVersion": "2026-07-29.1",
  "environment": "production",
  "apiBaseUrl": "https://api.example.com",
  "features": {
    "bulkExport": true
  }
}

响应建议：

http
Content-Type: application/json; charset=utf-8
Cache-Control: no-store
1
2

no-store 最简单但会增加每次启动请求。也可以使用带版本文件名的长期缓存配置，再由短缓存 HTML 指向它；关键是 bundle 与配置的发布和回滚关系明确。

配置应从同源 HTTPS 获取，或严格配置 CORS 和完整性边界。若攻击者能改写 apiBaseUrl，就可能把用户数据发送到恶意服务，因此“配置是公开的”不等于“配置可以不受完整性保护”。

4.3 HTML 注入 ​

服务端也可以在 HTML 中注入公开 JSON，使应用无需额外请求：

html
<script id="app-config" type="application/json">
  {"environment":"production","apiBaseUrl":"https://api.example.com"}
</script>
1
2
3

客户端读取：

ts
const element = document.querySelector('#app-config')
if (!element?.textContent) throw new Error('缺少 app-config')
const rawConfig: unknown = JSON.parse(element.textContent)
1
2
3

服务端序列化 JSON 时必须把 < 转义为 \u003c，避免用户可控值提前闭合 script 元素。不能用字符串拼接生成脚本。HTML 缓存粒度还要与租户和环境一致，否则 CDN 可能把一个租户配置返回给另一个租户。

4.4 配置接口 ​

当配置按租户、用户权限或地区动态变化时，可以由 BFF 返回：

http
GET /api/bootstrap
Authorization: Bearer <session>
1
2

响应只包含当前用户可见的公开能力，不返回上游密钥。用户仍可修改客户端配置，因此服务端授权不能依赖隐藏按钮或客户端 feature flag；每个受保护 API 都要独立鉴权。

5. 运行时校验与注入 ​

5.1 Schema ​

使用 Zod 建立公开配置 schema：

ts
import { z } from 'zod'

export const PublicConfigSchema = z
  .object({
    configVersion: z.string().min(1),
    environment: z.enum(['development', 'staging', 'production']),
    apiBaseUrl: z.string().url(),
    features: z
      .object({
        bulkExport: z.boolean().default(false)
      })
      .strict()
  })
  .strict()

export type PublicConfig = z.infer<typeof PublicConfigSchema>

5.2 加载、验证与冻结 ​

ts
import { PublicConfigSchema, type PublicConfig } from './config-schema'

export class ConfigLoadError extends Error {
  constructor(message: string, options?: ErrorOptions) {
    super(message, options)
    this.name = 'ConfigLoadError'
  }
}

export async function loadPublicConfig(): Promise<PublicConfig> {
  const baseUrl = new URL(import.meta.env.BASE_URL, window.location.origin)
  const configUrl = new URL('config.json', baseUrl)

  let response: Response
  try {
    response = await fetch(configUrl, {
      cache: 'no-store',
      credentials: 'same-origin'
    })
  } catch (error) {
    throw new ConfigLoadError('无法连接配置服务', { cause: error })
  }

  if (!response.ok) {
    throw new ConfigLoadError(`配置请求失败：HTTP ${response.status}`)
  }

  let rawConfig: unknown
  try {
    rawConfig = await response.json()
  } catch (error) {
    throw new ConfigLoadError('配置不是有效 JSON', { cause: error })
  }

  const result = PublicConfigSchema.safeParse(rawConfig)
  if (!result.success) {
    throw new ConfigLoadError('配置格式无效', { cause: result.error })
  }

  const apiUrl = new URL(result.data.apiBaseUrl)
  if (result.data.environment === 'production' && apiUrl.protocol !== 'https:') {
    throw new ConfigLoadError('生产 API 必须使用 HTTPS')
  }

  return Object.freeze({
    ...result.data,
    features: Object.freeze(result.data.features)
  })
}

5.3 依赖注入 ​

应用入口先加载配置，再创建依赖：

ts
import { startApp } from './app'
import { ConfigLoadError, loadPublicConfig } from './load-config'

const root = document.querySelector<HTMLElement>('#app')
if (!root) throw new Error('缺少 #app')

try {
  const config = await loadPublicConfig()
  startApp(root, config)
} catch (error) {
  const errorId = crypto.randomUUID()
  console.error('应用配置加载失败', { errorId, error })

  root.textContent =
    error instanceof ConfigLoadError
      ? `应用暂时无法启动，错误编号：${errorId}`
      : `应用初始化失败，错误编号：${errorId}`
}

6.1 服务端启动校验 ​

if (!result.success) {

    field: path.join('.'),
    message

若 schema 使用 .strict() 直接解析完整 process.env，操作系统提供的大量其他变量会被拒绝；服务端应挑选需要字段或允许 passthrough，再只导出白名单配置。

6.2 Secret Manager 与环境注入 ​

生产秘密应来自部署平台或 Secret Manager：

text
Secret Manager
  → 工作负载身份鉴权
  → 启动时注入环境/挂载文件/短期凭据
  → 应用只读取所需秘密
1
2
3
4

优先使用工作负载身份和短期凭据，避免长期静态 access key。应用账号只授予所需路径和操作；staging 与 production 使用不同秘密和权限边界。

环境变量便于注入，但可能出现在进程诊断、崩溃转储或误打印中；挂载文件也需限制文件权限和备份范围。载体不同不改变最小权限、审计和轮换要求。

6.3 CI 密钥 ​

常见 CI 秘密：registry 发布 token、Source Map 上传 token、部署凭据。安全原则：

  • 只在需要的 job/step 暴露。
  • 不向来自 fork 的不可信 PR 注入。
  • 不拼进客户端变量、构建参数或 artifact 文件名。
  • 命令关闭调试回显，日志系统启用掩码但不依赖掩码兜底。
  • 优先使用 OIDC 换取短期云凭据。
  • 受保护环境需要审批和分支限制。

构建缓存也可能保存环境影响的输出。含秘密的任务应证明秘密不会进入产物，或关闭共享缓存并隔离 runner。

6.4 轮换与撤销 ​

秘密生命周期：

  1. 创建并记录 owner、用途、权限和过期时间。
  2. 通过受控引用注入，不在源码复制值。
  3. 监测使用和异常访问。
  4. 先部署同时接受新旧凭据的过渡版本（若协议支持）。
  5. 切换调用方到新凭据。
  6. 撤销旧凭据并验证无调用。

泄漏时优先撤销，而不是先花时间清理 Git 历史。历史清理减少后续误用，但不能收回已经复制的秘密。

7.3 Secret scanning ​

仓库和 CI 应使用 secret scanner 检查已知 token 格式与高熵字符串，但扫描器会误报，也无法识别所有业务密钥。配合：

  • provider push protection。
  • 自定义内部 token pattern。
  • 提交前检查和服务端全历史扫描。
  • 误报 allowlist 的原因、范围和过期时间。

扫描通过不能证明没有秘密；运行时权限、轮换和日志控制仍是必要防线。

9. 常见失败与排查 ​

9.1 配置改了但页面没变 ​

先判断它属于构建时还是运行时：

现象原因处理
修改 .env 后 dev 不变开发服务器启动时加载重启并核对 mode
改部署变量后 bundle 不变值在 build 时已静态替换重新构建或改用运行时配置
config.json 更新后仍旧浏览器/CDN 缓存修正缓存与版本策略
某模块仍用旧值模块自行缓存或重复读取统一启动注入对象

9.2 环境之间行为漂移 ​

保存每次发布的：bundle hash、config version、非敏感配置摘要、release、部署目标。比较时区分“代码不同”和“配置不同”。禁止在服务器上手工编辑一份无人记录的 .env 后重启。

9.3 错误日志泄漏秘密 ​

常见危险代码：

ts
console.error('invalid config', process.env)
1

改为只输出校验失败字段。日志平台还应配置敏感字段过滤，但应用侧不发送秘密是第一道防线。

9.4 配置接口成为单点故障 ​

运行时配置失败会阻止启动。可选方案：

  • 与 HTML 同源部署并原子发布。
  • 使用短超时和有限重试。
  • 保存带版本的上一份公开配置，但只在安全允许时回退。
  • 对配置请求建立可用性和延迟监控。

不能盲目回退会影响权限、API 目标或数据隔离的配置。此类字段宁可停止启动。

9.5 以客户端开关保护权限 ​

用户可以在 DevTools 修改配置、调用隐藏 API。feature flag 只控制体验和发布节奏，权限始终由服务端根据会话与资源重新判断。

10. 选择与验收 ​

10.1 方案选择 ​

约束推荐方式代价
每个环境允许独立 artifact构建时公开配置需要分别构建和验证
同一 artifact 晋级多环境config.json 或 HTML 注入启动校验、缓存和失败处理
配置按用户/租户变化受鉴权 bootstrap API服务端容量与缓存隔离
值具有服务端权限BFF/服务端 secret需要服务端调用边界
动态灰度与紧急关闭专用 Feature Flag 服务SDK、治理和可用性成本

10.2 发布验收 ​

  1. 每个配置字段有类型、可见性、owner 和缺失策略。
  2. 客户端公开配置经过运行时 schema 校验。
  3. 生产 API 地址使用 HTTPS，并满足允许的 origin 策略。
  4. bundle、Source Map、缓存和日志中没有服务端密钥。
  5. CI secret 不会进入不可信 PR 或共享缓存。
  6. release 同时记录代码版本与 config version。
  7. 配置缺失、格式错误和接口不可用都有可观察失败界面。
  8. 轮换秘密无需修改源码，旧秘密能被撤销。

配置治理的核心不是统一使用 .env，而是让每个值在正确时间绑定、只跨越必要的信任边界，并在第一次使用前完成验证。客户端只有公开配置；真正的秘密必须留在受控服务端或短期 CI 任务中。
