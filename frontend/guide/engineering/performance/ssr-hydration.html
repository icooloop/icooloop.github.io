SSR 与 Hydration 性能 ​

作者：codex-gpt-sol-5.6

服务端渲染（SSR）可以让浏览器更早获得可解析 HTML，但页面可见不代表已经可操作。客户端仍要下载、解析和执行 JavaScript，再把事件、状态与服务端 DOM 连接起来；这个接管过程通常称为 Hydration。

本文以框架无关的交付流水线说明 SSR、流式输出、状态交接、Hydration 成本与不匹配诊断。React 19 和 Vue 3 的组件级优化与 DevTools 使用由后续项目诊断文章负责。

1. SSR 与 Hydration 的阶段模型 ​

1.1 从导航到可交互 ​

text
导航开始
  → CDN/服务端收到请求
  → 获取数据并生成 HTML
  → 首字节与 HTML 流到达
  → 浏览器解析并绘制服务端内容
  → 发现并下载客户端模块
  → 解析/执行 JavaScript
  → Hydration 匹配 DOM、恢复状态和事件
  → 关键交互可用

SSR 主要改变 HTML 与内容出现的时机；Hydration 仍消耗网络、JavaScript 和主线程。若服务端响应慢或客户端包很大，SSR 可能只把等待从“空白页面”移动成“看得见但点不动”。

1.2 需要分别观察的指标 ​

阶段证据说明
服务端开始回应TTFB、Server-Timing包含网络与服务端阶段
主要内容出现LCPSSR HTML、资源发现与渲染共同决定
客户端代码就绪模块请求、解析/执行任务不能只看传输大小
根边界接管自定义 Hydration ready mark由框架生命周期确认，不是入口函数返回
首次交互INP、业务交互 measure关注 Hydration 与用户输入竞争
后续边界接管每个 Island/Suspense 边界 mark根完成不代表全部懒边界完成

一次 Lighthouse 总分无法说明等待发生在哪个阶段。

1.3 Hydration 不是浏览器标准 API ​

浏览器负责解析 HTML 和执行脚本；如何把客户端组件树与现有 DOM 对齐，由 React、Vue 等框架实现。不同框架对事件委托、异步边界、不匹配恢复和优先级的处理不同。

通用不变量是：服务端输出、客户端首次状态和 DOM 结构必须能确定性对应；交互只有在相关事件与状态接管后才真正可用。

2. 渲染模式与 Hydration 范围 ​

2.1 CSR、SSR 与 SSG ​

模式HTML 生成位置客户端接管主要权衡
CSR浏览器客户端从空容器创建服务端简单，首屏依赖 JS/接口链
SSR每次请求服务端通常需要 Hydration个性化与首屏 HTML，增加服务成本和确定性要求
SSG构建时可选 HydrationTTFB 稳定，内容更新依赖重新生成/增量策略
纯 HTML/渐进增强服务端或构建时只接管少量行为客户端成本低，复杂交互需显式设计

选择不由“SEO”一个条件决定。内部应用也可能从更快可见内容受益；公开内容页若全量 Hydrate 巨大组件树，也可能获得良好 LCP 却有较差 INP。

2.2 全量、选择性与 Islands ​

  • 全量 Hydration：客户端接管完整应用树，模型统一但成本与树规模相关。
  • 选择性/并发 Hydration：框架按可见性、交互或优先级安排边界。
  • Islands：大部分 HTML 静态，只让独立交互区域加载客户端代码。
  • 渐进增强：HTML 表单和链接先可用，JavaScript 再增强体验。

这些术语在框架中的实现不同。评估时应记录“下载多少客户端代码、创建多少组件实例、哪一刻哪个操作可用”，而不是只看方案名称。

2.3 减少 Hydration 比加速 Hydration 更直接 ​

法律说明、帮助文本和静态价格表若无需客户端状态，不必为了统一组件模型全部接管。先删除不需要的客户端边界，再讨论 memo、调度或延迟策略。

Server-Timing 会暴露给客户端和开发工具，只能使用低敏感、低基数名称，不能写 SQL、用户 ID、内部主机或凭据。

3.2 流式 SSR ​

流式输出可以先发送文档骨架和已就绪内容，后续异步边界再到达。它能缩短内容发现时间，但有这些前提：

  • 首块包含完整有效的文档结构和关键资源引用。
  • 代理、压缩和 CDN 没有把小块缓冲到整个响应结束。
  • 后续块失败时页面有稳定回退。
  • 客户端能按框架协议接管流式边界。
  • 服务端处理背压和断开连接，不继续浪费计算。

首字节很快但主内容被放在最后一个流式块中，LCP 仍不会改善。

3.3 避免服务端数据瀑布 ​

服务端组件或 loader 也会形成串行依赖：

text
读取会话 → 读取订单 → 读取导出权限 → 开始 render
1

若订单与权限只依赖同一个已知用户，可以在会话完成后并行；若权限依赖订单所属租户，则必须串行。优化需要依据数据依赖，而不是机械 Promise.all。

4. 确定性的状态交接 ​

4.1 服务端与客户端共享同一快照 ​

Hydration 的客户端首次 render 必须使用生成 HTML 时的同一数据快照。客户端启动后立刻重新请求并用新数据 Hydrate，可能出现文本、数量和元素树不匹配。

状态交接至少记录：

  • Schema/version。
  • 生成该 HTML 的数据版本或时间点。
  • 用户可见初始状态。
  • Locale、timezone、实验与权限等会影响输出的上下文。
  • 客户端何时允许重新验证新数据。

4.2 安全序列化 ​

把 JSON.stringify(data) 直接插进 <script> 不安全。即使脚本类型是 application/json，HTML 解析器仍会识别 </script>。至少要转义 <，并通过 textContent 读取：

ts
export function serializeForHtml(value: unknown): string {
  return JSON.stringify(value)
    .replaceAll('<', '\\u003c')
    .replaceAll('\u2028', '\\u2028')
    .replaceAll('\u2029', '\\u2029')
}

状态中不能包含访问令牌、服务端密钥或用户不应看到的字段。HTML 已经发送到浏览器，“脚本不执行”不构成保密边界。

4.3 控制状态体积 ​

重复把完整实体同时放进 HTML 列表和 JSON 状态会增加响应、解析与内存。只序列化客户端首次交互需要的字段，并用 ID/规范化结构减少重复；大历史数据按交互加载。

状态 JSON 仍是 HTML 传输的一部分，应计入文档资源预算。

5. Hydration 不匹配 ​

5.1 常见非确定输入 ​

来源服务端与客户端为何不同修正
Date.now()执行时刻不同服务端生成固定时间并交接
Math.random()随机序列不同交接生成结果或稳定 seed
Locale/timezone服务器环境与浏览器不同显式传入并使用同一格式规则
viewport/media query服务端不知道真实视口使用响应式 CSS，或 Hydration 后增强
Cookie/权限CDN 与客户端会话视图不同正确缓存键并交接权限快照
异步数据Hydration 前数据已刷新先 Hydrate 快照，再受控重新验证
浏览器修正 HTML无效嵌套被解析器改写输出合法 HTML 并做渲染测试
第三方脚本/扩展Hydration 前修改 DOM延后第三方或隔离挂载区域

5.2 不匹配的后果不统一 ​

框架可能警告、局部修复、丢弃节点或重新创建子树，具体行为取决于框架、版本和不匹配位置。不能把“页面最后看起来一样”当作无成本：恢复会增加主线程工作，也可能丢失用户在接管前输入的内容。

5.3 谨慎使用忽略机制 ​

React 19 的 suppressHydrationWarning 只作用于元素的一级内容，是用于少量不可避免差异的逃生口。Vue 3.5+ 的 data-allow-mismatch 可以把允许范围限定为 text、children、class、style 或 attribute；较早的 Vue 3 版本没有这个能力。两者都不会修复结构或状态问题，不应加在根节点隐藏所有警告。

优先让输出确定；确需忽略时记录字段、范围、用户影响和回归测试。

6. Hydration 调度与交互 ​

6.1 主线程成本 ​

客户端接管通常包括模块解析/执行、创建组件/响应式结构、匹配节点、注册事件和运行生命周期。即使复用了 DOM，也不等于没有 CPU 成本。

在中低端设备上，大量同步 Hydration 可能形成 Long Task，用户点击后输入先排队。应在 Performance 中把脚本执行、Hydration 标记、事件和下一帧放在同一时间线观察。

6.2 延迟非关键边界 ​

地图、富文本预览、评论区等首屏非关键交互可以按可见、空闲或首次意图接管。延迟前必须回答：

  • 接管前内容能否阅读、链接/表单能否工作？
  • 用户首次点击是否会丢失，框架是否支持事件重放？
  • 边界代码何时获取，是否把延迟变成首次操作卡顿？
  • 页面离开时待处理任务能否取消？

requestIdleCallback 不是“用户永远不会操作”的保证，而且兼容性有限；关键接管不能只依赖空闲回调。

6.3 分块的代价 ​

边界越细，初始工作越容易分散，但会增加模块、状态协议、调度与错误恢复复杂度。应根据交互优先级和 Profile 划分，而不是把每个组件都变成独立 Island。

7. 测量 Hydration ​

7.1 入口返回不代表完成 ​

调用框架的 hydrate() / hydrateRoot() / mount() 后立即记录结束，只能测到“调度 Hydration”的同步耗时。并发框架可能稍后 commit，流式边界可能更晚完成。

正确完成点应来自根组件 commit/mounted 生命周期，关键懒边界再各自标记。

7.2 通用标记助手 ​

ts
// src/performance/hydration-marks.ts
const startMark = 'app-hydration:start'
const readyMark = 'app-hydration:root-ready'
const measureName = 'app-hydration-to-root-ready'

export function markHydrationStart(): void {
  performance.mark(startMark)
}

export function markHydrationRootReady(): void {
  if (performance.getEntriesByName(readyMark).length > 0) return
  performance.mark(readyMark)
  performance.measure(measureName, startMark, readyMark)
}

7.3 读取并关联导航阶段 ​

ts
export function readHydrationDiagnostics() {
  const navigation = performance.getEntriesByType('navigation')[0] as
    | PerformanceNavigationTiming
    | undefined
  const hydration = performance.getEntriesByName(
    'app-hydration-to-root-ready'
  ).at(-1)

  if (!navigation || !hydration) return undefined

  return {
    ttfb: navigation.responseStart - navigation.startTime,
    domContentLoaded:
      navigation.domContentLoadedEventEnd - navigation.startTime,
    hydrationStart: hydration.startTime,
    hydrationDuration: hydration.duration,
    rootReady: hydration.startTime + hydration.duration
  }
}

8. 完整示例：确定性订单页面 ​

下面使用 Node.js 输出服务端 HTML，再用浏览器模块接管刷新按钮。它是可运行的渐进增强示例，不实现某个框架的 Virtual DOM Hydration；真实框架应复用相同的序列化、安全和确定性边界。

8.1 服务端输出 ​

ts
// server.mts
import { readFile } from 'node:fs/promises'
import { createServer } from 'node:http'

interface Order {
  id: string
  customerName: string
}

interface Bootstrap {
  schemaVersion: 1
  renderVersion: string
  generatedAt: string
  orders: Order[]
}

const server = createServer(async (request, response) => {
  if (request.url === '/client.js') {
    try {
      const script = await readFile(new URL('./public/client.js', import.meta.url))
      response.writeHead(200, {
        'Content-Type': 'text/javascript; charset=utf-8',
        'Cache-Control': 'no-cache'
      })
      response.end(script)
    } catch {
      response.writeHead(404).end('client.js not found')
    }
    return
  }

  const bootstrap: Bootstrap = {
    schemaVersion: 1,
    renderVersion: 'orders-v18',
    generatedAt: '2026-07-29T10:00:00.000Z',
    orders: [
      { id: 'o-100', customerName: '林晓' },
      { id: 'o-101', customerName: '周宁' }
    ]
  }

  const html = renderPage(bootstrap)
  response.writeHead(200, {
    'Content-Type': 'text/html; charset=utf-8',
    'Cache-Control': 'no-cache',
    'Server-Timing': 'data;dur=18, render;dur=2'
  })
  response.end(html)
})

server.listen(4173, '127.0.0.1', () => {
  console.log('http://127.0.0.1:4173')
})

function renderPage(state: Bootstrap): string {
  const items = state.orders
    .map((order) => `<li>${escapeHtml(order.id)} ${escapeHtml(order.customerName)}</li>`)
    .join('')

  return `<!doctype html>
<html lang="zh-CN">
  <head><meta charset="UTF-8"><title>订单</title></head>
  <body>
    <main id="app" data-render-version="${escapeHtml(state.renderVersion)}">
      <h1>订单</h1>
      <p id="generated-at">生成于 ${escapeHtml(state.generatedAt)}</p>
      <ul id="orders">${items}</ul>
      <button id="refresh" type="button">刷新生成时间</button>
    </main>
    <script id="bootstrap" type="application/json">${serializeForHtml(state)}</script>
    <script type="module" src="/client.js"></script>
  </body>
</html>`
}

function escapeHtml(value: string): string {
  return value
    .replaceAll('&', '&amp;')
    .replaceAll('<', '&lt;')
    .replaceAll('>', '&gt;')
    .replaceAll('"', '&quot;')
    .replaceAll("'", '&#39;')
}

function serializeForHtml(value: unknown): string {
  return JSON.stringify(value)
    .replaceAll('<', '\\u003c')
    .replaceAll('\u2028', '\\u2028')
    .replaceAll('\u2029', '\\u2029')
}

function readBootstrap(): Bootstrap {
  const node = required<HTMLScriptElement>('#bootstrap')
  const value: unknown = JSON.parse(node.textContent ?? '')
  if (
    !isRecord(value) ||
    value.schemaVersion !== 1 ||
    typeof value.renderVersion !== 'string' ||
    typeof value.generatedAt !== 'string'
  ) {
    throw new Error('INVALID_BOOTSTRAP')
  }

  return {
    schemaVersion: 1,
    renderVersion: value.renderVersion,
    generatedAt: value.generatedAt,
    orders: parseOrders(value.orders)
  }
}

function parseOrders(value: unknown): Bootstrap['orders'] {
  if (!Array.isArray(value)) throw new Error('INVALID_BOOTSTRAP')

  return value.map((item) => {
    if (
      !isRecord(item) ||
      typeof item.id !== 'string' ||
      typeof item.customerName !== 'string'
    ) {
      throw new Error('INVALID_BOOTSTRAP')
    }
    return { id: item.id, customerName: item.customerName }
  })
}

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null
}

function required<T extends Element>(selector: string): T {
  const element = document.querySelector<T>(selector)
  if (!element) throw new Error(`Missing element: ${selector}`)
  return element
}

9. 诊断顺序 ​

9.1 HTML 早但内容晚 ​

查看 HTML 首块是否包含目标内容和 LCP 资源 URL。若只有空 shell 或 skeleton，SSR 名称本身不会改善主要内容。再检查服务端数据瀑布和流式块到达时间。

9.2 内容早但交互晚 ​

在 Performance 中检查客户端模块请求、Parse/Evaluate、长任务、Hydration marks 和首次输入。若主线程被大量组件接管占满，减少 Hydration 范围通常比给每个组件加缓存更有效。

9.3 只在生产 mismatch ​

核对 CDN 缓存键、Locale/timezone、实验配置、真实第三方脚本、压缩/HTML 重写和生产数据版本。开发环境数据固定且没有 CDN，往往无法暴露这些差异。

## PERF-261：订单页可见但首次点击无响应

- 现象：LCP p75 2.1 s；首次筛选 INP p75 610 ms。
- 设备分群：主要集中在 4 GB 内存 Android 与冷导航。
- Timeline：客户端入口 186 KB；根 Hydration 单个 Long Task 540 ms。
- 组件范围：首屏只有筛选与前 20 行可交互，但 5000 行详情全部 Hydrate。
- 改动：服务端输出分页；只 Hydrate 当前 20 行与筛选区；详情按展开接管。
- 实验室：root-ready 690 → 224 ms；首次筛选 580 → 176 ms。
- 相邻指标：LCP 2.0 s，CLS 0.03，均未退化。
- 限制：详情首次展开增加 54 ms 模块等待，按钮显示 pending 状态。
- 发布后：移动端 INP p75 610 → 198 ms，样本 18,420。

10. 常见误区与限制 ​

误区后果修正
SSR 一定更快服务端和 Hydration 成本可能更高分阶段测 TTFB、LCP、root-ready、INP
HTML 出现等于可交互用户点击可能在接管前丢失/排队定义关键交互 ready 指标
调用 hydrate 后立刻 mark 完成只测到调度入口从真实 commit/mounted 标记
客户端立即用新数据 Hydrate与服务端快照不匹配先复用快照，再重新验证
用 ignore/suppress 清空警告结构与状态错误仍存在只允许已知叶子差异
所有组件都做 Island模块、状态和错误边界过度复杂按交互优先级划分
只压缩状态 JSON重复实体和敏感字段仍存在最小化、规范化并安全序列化
流式首字节快就宣布成功主内容块和客户端代码仍可能很晚观察 LCP 资源与每个边界到达

SSR 还增加服务器容量、缓存和故障面。高流量页面必须把渲染 CPU、并发、超时和回源成本纳入容量验证，不能只看浏览器指标。

11. SSR 与 Hydration 检查表 ​

  • 是否画出 TTFB、HTML、LCP、客户端执行、根接管和关键边界时间线？
  • SSR/SSG/CSR/Island 的选择是否对应内容更新与交互需求？
  • 服务端首块是否包含真正关键内容和资源引用？
  • 客户端首次 render 是否复用同一数据、Locale、timezone、权限和实验快照？
  • Bootstrap 是否版本化、最小化、安全转义且不含敏感字段？
  • mismatch 是否按时间、随机、HTML、缓存、第三方和数据版本分类？
  • Hydration ready 是否来自实际 commit/mounted，而非入口返回？
  • 非关键边界延迟后，首次交互是否仍可恢复且有反馈？
  • 优化是否同时验证 TTFB、LCP、CLS、INP 和服务器成本？
