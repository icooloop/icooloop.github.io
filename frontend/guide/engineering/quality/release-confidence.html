发布门禁与质量度量 ​

作者：codex-gpt-sol-5.6

发布门禁把需求、评审、测试、构建、安全检查和运行指标转换成可追溯的放行条件。它的目标不是保证“零缺陷”，而是在当前变更风险下，确认关键证据已经针对同一提交通过，并让例外决策有负责人、期限和补偿措施。

本文关注门禁策略、证据绑定、例外和质量度量。CI/CD 负责执行任务和交付制品，Feature Flag、灰度与回滚负责控制生产暴露；本文只决定进入下一阶段需要哪些证据，不重复它们的实现。

1. 发布信心的组成与边界 ​

1.1 信心来自证据链 ​

一条“所有检查都是绿色”的状态还不足以放行。有效证据至少回答：

  • 验证了什么：测试、构建、扫描或人工评审的具体对象。
  • 对应哪个版本：源代码提交、构建制品摘要和配置版本。
  • 何时完成：结果是否已经过期，依赖和环境是否发生变化。
  • 在哪里完成：本地、CI、预发布还是生产探针。
  • 谁负责：检查所有者、批准人和失败处置人。
  • 结果在哪里：可访问的日志、报告、Trace 或审批记录。

测试数量或覆盖率本身不是信心。证据必须能追溯到已声明的风险和当前发布对象。

1.2 门禁、流水线与发布控制 ​

能力负责的问题本文边界
CI/CD 与部署流水线如何构建、测试、传递制品和部署提供检查结果，不在本文展开工作流语法
发布门禁当前证据是否满足进入下一阶段的策略本文主体
Feature Flag 与渐进式发布哪些用户何时看到新版本，如何暂停和回退消费门禁结论，不在本文展开开关实现
可观测性与 SLO上线后系统实际表现是否可接受提供运行证据，不替代发布前检查

同一个检查可以由流水线执行、被门禁读取，并在灰度阶段再次运行，但三个职责不应混成一段难以审计的脚本。

1.3 门禁不是零风险承诺 ​

任何测试环境都无法覆盖所有真实流量、数据和依赖状态。门禁作出的是风险接受决定：在已知约束下，证据是否足以进入下一阶段；未知风险则通过小范围发布、监控和可回退设计控制。

2. 门禁类型与证据模型 ​

2.1 硬门禁、条件门禁与观察项 ​

  • 硬门禁：不通过就不能继续，例如当前提交构建失败、关键契约不兼容。
  • 条件门禁：由变更风险触发，例如修改认证目录必须经过安全负责人审批。
  • 观察项：记录趋势但暂不阻塞，例如处于治理初期的低优先级可访问性警告。

不要把所有指标直接设成硬门禁。规则不稳定、误报高或没有明确修复所有者时，强制阻塞只会诱发绕过。

2.2 每条证据绑定不可变对象 ​

最小证据记录应包含：

ts
interface CheckEvidence {
  id: string
  status: 'passed' | 'failed' | 'cancelled'
  sourceSha: string
  artifactDigest?: `sha256:${string}`
  completedAt: string
  detailsUrl: string
}

2.3 证据有有效期和适用范围 ​

类型检查通常只要源码提交未变就仍有效；动态依赖漏洞结果、预发布 E2E 和人工审批则可能随时间或环境变化而过期。策略需要声明最大年龄、目标环境和风险范围，不能永久复用一次通过。

3. 按风险组织门禁 ​

3.1 变更风险分级 ​

下面是一份可执行讨论的分级，而不是只写“高、中、低”：

等级触发示例额外证据
低文档、无行为的内部重命名、已证明不进入产物的测试改动静态检查、受影响测试、构建
中普通页面功能、接口调用、共享组件、依赖升级组件/集成测试、契约检查、关键 E2E、回退说明
高登录授权、支付、隐私数据、公共 SDK、全局路由、不可逆迁移领域审批、安全/隐私评审、完整契约与 E2E、演练过的回退、渐进发布

风险不能只由作者手工选择。路径规则、依赖变化、权限声明和 PR 问卷可以自动提升等级；降级必须由有权限的负责人记录理由。

3.2 各阶段证明不同事实 ​

阶段主要证据放行结果
合并前Lint、类型、单元/组件/集成、评审、依赖规则允许进入主干
发布候选不可变构建、契约验证、关键 E2E、视觉差异、制品扫描允许部署目标环境
渐进发布错误率、延迟、业务成功率和样本量扩大、暂停或回退流量
发布后SLO、逃逸缺陷、支持反馈和复盘项关闭变更窗口或进入修复

把所有检查都放在 PR 阶段会拖慢反馈，也无法证明部署配置；把所有检查推迟到发布阶段又会让低成本问题太晚暴露。

3.3 一份填写完成的风险判断 ​

5. 可运行的门禁判定器 ​

5.1 实现提交、状态和时效检查 ​

ts
// scripts/evaluate-release.mts
import { readFile } from 'node:fs/promises'

interface Requirement {
  id: string
  maxAgeMinutes: number
}

interface ReleasePolicy {
  version: number
  releaseId: string
  commitSha: string
  environment: string
  riskLevel: 'low' | 'medium' | 'high'
  requiredChecks: Requirement[]
}

interface CheckEvidence {
  id: string
  status: 'passed' | 'failed' | 'cancelled'
  sourceSha: string
  completedAt: string
  detailsUrl: string
}

interface EvidenceFile {
  releaseId: string
  checks: CheckEvidence[]
}

const [policyPath, evidencePath] = process.argv.slice(2)
if (!policyPath || !evidencePath) {
  throw new Error('Usage: evaluate-release <policy.json> <evidence.json>')
}

const [policyValue, evidenceValue] = await Promise.all([
  readJson(policyPath),
  readJson(evidencePath)
])
const policy = parseReleasePolicy(policyValue)
const evidence = parseEvidenceFile(evidenceValue)

const evaluatedAt = new Date(process.env.EVALUATED_AT ?? Date.now())
if (Number.isNaN(evaluatedAt.getTime())) throw new Error('Invalid EVALUATED_AT')

const failures: string[] = []
if (policy.releaseId !== evidence.releaseId) {
  failures.push(`release mismatch: ${evidence.releaseId}`)
}

const checksById = new Map(evidence.checks.map((check) => [check.id, check]))

for (const requirement of policy.requiredChecks) {
  const check = checksById.get(requirement.id)
  if (!check) {
    failures.push(`${requirement.id}: missing`)
    continue
  }

  if (check.status !== 'passed') {
    failures.push(`${requirement.id}: ${check.status}`)
  }
  if (check.sourceSha !== policy.commitSha) {
    failures.push(`${requirement.id}: belongs to ${check.sourceSha}`)
  }

  const completedAt = new Date(check.completedAt)
  const ageMinutes = (evaluatedAt.getTime() - completedAt.getTime()) / 60_000
  if (Number.isNaN(ageMinutes) || ageMinutes < 0) {
    failures.push(`${requirement.id}: invalid completion time`)
  } else if (ageMinutes > requirement.maxAgeMinutes) {
    failures.push(`${requirement.id}: expired at ${ageMinutes.toFixed(1)} minutes`)
  }
}

const decision = failures.length === 0 ? 'allowed' : 'blocked'
console.log(JSON.stringify({
  decision,
  releaseId: policy.releaseId,
  commitSha: policy.commitSha,
  evaluatedAt: evaluatedAt.toISOString(),
  failures
}, null, 2))

if (failures.length > 0) process.exitCode = 1

async function readJson(filePath: string): Promise<unknown> {
  return JSON.parse(await readFile(filePath, 'utf8'))
}

function parseReleasePolicy(value: unknown): ReleasePolicy {
  if (!isRecord(value) || !Array.isArray(value.requiredChecks)) {
    throw new Error('Invalid release policy')
  }

  const riskLevel = value.riskLevel
  const requiredChecks = value.requiredChecks
  if (
    value.version !== 1 ||
    typeof value.releaseId !== 'string' ||
    typeof value.commitSha !== 'string' ||
    typeof value.environment !== 'string' ||
    (riskLevel !== 'low' && riskLevel !== 'medium' && riskLevel !== 'high') ||
    !requiredChecks.every(isRequirement) ||
    !hasUniqueIds(requiredChecks)
  ) {
    throw new Error('Invalid release policy')
  }

  return {
    version: value.version,
    releaseId: value.releaseId,
    commitSha: value.commitSha,
    environment: value.environment,
    riskLevel,
    requiredChecks
  }
}

function parseEvidenceFile(value: unknown): EvidenceFile {
  if (
    !isRecord(value) ||
    typeof value.releaseId !== 'string' ||
    !Array.isArray(value.checks) ||
    !value.checks.every(isCheckEvidence) ||
    !hasUniqueIds(value.checks)
  ) {
    throw new Error('Invalid evidence file')
  }
  return { releaseId: value.releaseId, checks: value.checks }
}

function isRequirement(value: unknown): value is Requirement {
  return isRecord(value) &&
    typeof value.id === 'string' &&
    typeof value.maxAgeMinutes === 'number' &&
    Number.isFinite(value.maxAgeMinutes) &&
    value.maxAgeMinutes >= 0
}

function isCheckEvidence(value: unknown): value is CheckEvidence {
  return isRecord(value) &&
    typeof value.id === 'string' &&
    (value.status === 'passed' ||
      value.status === 'failed' ||
      value.status === 'cancelled') &&
    typeof value.sourceSha === 'string' &&
    typeof value.completedAt === 'string' &&
    typeof value.detailsUrl === 'string'
}

function hasUniqueIds(values: ReadonlyArray<{ id: string }>): boolean {
  return new Set(values.map((value) => value.id)).size === values.length
}

function isRecord(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null
}

5.2 门禁结果必须进入平台规则 ​

只有脚本退出非零还不够。仓库规则、环境保护或发布编排器必须把该结果设置为必需状态，并确保：

  • 检查针对最新提交，代码变化后旧审批失效。
  • 普通提交者不能修改保护规则或伪造同名状态。
  • 发布身份只部署已批准的不可变制品。
  • 管理员绕过也会留下审计记录。

6. 失败、不可用与例外流程 ​

6.1 区分产品失败和证据不可用 ​

状态示例默认处置
产品失败单元断言失败、契约不兼容、关键 E2E 复现缺陷修复后重跑
环境失败Runner 宕机、测试环境 DNS 故障恢复环境并重跑，不当作通过
偶发失败未改代码重跑通过记录 flaky，达到预算后阻塞治理
证据过期检查针对旧 SHA 或超过有效期对当前对象重新验证
策略误配文档变更错误触发支付专项评审修正规则并留下变更记录

“无法运行”不等于“检查通过”。紧急情况下可以走受控例外，但不能把 cancelled 转换成绿色。

7. 质量度量 ​

7.1 结果指标 ​

  • 变更失败率：导致服务降级并需要回滚、热修或紧急修复的部署数 ÷ 总部署数。
  • 逃逸缺陷：进入目标环境后才发现、且发布前证据本应发现的缺陷，按严重度分类。
  • 回滚/热修次数：说明发布结果，但不能脱离发布频率和变更规模解读。
  • 业务路径成功率：例如订单导出创建与下载成功率，应在灰度和发布后观察。

测试在 CI 中失败不属于变更失败率；它表示门禁在发布前阻止了问题。不要为了指标好看而把不同阶段的失败混成一个数。

7.2 门禁健康指标 ​

  • 门禁耗时：从候选提交就绪到必需检查完成的 p50/p95，包括队列与执行时间。
  • 偶发失败率：同一代码和输入下首次失败、无修改重跑通过的执行数 ÷ 总执行数。
  • 误阻塞率：最终确认不是产品问题的阻塞次数 ÷ 总阻塞次数。
  • 绕过率：通过例外或管理员绕过的发布数 ÷ 总发布数。
  • 失效门禁数：长期不再发现问题、无人负责或无法解释风险映射的规则数量。

这些指标衡量门禁是否可信和可用。它们不是个人绩效指标，否则团队会隐藏偶发失败、减少测试或规避发布记录。

看板必须带分子、分母、窗口和处置，不能只展示红绿灯。样本很小时应查看原始事件，不要从单周百分比得出长期趋势。

7.4 覆盖率不是发布信心分数 ​

覆盖率说明哪些代码被执行过，不说明断言是否有效，也不证明部署、接口和用户流程。它可以作为寻找盲区的观察项；只有针对少数高风险模块、并结合分支含义时，才适合设置审慎阈值。

不要把覆盖率、缺陷数、评审人数和 E2E 数量加权成一个“87 分信心值”。不同证据不能互相抵消：认证契约失败时，更多单元测试不能把它补成通过。

8. 门禁治理与持续复查 ​

8.1 每条规则都有所有者和处置路径 ​

门禁定义应记录：保护的风险、负责人、触发范围、失败说明、重跑条件、服务级目标和退出条件。无人维护的必需检查最终只会被习惯性绕过。

检查失败信息要告诉开发者：失败事实、报告地址、常见原因和下一步，而不是只显示 quality-gate: failed。

8.2 变更后重算策略 ​

以下变化需要重新计算门禁，而不是复用旧结论：

  • 提交 SHA、锁文件、构建参数或运行时配置变化。
  • 风险标签、目标环境或功能开关范围变化。
  • 依赖契约出现新版本。
  • 人工审批后又修改了其审查范围内的代码。
  • 制品被重新构建，摘要发生变化。

8.3 删除低价值门禁 ​

满足以下任一条件时应复查、降级或删除：长期从未发现对应问题；与另一检查证明同一事实；误报长期超预算；风险已经由架构约束消除；失败后没有任何负责人处置。

删除前要确认风险已被其他证据覆盖。目标是让每个红灯都值得停下来，而不是让门禁数量持续增加。

9. 常见反模式 ​

反模式后果修正
所有检查都阻塞所有变更反馈慢，团队开始绕过用路径与风险触发条件门禁
只检查状态，不校验 SHA/制品旧结果批准新代码绑定不可变源码和制品摘要
CI 不可用就视为通过缺少证据仍进入生产明确失败、不可用和受控例外
用重试隐藏 flaky通过率变好，可信度下降记录首次失败并按预算治理
自动更新快照或基准回归直接变成正确结果人工审查差异后更新
用单一质量分数放行高风险失败被低价值数量抵消每个关键风险使用独立必需证据

10. 发布门禁检查表 ​

  • 每条必需检查是否映射到明确风险？
  • 风险等级是否由规则和领域负责人共同确定，而非作者任意降级？
  • 证据是否包含状态、源码 SHA、制品摘要、完成时间和详情链接？
  • 合并、发布候选、渐进发布和发布后是否分别证明不同事实？
  • 检查失败、环境不可用、偶发失败和证据过期是否明确区分？
  • 例外是否限定发布与时间，并有风险接受人、补偿措施和跟踪项？
  • 指标是否给出分子、分母、时间窗口、预算和处置？
  • 门禁耗时、误阻塞、偶发失败和绕过率是否持续治理？
  • 代码或制品变化后，旧审批和旧证据是否自动失效？
