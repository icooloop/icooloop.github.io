组件测试 ​

作者：codex-gpt-sol-5.6

组件测试在模拟 DOM 中渲染一个 UI 边界，通过用户能够观察和操作的元素验证输入、交互、异步状态与输出。它比纯函数测试更接近真实使用，又比完整页面集成测试更容易定位失败。

本文使用 Vue 3、Vitest 和 Vue Testing Library。示例测试一个异步导出按钮，不启动 Router、Pinia 或真实 HTTP；这些组合属于集成测试。

1. 组件测试的边界 ​

1.1 应当验证什么 ​

  • Props 改变后用户看到的内容和可用状态。
  • 点击、键盘输入等真实 DOM 事件触发的行为。
  • loading、成功、错误和禁用状态。
  • 对外事件或回调携带的业务数据。
  • 可访问名称、角色、焦点和状态通知。

组件测试不应断言 ref 的内部值、私有方法调用次数、生成的 Vue 实例结构或所有 CSS 类名。它们通常是实现细节，不能直接证明用户行为。

1.2 与相邻测试层的区别 ​

测试保留真实的部分典型替换
单元测试纯计算或状态转换所有外部副作用
组件测试单个组件、Vue 渲染和 DOM 事件组件外服务、复杂子系统
集成测试页面、子组件、Store、Router、访问层的组合远程 HTTP 或第三方系统
E2E浏览器、构建产物和部署链路非目标第三方或破坏性操作

3. 查询、事件与等待 API ​

3.1 render 与 screen ​

render(Component, options) 挂载组件并返回 rerender、emitted 等辅助能力；screen 从当前文档查询元素。

查询优先级应接近用户理解页面的方式：

  1. getByRole 配合可访问名称。
  2. getByLabelText、getByPlaceholderText 等表单语义。
  3. getByText 处理非交互内容。
  4. 只有没有稳定语义时才使用 getByTestId。

getBy* 找不到或找到多个会立即抛错，适合当前应存在的元素；queryBy* 找不到返回 null，适合断言不存在；findBy* 返回 Promise，适合等待稍后出现的元素。

3.2 fireEvent 与真实交互 ​

Vue Testing Library 的 fireEvent.click、fireEvent.update 会派发 DOM 事件并等待 Vue 更新。不要直接调用组件方法代替点击，否则事件绑定、禁用状态和 DOM 语义都没有被验证。

复杂键盘序列可采用 @testing-library/user-event，但它是独立包。无论使用哪种工具，都应从用户入口触发行为。

3.3 findBy* 与 waitFor ​

当异步结果最终出现在 DOM 中，优先使用 findByRole 等查询；当等待的是函数调用或元素属性变化，使用 waitFor：

ts
await waitFor(() => expect(createTask).toHaveBeenCalledOnce())
1

不要使用固定 setTimeout 等待。waitFor 会重复执行回调直到通过或超时，回调中必须包含会抛错的断言。

4. 完整示例：异步导出按钮 ​

4.1 组件实现 ​

vue
<!-- src/components/ExportButton.vue -->
<script setup lang="ts">
import { computed, ref } from 'vue'

const props = defineProps<{
  selectedCount: number
  createTask: () => Promise<void>
}>()

const emit = defineEmits<{
  completed: []
}>()

const busy = ref(false)
const error = ref('')
const disabled = computed(() => props.selectedCount === 0 || busy.value)

async function submit() {
  if (disabled.value) return
  busy.value = true
  error.value = ''

  try {
    await props.createTask()
    emit('completed')
  } catch {
    error.value = '导出任务创建失败，请重试'
  } finally {
    busy.value = false
  }
}
</script>

<template>
  <button type="button" :disabled="disabled" @click="submit">
    {{ busy ? '正在创建…' : `导出 ${selectedCount} 条订单` }}
  </button>
  <p v-if="error" role="alert">{{ error }}</p>
</template>

import ExportButton from './ExportButton.vue'

it('disables export when no order is selected', async () => {

4.3 异步状态与事件 ​

ts
import { fireEvent, render, screen } from '@testing-library/vue'
import { expect, it, vi } from 'vitest'
import ExportButton from './ExportButton.vue'

function deferred<T>() {
  let resolve!: (value: T | PromiseLike<T>) => void
  let reject!: (reason?: unknown) => void
  const promise = new Promise<T>((ok, fail) => {
    resolve = ok
    reject = fail
  })
  return { promise, resolve, reject }
}

it('prevents duplicate submission and emits completed', async () => {
  const request = deferred<void>()
  const createTask = vi.fn(() => request.promise)
  const { emitted } = render(ExportButton, {
    props: { selectedCount: 2, createTask }
  })

  await fireEvent.click(screen.getByRole('button', { name: '导出 2 条订单' }))

  const busyButton = screen.getByRole('button', { name: '正在创建…' })
  expect(busyButton).toBeDisabled()
  await fireEvent.click(busyButton)
  expect(createTask).toHaveBeenCalledOnce()

  request.resolve()

  expect(await screen.findByRole('button', { name: '导出 2 条订单' })).toBeEnabled()
  expect(emitted('completed')).toHaveLength(1)
})

5. 子组件、插槽与全局依赖 ​

5.1 使用真实轻量子组件 ​

默认保留与父组件共同形成用户行为的轻量子组件。全部 shallowMount 后只验证 Stub 名称，容易漏掉事件、插槽和可访问语义的组合问题。

昂贵图表、编辑器或跨域 SDK 可以替换为遵守其公共 Props/事件契约的最小 Stub。此时应另有该子系统自己的测试。

5.2 插槽和 Teleport ​

通过 render 的 slots 提供真实内容，并从 DOM 结果断言。对话框使用 Teleport 时，测试后要清理目标容器；Vue Testing Library 默认会在测试框架钩子中清理已渲染内容，但自行创建的全局节点仍由测试负责。

5.3 Router、Pinia 与国际化 ​

仅验证组件如何调用一个窄接口时，可通过 Props 或 global.mocks 提供替身。若测试声称验证导航、Store 状态或翻译资源组合，应安装真实插件并升级为集成测试。

6. 可访问性与浏览器限制 ​

6.1 语义查询能发现什么 ​

getByRole 会迫使测试使用浏览器可访问树中的角色和名称，能发现按钮没有名称、标签未关联输入框等问题。jest-dom 还可以断言焦点、可见性和表单状态。

它不能证明颜色对比、屏幕阅读器实际播报、真实 Tab 顺序或浏览器布局。自动化可访问性扫描也只能发现规则可编码的部分。

6.2 jsdom 不能证明什么 ​

jsdom 不进行真实排版和绘制，元素尺寸、滚动吸附、下载、原生验证 UI、媒体查询和部分 Selection API 可能与浏览器不同。遇到这些边界，应使用 Playwright 组件测试或 E2E，而不是写越来越复杂的假实现。

7. 常见失败与调试 ​

症状原因修正
找不到按钮元素没有可访问名称，或查询时机错误检查语义；异步出现用 findBy*
“找到多个元素”查询范围过宽用名称或 within 缩小范围
点击后断言偶发失败没等待 Promise 或 Vue 更新await fireEvent、findBy* 或 waitFor
重构模板测试全坏使用类名、选择器或组件实例按角色和可见结果查询
shallow 测试全部通过但页面失败子组件契约被 Stub 掩盖保留真实轻量子组件，补集成测试
jsdom 中尺寸永远为 0环境不做布局在真实浏览器验证布局

失败时可使用 screen.debug() 临时输出当前 DOM，或使用 Testing Playground 推荐查询。不要把巨大的 DOM 快照当成长期断言。

8. 组件测试检查表 ​

  • 测试是否从 Props、插槽和用户事件进入？
  • 断言是否观察文本、角色、状态、焦点或对外事件？
  • 是否覆盖 idle、busy、success、error 和 disabled 等真实状态？
  • 异步行为是否用可控 Promise，而不是固定等待？
  • 子组件替换是否保留了本次测试所需的公共契约？
  • jsdom 无法证明的布局和浏览器行为是否交给更高层？
